# Folio: 10 Synthetic Long-Document Acceptance Test Cases

> 中文版: [中文版](README.zh-CN.md)

These cases provide fictional business materials ready for upload, copyable user requirements, and delivery blueprints for the expected Word documents. They test the complete workflow from source research to final document delivery. All content is synthetic and contains no original user materials, credentials, or real personal information.

**The delivery blueprints are not completed business deliverables.** `expected/交付预期.docx` specifies the target filename, table of contents, minimum depth required for each chapter, facts that must be correct, calculation results, charts and diagrams, information gaps, and acceptance criteria. The actual long-form documents must be generated by the agent under test. Generating the attachments does not invoke a model, access the internet, or consume Tavily quota.

## Case Directory

| ID | Business Scenario | Target Document | Target Body Length | Key Checks |
| --- | --- | --- | --- | --- |
| TC01 | Expense Reimbursement and Business Travel | User Requirements Document (URD) | 15,000–20,000 | Policy effective dates, monetary thresholds, approval responsibilities, reimbursement calculations |
| TC02 | Omnichannel Order Fulfillment | Software Requirements Specification (SRS) | 25,000–35,000 | Payment timeout race conditions, idempotency, funds reserved for refunds, amount allocation, state diagrams |
| TC03 | Manufacturing Quality Traceability | SRS | 35,000–45,000 | Cross-sheet relationships, complete fields, batch splitting, recall quantities, hidden sheets |
| TC04 | Customer Service Ticket Center | URD | 20,000–30,000 | Applicability of old and new policies, unresolved conflicts, SLAs, permissions and interfaces |
| TC05 | Inventory and Replenishment Business Analysis | General Analysis Report | 18,000–25,000 | Time windows, net sales, refunds, inventory positions, pack-size rounding and budgets |
| TC06 | Platform Operations Handover | General Operations Manual | 25,000–35,000 | Insufficient source materials, 3 local research rounds, 2 mock web research rounds, labeling model-supplied additions |
| TC07 | Campus Services Portal | URD | 25,000–35,000 | PPT files, prototype images, scanned pages, mixed-content PDFs, exceptions found only in images |
| TC08 | Data Governance Platform | SRS | 50,000–65,000 | Long source files, coverage of all fields and interfaces, supplementary rules at the end |
| TC09 | IT Business Continuity Exercise | General Execution Manual | 30,000–40,000 | Cross-team procedures, recovery metrics, time zones, rollback thresholds, long decision tables |
| TC10 | Group-Wide Integrated Operations Platform | SRS | 80,000–100,000 | 148 source materials, 12 business domains, 144 requirement cards, 48 interfaces, recovery and long-document formatting |

Length is measured consistently in **effective body characters**: Chinese characters, English letters, and digits are counted individually, including table content but excluding the cover, table of contents, headings, headers and footers, whitespace, and punctuation. Page counts depend on fonts, images, and tables, so no strict page-count threshold applies. Repeated copies of the same paragraph or table must not be used to meet the length requirement.

The recommended sequence is **TC01 → TC02 → TC05 → TC04/03/07 → TC06 → TC08/09 → TC10**. The 80,000–100,000-character range is a stress-test acceptance target; it does not imply that the current default time and call budgets are sufficient to complete it. Record the configuration, quota, and interruption reason for every run to avoid conflating budget-related termination with errors in business understanding.

## How to Use Each Case Package

```text
cases/01_expense_urd/
  sources/                 Uploadable mock source materials, including actual Office/PDF/image files
  upload_sources.zip       Source materials only; extract and batch-upload the files inside
  prompt.txt               Generation requirements to copy into the conversation
  manifest.json            File list, types, sizes, and SHA-256 hashes for testers
  expected/
    交付预期.docx           Human-readable expected document blueprint and acceptance criteria
    expected.json          The same evaluation criteria in structured form
```

1. Start a separate conversation and state the document type in the writing request. The GUI has no document-type selector. CLI/API users may explicitly configure URD/SRS guides; general documents need no guide.
2. Upload only the files under `sources/`. The GUI does not accept ZIP files; extract them first. Do not upload `expected/`, `recipes/`, `manifest.json`, materials from other cases, or mock web responses. This prevents expected answers from entering the model’s research materials.
3. Send `prompt.txt`, verify that the complete table of contents covers the specified scope, and then confirm generation. Chapters may use equivalent titles or be divided reasonably, but they must contain substantive content rather than headings alone.
4. Save the actual Word document, task ID, configuration snapshot, elapsed time, call count, source coverage records, and items requiring confirmation. Verify research rounds by business task; do not mistake the call count for the entire job for the 3 rounds allowed for an individual task.
5. Check each item against `交付预期.docx`. Verify amounts, times, effective scope, negations, and exceptions against the original materials. Where images have been generated, also verify the actual business branches represented and the clarity of the final images.

`manifest.json` is the test package inventory. The application must still perform its own preprocessing and generate a source Manifest and structure files; this inventory cannot be treated as evidence that research has already been completed. Prototype and scanned-page content exists only in the corresponding uploaded originals. Text in the recipes is used solely to reconstruct test data and must not be provided to the model under test.

## Five Acceptance Variants Using Uploaded Templates

The original 10 cases continue to test free-form planning. `template_variants/` provides 5 additional actual DOCX templates that reuse the source materials and business requirements of the corresponding cases. The original case answers are neither modified nor copied into the templates.

| ID | Reused Case | Template Focus |
| --- | --- | --- |
| TV01 | TC01 Expense Reimbursement URD | Fixed chapter titles and order; renaming, deleting chapters, or adding subheadings is not permitted |
| TV02 | TC02 Order SRS | Two required tables in the same chapter have identical column names; they must be completed separately and must not be merged or counted twice |
| TV05 | TC05 Inventory Analysis Report | Preserve the two-row merged header; do not merge data rows; blank rows do not count as completed table entries |
| TV06 | TC06 Operations Manual | Required chapters and the recovery parameter table must be retained; RTO/RPO and other parameters not approved in the source materials must remain marked as requiring confirmation |
| TV08 | TC08 Data Governance Long Document | Retain 14 fixed top-level chapters; expand subsections only within Chapters 3 through 12; the target remains 50,000–65,000 effective characters |

For example, `template_variants/02_order_srs/` contains `文档模板.docx`, `prompt.txt`, `expected.json`, and `manifest.json`. Start a new conversation, upload this **DOCX and designate its purpose as “Template”**, then upload the business materials from the original `cases/02_order_srs/sources/` directory and send the variant’s `prompt.txt`. Do not upload `expected.json`, `manifest.json`, or the original case’s `expected/` directory. The variant Manifest only helps testers locate the original materials and verify their hashes.

All templates deliberately use Arial/FangSong body fonts, 17-point top-level headings, nondefault page margins, headers and footers, and a `{{document_title}}` cover. The body also contains clearly labeled example text from an old project. Acceptance checks must confirm all of the following: template examples have not been used as business evidence or document-wide facts; completion instructions and examples have been removed from the deliverable; the fixed structure, every required table, and template formatting have been retained; and actual business facts, calculations, charts and diagrams, and length still meet the original case’s delivery expectations. Template requirements are stricter than the original free-generation cases, which allow equivalent headings.

Disable web access when manually evaluating TV06 in the GUI. If using a test driver, reuse only the original TC06 offline mock web responses. Generic recovery targets found online must not be treated as project-approved metrics. Retaining items that require confirmation can produce a correct draft; parameters must not be fabricated merely because a table is mandatory.

Rebuilding and offline checks involve local files only, do not invoke a model, and do not modify the original 10 source packages:

```bash
uv run python examples/acceptance_cases/build_template_variants.py
uv run pytest -q tests/test_template_acceptance_cases.py
```

These variants have been verified for file parseability and template-constraint extraction. **This does not mean they have passed long-document generation acceptance testing with a real model.** Actual outputs still require manual review of business content, template consistency, and Word/PDF pages. Each `expected.json` explicitly records this limitation. The original `folio-10-cases.zip` contains only the original 10 cases; the additional template variants are provided separately under `template_variants/`.

## How to Evaluate Expected Results

- **Pass**: The table-of-contents scope, key facts, complete item coverage, required charts and diagrams, length, and final formatting all meet the requirements, and all newly introduced recommendations are clearly labeled.
- **Draft with correctly retained gaps**: Unresolved conflicts such as those in TC04 and unapproved parameters such as those in TC06 are accurately retained in the body and issue table. Unresolved items that the case explicitly requires to be retained are not business errors in themselves. Failure to meet the length requirement, omission of available facts, or technical interruption must still be recorded separately as failures.
- **Business failure**: Incorrect thresholds, calculation errors, use of the wrong version, omitted exceptions, fabricated approvals or sources, omitted required fields, or model recommendations presented as confirmed facts.
- **Technical or formatting failure**: Tool/service failure, exhausted quota, missing chapters, no deliverable, missing images or unreadable text within images, tables extending beyond page boundaries, or duplicated body content.

Each case’s `expected.json` includes fact locations and calculation rules. `required_tokens` is used only to identify potential omissions. Matching these terms does not prove that a sentence correctly expresses causality, negation, scope, or numerical relationships. Complete semantics and consistency between text and visuals still require manual review.

## TC06 Mock Web Access Notes

TC06 additionally includes `mock_web.json`, whose two rounds of results use fictional `example.invalid` addresses. These are not real web pages, and no HTTP requests are sent. The file remains on the test-driver side and is not uploaded to the source repository. `mock_web.py` provides `FixtureWebKnowledge`, which can be injected through `Engine(..., web_knowledge=fixture)` for **isolated, single-business-task tests**. This object records call counts; a third call raises an error and is counted as an attempt.

`tests/test_acceptance_cases.py` uses a controlled Runtime to keep recovery-metric gaps unresolved while exercising 3 local research rounds, two rounds of offline web responses, and subsequent completion. It also prohibits actual HTTP access. This verifies workflow order; it does not simulate the actual writing quality of a 30,000-character deliverable. A complete multitask job must not share a single instance containing only two responses and use that result to infer outcomes for each task.

When only the TC06 materials are uploaded to the GUI, the model may determine early that a subtask already has sufficient information. This is normal early termination. The GUI does not currently load the mock adapter in this directory automatically. Testers may disable web access to inspect how final information gaps are handled. Testing actual Tavily access requires separate configuration and separate recording of live results; those results must not be treated as the same deterministic test as the fixed mock results.

## Rebuilding and Validation

Run from the project root:

```bash
# Dependencies come from the current project; rebuilding PDF/PNG files also requires Playwright Chromium to be installed.
uv run python examples/acceptance_cases/build_cases.py

# Rebuild a single case; use --output to specify a new output directory if needed.
uv run python examples/acceptance_cases/build_cases.py --case TC01

# Validate that all sources can be parsed by the project's actual readers, along with Manifest hashes, calculation results, and the offline 3+2 workflow.
uv run pytest -q tests/test_acceptance_cases.py tests/test_acceptance_output_counting.py
```

Recipes are located in `recipes/*.json` and use actual business data to generate real DOCX, XLSX, PPTX, PDF, PNG, Markdown, and TXT files. Standard PDF pages contain extractable text; `scan_pdf` or mixed-content pages with `scan: true` produce image-only pages without a text layer. Rebuilding produces consistent content, but timestamps in Office/PDF containers may change binary hashes. The new Manifest records the updated hashes accordingly.

If Chromium is unavailable in the environment, install it using the project’s existing illustration setup process or `uv run playwright install chromium`. No image generation service is required. Test images are programmatically rendered business wireframes and scanned materials.

Actual deliverables can first undergo offline screening:

```bash
uv run python examples/acceptance_cases/check_output.py \
  01_expense_urd /绝对路径/实际生成文件.docx \
  --report artifacts/acceptance/TC01-check.json
```

The report provides the effective body character count, headings, table/image counts, long repeated paragraphs, and signals of missing factual terms and coverage identifiers. It always sets `requires_manual_review`. Character counting depends on proper heading styles; unstyled tables of contents or covers require manual correction. The report does not replace checks of actual pagination and fonts in Word/WPS. The expected blueprint is far shorter than the target deliverable and cannot substitute for acceptance testing of the actual output.

The complete test package is `folio-10-cases.zip` in the same directory, accompanied by `测试案例总览.docx`. Each case’s `upload_sources.zip` contains only that case’s original source materials.
