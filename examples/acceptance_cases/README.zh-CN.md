# Folio：10 套合成长文档验收案例

> English version: [English version](README.md)

这些案例提供可直接上传的虚构业务资料、可复制的用户要求，以及预期 Word 的交付蓝图。它们用于检验从资料研究到最终文档的完整流程，全部内容均为合成数据，不含用户原始资料、密钥或真实个人信息。

**交付蓝图不是已经生成的业务成品。** `expected/交付预期.docx` 描述目标文件名、目录、各章最低展开量、必须正确的事实、计算答案、图表、缺口和验收条件；实际长文应由待测智能体生成。生成附件不调用模型、不联网，也不消耗 Tavily 额度。

## 案例目录

| 编号 | 业务场景 | 目标文档 | 正文目标 | 重点检查 |
| --- | --- | --- | --- | --- |
| TC01 | 费用报销与差旅 | 用户需求说明书 URD | 1.5～2 万 | 制度生效日期、金额边界、审批职责、报销核算 |
| TC02 | 全渠道订单履约 | 软件需求规格说明书 SRS | 2.5～3.5 万 | 支付超时竞态、幂等、退款占用、金额分摊、状态图 |
| TC03 | 制造质量追溯 | SRS | 3.5～4.5 万 | 多 Sheet 关联、完整字段、批次拆分、召回数量、隐藏 Sheet |
| TC04 | 客服工单中心 | URD | 2～3 万 | 新旧制度适用范围、未决冲突、SLA、权限与界面 |
| TC05 | 库存与补货经营分析 | 通用分析报告 | 1.8～2.5 万 | 时间窗口、净销售、退款、库存位置、包装取整与预算 |
| TC06 | 平台运维交接 | 通用运维手册 | 2.5～3.5 万 | 资料不足、本地 3 轮、Mock 联网 2 轮、标注模型补全 |
| TC07 | 校园服务门户 | URD | 2.5～3.5 万 | PPT、原型图、扫描页、混排 PDF、仅在图片中的例外 |
| TC08 | 数据治理平台 | SRS | 5～6.5 万 | 长源文件、全字段与全接口覆盖、末尾补充规则 |
| TC09 | IT 业务连续性演练 | 通用执行手册 | 3～4 万 | 跨团队步骤、恢复指标、时区、回滚门槛、长决策表 |
| TC10 | 集团一体化运营平台 | SRS | 8～10 万 | 148 份资料、12 业务域、144 张需求卡、48 个接口、恢复和长文排版 |

字数统一按**正文有效字符**计：汉字、英文字母、数字逐字符计数，计入表格内容，不计封面、目录、标题、页眉页脚、空白和标点。页数受字体、图片和表格影响，不设硬性页数门槛。不得用同一段落、同一表格反复复制补足字数。

推荐顺序为 **TC01 → TC02 → TC05 → TC04/03/07 → TC06 → TC08/09 → TC10**。8～10 万字是压力验收目标，不能据此推断当前默认时间和调用预算一定能完成。每次运行记录配置、额度和中断原因，避免把因预算不足退出与业务理解错误混为一谈。

## 每套文件怎么使用

```text
cases/01_expense_urd/
  sources/                 可上传的 Mock 原件，包含真实 Office/PDF/图片文件
  upload_sources.zip       仅打包资料；解压后批量上传其中的文件
  prompt.txt               复制到对话框的生成要求
  manifest.json            测试人员使用的文件清单、类型、大小和 SHA-256
  expected/
    交付预期.docx           人工可读的预期文档蓝图与验收标准
    expected.json          同一套结构化判定依据
```

1. 新建独立会话，在生成要求中说明本案例的文档类型；GUI 没有文档类型选择器。CLI 可显式设置 URD/SRS 写作指南。
2. 仅上传 `sources/` 下的文件。GUI 不接收 ZIP，请先解压。不要上传 `expected/`、`recipes/`、`manifest.json`、其他案例资料或 Mock 网页响应；这样可以避免预期答案进入模型的研究资料。
3. 发送 `prompt.txt`，核对完整目录是否覆盖指定范围，再确认生成。章节可以采用等价标题或合理拆分，不能只保留标题而没有实际内容。
4. 保存实际 Word、任务 ID、配置快照、耗时、调用数、资料覆盖记录和待确认项。研究次数按业务任务核对，不将全作业的调用数误当成单任务 3 轮。
5. 对照 `交付预期.docx` 逐项核验。对金额、时间、生效范围、否定和例外使用原件核对；图片有生成还需要核对实际业务分支和成品清晰度。

`manifest.json` 是测试包清单。应用内部仍应自行预处理并生成资料 Manifest 和结构文件，不能将本清单当作已经完成研究的证据。原型和扫描页的内容只存在于相应上传原件；配方中的文本仅用于重建测试数据，不能提供给被测模型。

## 上传模板的五个验收变体

原有 10 案继续测试自由规划。`template_variants/` 另提供 5 个真实 DOCX 模板，复用对应案例的原始资料和业务要求，不修改或复制原案例答案到模板中。

| 编号 | 复用案例 | 模板重点 |
| --- | --- | --- |
| TV01 | TC01 费用报销 URD | 固定章节标题和顺序，不允许自行改名、删章或增加子标题 |
| TV02 | TC02 订单 SRS | 同一章节有两张列名相同的必填表，必须分别填写，不能合并或重复计数 |
| TV05 | TC05 库存分析报告 | 保留两行合并表头，数据行不合并；空白行不能算完成填表 |
| TV06 | TC06 运维手册 | 必需章节与恢复参数表必须保留；资料没有批准的 RTO/RPO 等仍写待确认 |
| TV08 | TC08 数据治理长文 | 保留 14 个固定一级章节，只在第 3 至 12 章内扩展子章节，目标仍为 5～6.5 万有效字符 |

例如 `template_variants/02_order_srs/` 包含 `文档模板.docx`、`prompt.txt`、`expected.json` 和 `manifest.json`。新建会话，上传这个 **DOCX 并将用途标为“模板”**，再上传原 `cases/02_order_srs/sources/` 中的业务资料，发送变体的 `prompt.txt`。不要上传 `expected.json`、`manifest.json` 或原案例 `expected/`；变体 Manifest 仅帮助测试人员定位原资料及核对摘要。

所有模板都特意设置了 Arial/仿宋正文、17 磅一级标题、不同于默认值的页面边距、页眉页脚和 `{{document_title}}` 封面。正文里还放了一个明确标注的旧项目示例数字。验收时应同时确认：模板示例没有进入业务证据或全局事实；成品删除填写说明和示例；固定结构、每张必填表及模板格式保留；真实业务事实、计算、图表、篇幅继续按原案例的交付预期检查。模板要求比原自由生成案例的“允许等价标题”更严格。

TV06 在 GUI 人工验收时关闭联网。若使用测试驱动，仅复用原 TC06 的离线 Mock 网页响应；不能把网上的通用恢复目标当作项目已经批准的指标。需要保留的待确认项可以形成正确的草稿，不因表格必填而编造参数。

重建和离线检查只涉及本地文件，不调用模型，也不改动原来的 10 套资料：

```bash
uv run python examples/acceptance_cases/build_template_variants.py
uv run pytest -q tests/test_template_acceptance_cases.py
```

这些变体已验证文件可解析及模板约束可提取，**不表示已经通过真实模型的长文生成验收**。实际输出还需人工检查业务内容、模板一致性和 Word/PDF 页面；每份 `expected.json` 均明确记录这个边界。原 `folio-10-cases.zip` 只包含原 10 案，新增模板变体在 `template_variants/` 单独提供。

## 预期结果如何判定

- **正常通过**：目录范围、关键事实、全量条目、必要图表、字数和成品版式均符合要求，所有新增建议有明确标记。
- **正确保留缺口的草稿**：如 TC04 的未决冲突、TC06 的未批准参数，在正文和问题表中准确保留；案例要求保留的未决项本身不构成业务错误。未达到字数、缺失已有事实或技术中断仍须单列失败。
- **业务失败**：错误阈值、错算金额、误用版本、漏掉例外、伪造批准/来源、遗漏指定字段、把模型建议写成已确认事实。
- **技术或版式失败**：工具/服务失败、额度耗尽、缺章、无成品、图片缺失或图中文字无法阅读、表格越界、重复正文。

每案的 `expected.json` 包含事实位置和计算规则。`required_tokens` 只用于查找遗漏信号，命中这些词不能证明句子的因果、否定、范围或数字关系正确。完整语义与图文一致性仍需人工复核。

## TC06 的 Mock 联网说明

TC06 额外包含 `mock_web.json`，其中两轮结果来自 `example.invalid` 虚构地址，不是真实网页，不会发出 HTTP 请求。它留在测试驱动侧，不上传资料库。`mock_web.py` 提供 `FixtureWebKnowledge`，可通过 `Engine(..., web_knowledge=fixture)` 注入**隔离的单业务任务测试**；该对象记录次数，第三次调用会报错并计入尝试。

`tests/test_acceptance_cases.py` 用受控 Runtime 保持恢复指标缺口未解决，走过本地 3 轮、两轮离线网页响应及补全；同时禁止真实 HTTP。这验证流程顺序，不模拟 3 万字成品的真实写作质量。完整多任务作业不能共享只有两次响应的单实例来推断每任务结果。

仅把 TC06 资料上传 GUI，模型可能提前确认某个子任务已有足够资料；这属于正常提前结束。GUI 目前不会自动加载本目录的 Mock 适配器。测试人员可关闭联网检查最终缺口处理；测试真实 Tavily 时需另行配置，并单独记录实时结果，不能与固定 Mock 结果比较为同一个确定性测试。

## 重建与验证

在项目根目录执行：

```bash
# 依赖来自当前项目；PDF/PNG 重建还需要已安装的 Playwright Chromium。
uv run python examples/acceptance_cases/build_cases.py

# 仅重建一套，也可以用 --output 指定新的输出目录。
uv run python examples/acceptance_cases/build_cases.py --case TC01

# 验证全部来源能由项目实际读取器解析、Manifest 摘要、计算答案和离线 3+2 流程。
uv run pytest -q tests/test_acceptance_cases.py tests/test_acceptance_output_counting.py
```

配方位于 `recipes/*.json`，使用实际业务数据生成真实 DOCX、XLSX、PPTX、PDF、PNG、Markdown、TXT。普通 PDF 页有可提取文本；`scan_pdf` 或混排页的 `scan: true` 会生成只有图片的页面，不附带文字层。重建生成内容一致，Office/PDF 容器时间戳可能使二进制哈希变化，新的 Manifest 会同步记录新摘要。

如果环境没有 Chromium，使用项目已有的配图安装流程或 `uv run playwright install chromium` 安装；无需图片生成服务。测试图像是程序渲染的业务线框和扫描资料。

实际成品可以先做离线初筛：

```bash
uv run python examples/acceptance_cases/check_output.py \
  01_expense_urd /绝对路径/实际生成文件.docx \
  --report artifacts/acceptance/TC01-check.json
```

报告提供正文有效字符数、标题、表格/图片数量、长重复段落、事实词和覆盖编号的缺失信号，始终标记 `requires_manual_review`。字数检测依赖真实标题样式；无样式的目录或封面需人工校正，报告不替代 Word/WPS 的实际分页和字体检查。预期蓝图长度远小于目标成品，不能用它代替实际结果验收。

全部测试包为同目录下的 `folio-10-cases.zip`，并附有 `测试案例总览.docx`；各案例的 `upload_sources.zip` 只包含该案例原始资料。
