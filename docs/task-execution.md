# Business Task Execution Design

> 中文版: [中文版](task-execution.zh-CN.md)

This document describes the current implementation; updates to meeting minutes are out of scope.

## Document Structure and Execution Plan

DocPlan stores stable document nodes, ordering, heading levels, writing constraints, and node purposes. WorkPlan stores business execution units; the two do not use the same granularity. The LLM proposes groupings based on the complete content-node index, user requirements, and material index, rather than grouping by a fixed heading level such as level 1, level 3, or leaf headings.

Each WorkTask contains `task_id`, `title`, `objective`, `section_ids`, `questions`, `depends_on`, `completion_criteria`, and `rationale`. Programmatic validation checks that task IDs are unique; content-node coverage is complete, with exactly one writing owner per node; containers cannot be assigned writing work; dependencies exist and are acyclic; and the number of nodes per task complies with configuration. Format and constraint errors are returned to the model for correction, subject to the existing retry and total-call budgets.

Initial planning reads the titles and character counts of local factual materials, the local knowledge-file index, or the remote dataset ID. Finished-document examples are excluded from the factual index. The index is bounded: node writing instructions display at most 600 characters and indicate whether they have been truncated; execution reads the full instructions. When remote materials have not yet been retrieved, their quantity is explicitly marked as unknown rather than implying a complete understanding of the knowledge base.

When there are at least 4 tasks, the longest dependency path has at least 3 levels, and parallel execution is allowed, `audit_work_dependencies` may run once before execution or on resume. The model returns only retain, remove, or uncertain for candidate edges, with brief reasons; it does not rewrite tasks. At most 16 edges are checked, with a 20-second call timeout and no retries. If the context is too large, the call is unavailable, or the result is incomplete, generation continues with the original graph. Only incoming edges of tasks with neither a WorkState nor body nodes may be removed; research versions and progress of tasks already started are retained. The call counts toward the logical-call budget and is archived; this direct runtime path does not use the HTTP budget scope or the main provider-wide concurrency gate. Store saves the effective plan and audit cache in the same transaction, and resume does not repeat the call. Business-process ordering or shared materials do not mean generation tasks must finish sequentially; uncertain dependencies on actual deliverables are retained.

## Agent Roles and Handoff Contracts

The business execution implementation is in [agents.py](../src/folio/orchestration/agents.py). `BusinessWorkflow` preserves the Engine's existing entry points and provides shared services; `BusinessAgent` takes over autonomous file research, gap completion, and task execution; `ReviewAgent` takes over task review; and `BusinessCoordinator` takes over DAG scheduling. All model calls still use the existing runtime, request-coverage contract, and call budget. Role handoffs add no fixed requests; in V2, each research-tool decision and derived-result verification produces actual model requests controlled by the budget.

| Contract | Contents and checks |
| --- | --- |
| `BusinessAssignment` | WorkTask, confirmed outline and input hashes, existing node versions, dependency results, and remaining retrieval budget; verify that these still match the current plan and sources before taking over |
| `BusinessResult` | task_id, complete node versions, review_key, and currently effective issues; successor tasks may be released only when all nodes are present and review versions match |
| `RepairAssignment` | Business owner, expected node versions, original issues, and repair requirements; direct changes across ownership boundaries and use of stale repair assignments are prohibited |

Task packages, delivery receipts, and repair assignments are written to `contexts/agent_assignments`, `agent_results`, and `agent_repairs`, respectively. These are auditable inputs and outputs, not the model's internal reasoning. Body content, research, issues, and budgets remain managed by the same Store; pause and resume do not depend on in-memory Agent sessions.

## Execution and Model Interaction

```text
Writing requirements, material list, and structure excerpts → DocPlan
    ↓ work_plan (LLM)
WorkPlan → Programmatic validation of coverage, unique ownership, dependencies, and budgets
    ↓ Asynchronous ready queue (checks all tasks; at most 16 concurrent tasks by default)
V2 task research: research_step → File reading / Search / Isolated Python / Artifact verification → Next decision
    ↓ finish: Retain acquired evidence and unresolved questions → understand_work
Existing knowledge bases and the enabled search provider may be used as needed, subject to their source and quota boundaries
    ↓ Gaps remain after research → complete_gaps (LLM) generates suggestions in red
Per content node: generate → extract → validate (shared business record; source text read by action)
    ↓ review_work
Whole-task checks → Full-document review → drill_down → Bounded repair → Recheck
    ↓
Built-in Word layout → Business-group formatting-property optimization, at most 4 concurrent groups → Final pagination
    ↓
Template and formatting-protection checks → Delivery and execution report
```

New GUI and LLM CLI jobs use the autonomous research loop in `research/workflow.py`. Shared `SourceIndex` preprocessing converts originals into a file list, independent structural indexes, and body-text caches. Workspace builds on these to provide progressive reading of Word, Excel, PDF, PPTX, text, and images. Business tasks first inspect the list and structure, then read complete chapters and subsections by fragment or `node_id`. Tasks share the original parsing results, while OCR, notes, and computational artifacts remain task-owned. Sandbox allocates containers on demand; ArtifactManager distinguishes execution completion, artifact registration, and evidence verification. V2 local research has at most three rounds, with 12 tool steps per round by default. If three rounds are still insufficient, the coordinator schedules at most two web-search rounds; ordinary rework does not reset the round count. Original-image viewing, independent verification of visual interpretations, pagination of historical results/evidence, scope coverage, and OCR continuation all reuse the current task and fixed factual snapshot. For details on V2 tool steps, parsing caches, derived evidence, complete coverage manifests, and recovery, see [File Research and Execution Design](agent-research.md). Legacy jobs without `research` configured retain the `next_action/search/write/pending` path, but action selection and query requests also use native tool_calls rather than parsing textual action JSON. The three-round internal-retrieval description below applies to the legacy path and the quota for explicit V2 calls to existing knowledge bases; it does not limit V2 paginated reading of original files to three reads.

`BusinessRecord` stores summary, facts with evidence_ids, terminology, conflicts, and open_questions. Fact references must exist; semantic support is checked by independent review. Facts in the record are not business approval results and cannot replace original Evidence. After supplementary retrieval, the model reads the current evidence, understands it in batches when necessary, and consolidates all facts; summaries do not replace original evidence.

A task may call the writing model multiple times. Each call writes only one explicit document node and receives the task objective, questions, completion criteria, necessary node index, shared record, and complete evidence selected for the current node; it does not include the full body of other nodes in the same task. For both generation and repair, whether or not the entire material package fits in context, materials are first selected according to the current node's subject, path, and writing requirements. This prevents materials for another section in the same task from being used directly as the basis for the current section. Required project-source coverage and source text for selected facts are still mandatory. This preserves node-level repair and recovery while allowing sections to share business understanding.

Dependency readiness means the upstream body content and task review are both complete; it does not mean requirements have been confirmed. After upstream task review is complete, downstream tasks select sourced, supported statements and suggestions as needed. Full original review issues remain in the backend, while handoffs use currently effective issues. Only selected relevant risks and their sources are passed downstream. When multiple tasks are selected on the same page, each task's original risks are restored by task ownership; copying a mixed summary to every task is prohibited. Nodes with currently effective issues or stale task-review versions do not provide supported facts downstream. Downstream tasks must not promote items pending confirmation into business conclusions.

## Parallel State and Gap Completion

The scheduler maintains pending/running/completed states and uses `asyncio.wait(FIRST_COMPLETED)` to release capacity and dependencies. Ready tasks do not need to be selected individually by the LLM; by default, at most 16 business tasks run concurrently. Actual dependencies continue to wait for upstream body content and task review to finish. Tasks research first, then all nodes awaiting writing enter up to eight-way writing concurrency, followed by consolidated task review. Gap-completion records are merged under the task lock. During business-task execution, the main model allows at most 32 concurrent calls; later stages such as review allow 16, with a shared main-service limit of 32 across stages. Verified and enabled decision services share a separate limit of 16 concurrent calls per job. The combined main-model and decision-service limit is 48. Without a decision model, filtering also consumes main-model slots. Intent handling may fall back to the main model and still uses the main-model queue; next-action decisions always use native tool calls on the main LLM. Exceptions or cancellation cancel and gather all worker coroutines to prevent residual writes after the job lock is released. Resume skips committed nodes and completes unfinished task reviews.

Each task fixes `global_facts` when a new research version begins, reading only nodes whose corresponding task-review versions are complete and that have no currently effective blocking issues. The original evidence corresponding to the snapshot is included in task materials even if the fact provider is not an explicit dependency. Running requests do not automatically receive new facts from other tasks. Tasks/nodes are upserted by their respective IDs within SQLite transactions, and the entire job has a file lock. Global facts are a derived view of all current node records, not shared JSON modified through read-modify-write operations by multiple coroutines. Conflicts on the same business key retain all sources and node versions for a final consolidated check.

Shared facts and dependency handoffs use the same `IssueLedger` and derived-state entry point. False-positive dispositions in `adjudications.json` filter current issues by body and task-review versions while retaining original check records. `SectionState.claim_verdicts/validation_completed` stores per-fact support verdicts. Only facts with an existing positive verdict or a compatible legacy supported state, and valid references, may enter the shared view. Negative or incomplete verdicts, model suggestions, and missing sources are not promoted merely because an issue is excluded. `WorkState.review_revisions` prevents old task reviews from endorsing new body content.

When gaps remain in the compatibility research path, the internal retrieval budget is used first, with at most three rounds per task by default. Once the internal budget is exhausted, if the search service has been tested successfully and enabled, at most two web evidence searches (`advanced` for Tavily, the native search payload for DeepSeek) run. Each uses `web_query` to generate public-knowledge queries around the gaps, then reorganizes the record and reassesses after obtaining materials, stopping as soon as sufficient evidence is available. When search is disabled, the existing path of internal retrieval followed by gap completion is used directly. Internal `searches` and web `web_searches` are persisted per task and are not reset by restarts, repair instructions, dependency changes, or research-version changes.

The [web research workflow](../src/folio/orchestration/web_research.py) saves an attempt record before sending a request. Failures, interruptions, and skipped duplicate queries still consume one attempt, and resume does not automatically resend them. Web-search failure does not block delivery. The [search adapters](../src/folio/knowledge/search.py), using the shared [Tavily implementation](../src/folio/knowledge/tavily.py), save each source's URL, title, excerpt, retrieval time, and `public_web` role. Such sources cannot serve as evidence of internal project thresholds, personnel, or approval decisions; applying public practices to the project remains a model suggestion.

After all available budgets are exhausted, `complete_gaps` receives current gaps, necessary evidence, relevant dependency suggestions, and target nodes in batches, and outputs concrete suggestions with `section_ids`. The program verifies that each gap ID is covered exactly once and that nodes are valid, persists `proposals`, and passes them to the writing model for integration within the section's scope; the program no longer appends entire passages directly. Metadata that cannot be inferred, such as author, date, and version, as well as information-collection, retrieval, and document-writing guidance, is marked `disposition=record_only` and retained only in the backend.

If writing returns an empty body without identifying gaps, the same bounded supplementary-retrieval and gap-completion process begins immediately based on the section's confirmed requirements, rather than waiting for cross-chapter checks to discover the problem. Once the retrieval quota is exhausted, if writing repeatedly raises the same gap and its corresponding completion proposal already appears verbatim and in full in the section's red-text paragraphs, the match is recorded and duplicate integration is skipped. No semantic-equivalence inference is performed; the original gap is not removed from the work record, and the body is still verified independently. Item-by-item integration protects known complete paragraphs for other proposals and blocks just written for preceding items; later items cannot delete or rewrite them. Invalid changes retain the original text and leave a pending-confirmation record.

Material selection for gap completion prepares at most three items ahead, skipping backend-only records. Prefetching returns only selected materials and does not generate body patches in advance. When each item's turn arrives, the request is rebuilt using the latest body content, protected blocks, and existing references, capacity is measured, and integration proceeds serially. Material-selection failure for an individual item leaves it pending confirmation in the original order; exhaustion of the global call budget continues to propagate outward. On exit, all prefetch operations are awaited through cancellation cleanup.

Both new gaps produced by writing and early-returned `model_proposal` results are checked by the [engine](../src/folio/orchestration/engine.py) against the remaining budget. Even after three internal retrieval rounds are complete, if one web-search attempt remains, supplementary retrieval must happen before deciding whether to complete the gap. For the compatibility path, `model_completion_allowed` uses the original retrieval counters; for V2, it uses `fallback_ready`, saved after the coordinator completes the local/web stages. Supplementary retrieval is mutually exclusive per task and saves independent state to prevent concurrent repairs from overwriting counters. After renewed research, each section completes only the intersection of its current `requested_gaps` and the still-unresolved `work.missing`; supplementary retrieval for another section must not hand all remaining task gaps to the current node. Resolved gaps no longer generate suggestions, while historical supporting material and suggestions remain available for audit.

Completed business content is retained in the backend with `origin=model_proposal`. Word distinguishes it only through red text, without adding a “【Model Suggestion】” label or proposal explanation. Initial body formatting inherits the specified table headers, fonts, and font sizes; final formatting permits only constrained adjustments and preserves red text. No fabricated evidence references are supplied, and this content does not enter supported facts. Downstream tasks receive upstream task suggestions separately. Full-document review checks suggestions within adjacent windows, concrete facts, shared topics, and dependency-based node groups; it does not pair content merely because both sides contain model suggestions. Documents containing suggestions are output as complete drafts and are not automatically published as confirmed facts. Interface, model-call, formatting, or consistency-check failures are still explicitly reported.

## Review, Repair, and Consistency

Evidence references for fact organization, writing, fact extraction, and next-action decisions use output enumerations built from the actual `evidence` on every call. IDs for dependency facts, chapters, or other batches are not part of the current referenceable set. The transport layer converts enumerations and material IDs together into short references and restores them afterward; capacity measurement uses the same constraints. Invalid references are still rejected, without silently deleting facts or guessing replacement IDs. Correction feedback gives the specific fact location, invalid ID, and valid range. Complete failed JSON outputs are saved under the job's `contexts/rejected/` for comparison with the model's actual response. A valid ID means only that the source reference exists; whether the content is supported by evidence still requires subsequent extraction and validation.

Persisted `Finding.description` and `key` allow 3,500 and 300 characters. Model requests for `Review` / `LocalReview` still constrain description and key to 240 and 120 characters; each verdict's reason allows 1,000 characters. These requests ask for brief diagnoses rather than copied source material. The larger storage limits also support program-generated findings; they do not apply uniformly to all review requests. `Extraction` summaries and claim statements allow 3,500 characters, while a `BusinessRecord` request summary remains limited to 800 characters. When body review requires further splitting because of capacity or output truncation, a single table may be recursively split by complete rows. Each subrequest retains the corresponding evidence and original table-row range; issues are merged after all rows have been checked, without falsely reporting missing rows from other requests as omissions. For a small review unit whose input fits but cannot be split further, if output is still truncated, one concise retry with compact_review_retry is allowed. A second failure is explicitly reported; partial JSON is not accepted or treated as a review pass.

Arrays already constrained to be empty by the output Schema (maxItems=0) are not assigned to the model: the transport layer removes the fields, the backend restores top-level constants, and nested fields use the empty-array defaults defined by the model. For example, when body review has no per-fact verdicts, only findings is requested, and the program restores verdicts=[]. This avoids the current model continuously emitting whitespace inside a verdicts array that must be empty. Illegal nonempty values actually returned by the model are not overwritten; normal validation still applies. Failure logs record the trailing-whitespace count to distinguish whitespace loops from genuinely oversized content.

Similarly, material-index pages without kind=risk do not ask the model to fill risk references or summaries; the program restores risk_refs=[] and risk_summary="". The selector only selects materials available on the current page. When risk materials exist, it must still provide valid risk references and corresponding summaries rather than inventing risk conclusions.

Node validation remains responsible for content format, table headers, references, fact extraction, and local semantics. Required project-source coverage is matched per node; each subsection must not be required to repeat coverage of all materials for the entire task. When the business main table and an additional table have identical data rows, source types, and references, and their captions are identical or only one has a caption, duplicate tables are merged while retaining the nonempty caption and illustration references. Tables with different data, sources, or two different captions are not merged.

Explicit affirmative writing instructions requiring flowcharts or interface diagrams are enforced through local rules, output constraints, and missing-diagram checks. Illustrations are not added based on headings or ordinary mentions of “process/interface”; negation, conditions, examples, and “either/or” are not upgraded into two mandatory requirements. Actual child-section diagrams may satisfy parent-section requirements. For containers with no body-writing responsibility, if no subsection has yet taken responsibility, an item pending confirmation is recorded rather than repeatedly revising an empty container. Complete body and source validation remains in place; see [Document Illustration Tools](illustrations.md).

Whole-task review checks the division of responsibilities across subsections, process continuity, and rules with the same scope of applicability; per-item evidence support is handled by node validation. If a task does not fit in one call, at most 8 genuinely relevant cross-node checks are first identified from the task questions, completion criteria, and outline, then materials are selected by question and read in batches. All node pairs are not enumerated. Current body content, necessary sources, and source types remain protected by coverage validation; the system cannot claim to have reviewed original text that was not supplied.

Full-document review retains adjacent overlapping windows, prioritizes concrete facts organized by the same `scope / subject / predicate`, and adds groups based on shared topics and explicit business dependencies. Each group contains no more than `review_batch_size` sections (6 by default). When a broad subject appears in multiple sections, it is split into linked small groups rather than creating all node pairs. Relationships already covered by a window or topic group receive only an additional grouping reason; intersecting topic groups may be merged within capacity. For the same fact key, representatives of different verbatim values are gathered within the group-width limit. Beyond that limit, one detailed-review candidate containing all group records is formed rather than expanding every unequal-value pair, including candidate assertions that are unsupported or not declared single-valued. If the first representatives all belong to one task, representatives from other tasks are sought. Keys already covered by broad fact groups do not generate separate rule candidates. When the complete group cannot be fully checked, it is explicitly retained as pending confirmation. Different wording of values produces review candidates, not direct contradiction verdicts. The deterministic factual-conflict index remains in place; a shared topic, synonymous wording, different business conditions, or failure to repeat an explanation in another chapter cannot alone establish a conflict.

Cross-chapter requests carry complete fact-anchored body blocks and model proposals. Each candidate must locate at least two different chapters using real `block_refs`, and provide `comparison_scope` (shared applicable subjects, stages, and conditions) and `incompatibility` (what cannot hold simultaneously or cannot connect coherently). Single-section source and omission checks remain in node and task reviews. Complete source blocks exceeding capacity may be explicitly deferred to detailed review. Facts, proposal indexes, and backend source text are not deleted, and index differences alone cannot authorize repairs.

Review groups execute concurrently through a bounded work queue. `max_parallel_reviews` defaults to 16 (configurable from 1–16) and shares the per-job model-call concurrency limit. Internal content within the same task is already handled by whole-task review, so full-document model groups are not created solely for that task. Other checks within budget still run when there are items pending confirmation. Implicit relationships lacking extracted topics and falling outside adjacent windows or dependency scope may still be missed; enumeration of all potential relationships is not guaranteed.

Suspected issues are merged only when their type, location, reference set, and normalized description are all identical. Original records remain in `contexts/review_deduplication/`; suspected issues with the same short issue key but different descriptions remain separate. “Missing citation” rules in local and task reviews must locate fact blocks supplied in the current request. The output protocol and programmatic validation reject missing-citation allegations targeting only red-text gap completions; actual factual conflicts, fabrication, and omissions may still be reported. Deduplicated effective issues enter independent detailed review, which checks the source text to identify false positives. Red text cannot exempt content from structural and source hard checks or elevate a design into confirmed facts.

Issues use v2 content identity from creation. Deduplication, the effective-issue view, and versioned exemptions use the same fingerprint, rather than temporarily changing keys only when an issue appears in a particular list. Identity includes description, rule, basis category, location, and comparison scope; when no location exists, the original issue key is retained. Different issues remain separate after batching, reordering, or restart. Legacy exemption identities lack complete descriptions; they remain for audit but require renewed detailed review and are not automatically migrated.

When detailed review confirms multiple issues, the program selects a mutually noninterfering batch based on business-task ownership and dependency read/write scope, then revises them in parallel against the same saved body content. Revisions involving the same task, referencing another task awaiting repair, or having transitive dependencies are deferred to the next round to avoid stale judgments. After all worker coroutines finish, Store compares expected read versions, commits the entire batch of nodes, and invalidates related reviews in one SQLite transaction, followed by rechecking. Failures in either the candidate stage or the transaction save no partial body content; cancellation collects in-flight coroutines. Repair-assignment ownership is validated against the original business owner, and budgets are calculated by nodes actually modified. If structural repairs still fail explicit acceptance criteria, the batch retains the original body and records items pending confirmation. Task reviews also run in parallel by dependency wave; successor reviews do not start until actual prerequisite tasks have completed review.

Revisions and initial writing share source validation: a chapter consisting entirely of unsupported proposals cannot become uncited facts during revision, and existing valid references cannot be cleared. Existing incorrect facts are not automatically colored red to bypass verification. If a figure-title area repeatedly copies at least two complete source passages from the same source, duplicate-block locations are returned for correction within the existing retry limit. Identical text under different business headings, text from different sources, and tables and lists are not automatically merged.

When detailed review requires a user decision, cannot reach a verdict, or still fails to provide an executable repair decision after bounded retries, the issues are retained and a draft pending confirmation is delivered. Users may submit answers against the current issue version and a call budget for the round, then continue after the previous delivery is archived. Business answers become project evidence limited to designated sections; the original owner directly revises the affected sections, followed by renewed review and export. The outline remains unchanged, and unanswered issues do not disappear automatically. This round's repair budget uses the section versions at submission as its baseline; retrieval counts and cumulative model calls are not reset. Technical retries may omit answers. For interface, idempotency, and budget boundaries, see [Pending-Confirmation Answers and Resume Design](confirmation-and-resume.md).

Local repairs receive the same task's business record, relevant dependencies, and necessary source text for the current node. After affected nodes are written back, the entire task is checked again. Writing body content clears review-validity markers for that task and tasks depending on it. When dependency facts change, downstream task reviews read the new dependencies and recheck existing body content. Research records are refreshed only by subsequent explicit repairs or a new research version; retrieval quotas are not reset, and old body content is not automatically treated as adapted. A global-review snapshot must match current nodes and business records before publication.

## Persistence and Observability

- SQLite `work_plans`: the fixed execution plan for each job.
- SQLite `work_states`: research-context hash, business record, evidence, internal query history, web attempts and status, gaps, research status, review_key, and corresponding review_revisions.
- Model calls and retrieval continue to use existing caches. Successful cache entries for identical requests are validated and reused before accessing the capacity service on a miss. Cache invalidation or process exit before a remote response is persisted may still cause another request; exactly-once external execution is not guaranteed.
- `GET /jobs/{id}` includes work_plan; `GET /jobs/{id}/work` returns the plan and task states.
- GUI SSE displays actual grouping, retrieval, record organization, and whole-task checks, not internal chains of thought.
- On completion, `work-plan.json`, `work-records.json`, and `formatting.json` are exported to the job directory; existing trace and Word files are retained.

User pause requests notify the current executor through persisted `pausing` state; both Web and standalone Worker monitor this state. The executor cancels and waits for all concurrent requests, illustration work, and local file writes to exit, then closes model clients before confirming `paused`, retaining the job lock throughout. State is checked atomically again before startup to prevent queued jobs from starting incorrectly after a pause. Resume requeues the same job and preserves its execution stage; when body content is complete and review or export has begun, business research is not restarted. Successful calls and saved sections continue to be reused; interrupted calls must be requested again. Actual call counts, existing failure-retry records, and retrieval rounds are not reset. Interruptions of unfinished calls do not consume failure-retry slots, but total-call budget already charged is not refunded. `run_timeout_seconds` still limits each execution window; resuming a job starts a new window.

Upgrades do not automatically modify completed legacy documents. Pending-confirmation jobs that satisfy the checkpoint contract may still begin a new round through explicit user answers or retries, archiving the original delivery first. When unfinished jobs from the old in-house engine resume without a WorkPlan, an execution plan is created, existing nodes and evidence are reused, and the new whole-task review runs; old final-review conclusions are not reused. Jobs from retired frameworks follow the original migration rules.

## First-Version Boundaries

WorkPlan task assignments are determined before execution. Dependency audits change only blocking edges of tasks that have not started; they do not dynamically split, merge, or replan tasks during execution. Collaboration among multiple research subtasks for a single node is also not implemented. Word outlines are now planned in one pass by the LLM based on writing requirements and materials, with structural and optional template validation plus source-requirement coverage review; see [LLM Outline Planning Design](outline-planning.md).

By default, each task has at most 8 content nodes (`max_work_sections`), and business concurrency is capped at 16 tasks (`max_parallel_tasks`), with no truncation window for ready candidates. Each task has at most 3 cumulative internal retrieval rounds, plus at most 2 web evidence searches when search is enabled. The default character budget for one material read/retrieval is 600,000, and results from multiple rounds are retained cumulatively. All LLM requests default to 600,000 input Tokens and 128,000 output Tokens. When the service cannot count tokens, an explicitly labeled local Token estimate is used; known smaller service windows must still be respected. Only compatibility Runtimes lacking Token metering and independent decision services use the 600,000-character fallback. Main-LLM material selection is no longer restricted to 32,000 characters and 24 candidates; all independent decision models handle at most 24 items per page, with oversized items split losslessly. These are resource budgets, not rules based on heading levels or business types.

When the model-call budget is exhausted or a supported service/timeout interruption occurs, new model calls stop and a `needs_confirmation` draft is exported only if body content and container states for every outline node have been saved. Incomplete checks are explicitly recorded, original suspected issues, valid illustrations, and pending illustration positions are retained, and `review_passed=false`. If body content is incomplete, the job still fails and retains its checkpoint. A technically interrupted draft does not count as passing complete-generation acceptance. Pause/cancel, storage errors, programming errors, and export failures are not masked by this path. Pending-confirmation jobs do not resume automatically; they are requeued only after the user explicitly submits answers or a retry with a new-round budget.

Task plans and records are currently available through APIs and files. The GUI retains a concise conversation and process display without introducing a task board or editing page. Fonts, tables, and the table of contents are rendered consistently using the built-in layout.

## Complete Node-to-Task Assignment

The internal work-plan model remains WorkPlan / WorkTask. In actual LLM transport, each task returns `node_refs` using reversible short references such as n1 and n2. JSON Schema directly constrains the number of nodes in each group and restricts valid IDs; the program checks unique node ownership, complete coverage, and acyclic dependencies. If the model omits nodes, generated groups are retained and only remaining nodes are sent to the next call. New tasks cannot reuse existing task IDs but may declare dependencies on existing tasks. Generation starts only after the final complete plan passes validation. This repair remains subject to the three-call planning limit and does not group on the model's behalf by fixed outline levels or node order. Any node listed as a content node must be assigned, even if it has children; only nodes explicitly marked container are excluded from the list.

runtime/work_plan_transport.py only restores internal section_ids according to ownership selected by the model; it does not group nodes, add tasks, or select owners. Duplicate task IDs, missing assignments, and assignments to nonexistent tasks still raise errors. Internal validation continues to enforce unique writing ownership, acyclic dependencies, and per-task node limits. Failure feedback includes the returned invalid plan for correction. While the work plan is incomplete, the interface explicitly identifies this stage rather than generically prompting a knowledge-base check.

Work planning uses a separate `work_plan_attempts` budget (at most 3 model calls by default); other regular calls still follow `call_attempts`. Internal retrieval and optional web evidence searches follow the task budgets described above. Over-limit feedback includes the specific task, node count, and all node references; correction requests include the previous candidate plan. Inputs also provide the total node count and minimum task count, requiring the model to retain valid groups and split oversized business subproblems. Exhausting the budget causes an explicit failure, not unlimited retries or programmatically fabricated tasks.

## Context Scope and Model Capacity for Body Validation

`extract` receives only the current node, complete body content, original evidence, and current feedback; it no longer includes the entire task-node group or other chapters' body content. `validate` retains the current body, evidence, shared business record, proposals, and dependency conclusions; cross-chapter source-text consistency is handled by `review_work` and global review. This avoids repeatedly passing the entire group's body content during per-node fact extraction and prevents facts from other chapters from being incorrectly extracted as conclusions for the current section.

`runtime/extraction_transport.py` converts extraction response fields into short names, restores the original business structure on receipt, and sets all extracted facts to `candidate`. Fact text, qualifications, entities, and references remain unchanged; `supported` is still determined by independent verification. The database and historical caches continue to use full field names. This is transport compression, not reduced extraction or merged validation steps.

After body content has been returned in full, if `extract` or `validate` still fails to finish within the original attempt budget because of continuous whitespace, output truncation, protocol errors, repeated output, or timeouts, the body is retained and other sections continue, while an item pending confirmation records “fact extraction/body validation incomplete.” Failed extraction does not accept partial JSON; facts whose validation is incomplete remain `candidate`, deterministic checks still run, and the result cannot be marked as passed. Configuration, authentication, quota, capacity, and programming errors do not use this handling. The interface explicitly shows the affected section, failure reason, and outcome rather than hiding failure by increasing retries.

When the runtime receives an explicit server-side context-capacity error, it reads numeric diagnostics from the response and lowers the output reservation without changing the input or Schema. Each adjustment retains at most 75% of the previous reservation and leaves window headroom; capacity adjustment allows at most 3 rounds (native-tool compatibility retries add separate HTTP attempts). Adjustments apply only to capacity rejections before body output begins. Oversized input itself, insufficient numeric diagnostics, ordinary 400 errors, and authentication failures do not use this strategy. Truncated responses still count as failures, and partial JSON cannot be accepted. Successful-call usage records `context_rejections` and `effective_max_tokens`. If transport-layer adjustments still fail, the engine does not add formatting feedback and retry the same request. Before sending, the server-side tokenizer is preferred for measuring actual input and reserving the configured output allowance; when the service does not support counting, a labeled local Token estimate is used. Batchable actions adjust request boundaries after capacity/output-truncation errors, and successful subrequests are reused independently.

When automatic suggestions in shared body content are exactly identical to `model_proposals`, `proposal_ref` points to the complete content for the same `gap_id`, avoiding repeated transmission of the same large suggestion across multiple written chapters. Replacement occurs only when body text, including suggestion labels, matches exactly. Manually edited or model-rewritten paragraphs retain their original text; factual paragraphs and references remain unchanged. Default fields omitted from the body model are explicitly explained in the prompt. This compact format is used for whole-task review; persisted body content and the final Word document remain unchanged.

## Action Selection and Retrieval Limits

Each `next_action` request exposes only currently allowed native functions (`search`, `write`, or `pending`). The main LLM selects a function through `tool_calls`; the program validates the call and remaining budgets. Once internal retrieval is exhausted, `search` is removed. The coordinator handles remaining web-search attempts and gap completion. Invalid calls receive bounded feedback; they are not silently converted into writing.

The optional decision service handles intent and material relevance only. It does not decide `next_action`, generate tool arguments, or control research quotas. See [LLM interaction flow](model-interactions.md).

## Final Formatting and Delivery

After body review is complete, a DOCX is first generated using the built-in layout, then `format_document` is called for existing WorkPlan business groups without replanning or rewriting body content. The [formatting workflow](../src/folio/orchestration/formatting.py) allows at most 3 calls and 25 seconds per group, and at most 120 seconds for the entire stage; each call is attempted only once. The model submits only allowlisted formatting patches. Font size may change by at most 1 point relative to the original initial-layout baseline; text, order, cover, headings, fonts, and suggestion red are protected programmatically. Failures or timeouts do not block delivery. Only adjustments that pass protection checks enter final pagination; if adjustments cause pagination failure, the built-in layout is restored. This stage reads formatting properties of paragraphs, tables, and other elements; it does not imply an assessment of actual page aesthetics.

The business Agent uses `VisualRequest` in body content to determine the meaning, source blocks, and insertion position of prototype diagrams or flowcharts. Shared `VisualAgent` reuses the existing generation/rendering/validation workflow. Diagrams whose sources have no substantive issues may be produced in the background after local verification, in parallel with remaining writing. Final export merges valid results according to current body identity.

The final Jev per-page scoring, automatic low-score correction, and rescoring workflow has been removed. Normal generation no longer uses page scores as a delivery condition. Image-input capabilities remain available for research and style analysis. Historical scoring reports and verifiable patches remain readable; historical incomplete reviews are not relabeled as passed. The independent DocPolish project is not yet integrated with Folio and does not run automatically at delivery.

`formatting.json` stores the baseline, patches, and unfinished scope; `layout.json` stores the result summary. `reformat` can replay matching safe patches without calling the model again. For detailed boundaries, see [Materials and Word Layout Design](source-materials-and-layout.md).

## Lossless Transport Format for Body Tasks

`runtime/business_transport.py` handles writing, extraction, validation, retrieval decisions, and review requests uniformly without changing business structures in the database or Word content:

- Long node, evidence, fact, and body-block references are converted to short `sfrefN` IDs valid for the current call. Only explicit reference fields are converted; ordinary source text and table cells are not replaced. References in model responses are restored to original IDs before validation.
- Multi-row object arrays with identical fields use `$columns` to declare field names once and `$rows` to retain all values in their original order. Objects with different fields are not combined; null values, line breaks, table structure, and all source text are retained. This is transport encoding, not material summarization or task splitting.
- Model-readable messages carry a compact, complete transport Schema. Structured-output mode also applies `response_format` constraints; ordinary prompt mode relies on the same contract in the messages.
- `LLMRuntime.request_parts()` is used both to send requests and by `prompt_chars()`. Local call budgets, business-task review batching, and global-review batching all use actual transport messages for calculation, avoiding rejection based on verbose original JSON when the compact request could actually be sent.

Capacity is currently managed jointly through action-specific material selection, compact transport, server-side Token counting or explicitly labeled local estimation, and request batching, with defaults of 600,000 input Tokens and 128,000 output Tokens. The compatibility Runtime's 600,000-character fallback is not intersected with the actual Token budget. Compression effectiveness depends on input structure; the compression ratio of a particular real request is not a fixed guarantee. Compact representations cannot remove physical model-capacity limits; when limits are still exceeded, source text is not truncated and incomplete model results are not accepted.

## Repeated and Truncated Writing Output

Streaming responses from `generate/repair` are read block by complete body block through `RepeatedParagraphGuard`. The stream is aborted and the connection closed if a long paragraph whose fields other than `block_id` are identical appears 3 consecutive times, or if a body sequence with a shortest period of 2–8 paragraphs repeats for 3 consecutive cycles. The latter requires at least 60 non-whitespace characters per cycle; the threshold for a single long paragraph is 80. Differences in sources, references, body content, and scope are preserved. Headings, tables, and explicit scope changes reset the sequence; short labels cannot accumulate repetition counts to meet the threshold. Complete responses and caches are also checked. Detection only rejects abnormal output and uses the original retry budget; it does not delete body content or splice partial JSON into a purportedly complete result.

Repetition and output truncation each produce explicit retry feedback to the model, requiring it not to repeat rules, rewrite other nodes or existing model suggestions, and to end the JSON after completing the current node. `call_attempts` still applies; output allowances are not increased, and continuation is not unlimited. At the retry limit, existing checkpoints are retained and the failure type is reported accurately. Repeated output must be distinguished from normal long body content; diagnostics must retain the error type rather than attributing every case to oversized input materials.

## Decoupling Request Working Sets from Business Tasks

For the complete implementation, action-input contracts, batch coverage, recovery, and audit paths, see [Request Context and Capacity Design](context-and-capacity.md). Complete upstream review reports are no longer passed directly into ordinary downstream requests, and business-task boundaries no longer serve as request-capacity safeguards.

## Concurrent Review and Group Progress

Cross-task review first fixes the node versions and grouping for the current round, then up to `max_parallel_reviews` coroutines take groups from the queue, taking the next group after each completion. Results are gathered in original group order and deduplicated by type, location, references, and normalized description. Different issues with the same short key retain independent identities, and deterministic fact-key conflict checks remain in place. This is configured separately from business-writing concurrency, `max_parallel_tasks`.

If a group fails or external cancellation occurs, the remaining review coroutines are cancelled and awaited before the job lock is released. Successful requests can still be recovered from the persistent cache. Within the same engine, identical requests use a lock to enter the cache/call process serially, avoiding duplicate calls, competition for retry attempts, or overwritten results when multiple parent groups split into identical subrequests.

The interface displays “N groups total, up to K processed concurrently” and “X/N groups completed.” The group count refers to the top-level review groups for the current round. Further splitting within a group because of capacity does not change this total; a group counts as complete only when all subrequests finish. Review plans and per-group results are saved in `contexts/review_plans` and `contexts/review_results`, respectively; successful subrequests continue to use the SQLite `tasks` cache.

### Objective Fields Pending Entry and Supplementary Business Research

Body content may use `record_only_pending` to mark missing names, contact details, document dates, versions, or identifiers in existing blank table cells. Each item binds to a real table block, final table row and column, and verbatim column name. The header row is numbered 0, and the first data row is 1. The same blank cell may lack both a name and contact details; duplicates are determined by position and `kind`, retaining each item's description. This generates only backend items pending entry, does not enter supplementary business research, and does not fabricate values. Body validation and task review still check whether business rules have been incorrectly classified as metadata. Pagination retains original row numbers and headers, and the business main table restores synchronized references. Legacy `pending_items` are not reclassified by keywords; business-information gaps still follow the original workflow. Items pending entry are not treated as a review pass.

In detailed review, `confirmed` means “the candidate issue is valid,” not “the body content is correct.” A reason stating “no contradiction, no change needed” should return false. When an error is confirmed and no user decision is required, valid target nodes and concrete repair instructions must also be provided. Responses with contradictory fields are retried or retained as incomplete conclusions; the program does not guess and rewrite the verdict.
