# 请求上下文与容量设计

> English version: [English version](context-and-capacity.md)

模型侧系统提示词、工具说明和任务指令统一使用英文；提示词语言不决定输出语言。`runtime/language.py` 提供共用规则：文档标题、正文、表格和配图文字默认使用用户输入的语言，显式指定的输出语言优先。多阶段任务保留原始用户要求作为语言依据，不能改为跟随英文系统指令、资料、示例或内部笔记。中英混合输入以最新明确语言偏好为准，否则沿用用户主要指令的语言。`ui_language` 单独指定界面过程语言，控制任务标题、步骤说明、状态和临时占位，不改变已确认的正文语言。原始用户文本和资料不预先翻译；协议键、枚举、工具名、编号、代码、逐字引文和模板必须保留的标签维持原样。

## 风格示例的有界分析

`style_analysis` 使用可读 Markdown 输入，只有这个专门步骤可以读取示例原文；业务上下文仅接收脱离示例业务事实的风格规则。全部可提取文字按原文顺序切分、按完整请求的 Token 容量装箱，不以固定样本数代表全文。默认输入 600,000 Token；兼容 Runtime 缺少 Token 计量时，`StyleAnalysisConfig.max_prompt_chars` 使用 600,000 字符的回退值。`max_total_chars` 默认留空，不再因累计分析超过 2,000,000 字符而提前停止；显式配置数值时仍执行该资源额度。整场分析仍最多 128 次请求、最多 10,000 个连续文本片段、每片段最多 1,200 字符、单次 90 秒；连续分段不代表丢弃其余原文，调用和时间政策也不等同于单次输入窗口。主作业与目录总预算仍可提前限制分析，JobInput 的 `style_analysis` 可收窄配置。图像输入单独受每请求最多两页及模型窗口预留约束，不把图像预留 Token 冒称文本字符。风格规则进入写作及排版上下文时不再截成 10K/16K 字符，完整请求统一接受容量计量。

程序安排所有可提取文本的有限批次；模型返回空补读列表不能提前终止。每批原文留在专门分析审计中，归纳结果跨批保留，最后检查逐维结论；缺失的文字维度允许一次定向复核。多批文字另进行一次完整观察综合核对，校验所有观察编号已审阅，合并重复并限定不同章节写法的适用范围；原始分批观察仍保留。最终综合请求同时携带已测得的原生版式、全文结构与篇幅统计，不能只凭规则摘要判断原文缺项。完整观察放不下或综合校验失败时保持未完成，不截断后冒称已综合。`style.md` 保存结论、依据位置、文本覆盖、逐维完成情况和程序测量。只允许将确实需要页面图像的部分列为视觉缺项；容量不足、解析失败或模型未完成时保留部分结果及未读范围，不宣称已完成。

DOCX 风格读取包含目录、封面、页眉页脚、文本框、脚注和尾注；这些区域的原生格式单独观测，不污染正文默认参数，原文不进入业务事实。数字 PDF 通过原生字体、颜色配置和绘制信息测量；颜色使用文件实际嵌入的 ICC 配置转换，不猜测任意色彩空间。原文件未保存的 Word 原始编辑设置与需要页面图像的视觉属性分别说明，不用图片去猜原始编辑参数。原生页面解析失败必须标为未完成。

分析缓存绑定完整源文件哈希、提取版本、修订视图和预算；语义未完成的缓存不能冒充成功分析复用。目录确认后将采用的风格与源哈希冻结到任务，恢复时使用已确认结果并核对哈希，不重新收费分析同一已确认风格。排版数值由程序校验，模型输出的文风描述不能直接修改 Word 数值参数。

聊天中的 `analyze_style` 使用同一分析器与缓存，独立于目录规划。意图判断根据附件清单选择已有 `style_reference` 的 ID；程序校验用途与真实 ID，文件名、历史讨论与否定关系由模型结合上下文判断。原件和审计保存在 `conversation-styles/<revision>/`，成功形成的风格结果按会话绑定。分析请求数量由全文分批及完成检查决定；入口意图判断及分析后的普通流式答复分别计费，不包含在风格分析调用数中。后续答复的 `workflow.style_analysis` 最多 6,000 字符，按维度预留空间，保留文件名/ID、文字覆盖、十维规则、可靠测量与未确认项；过长时明确提示完整内容见 `style.md`，不发送范文原文、定位索引或完整审计。缺失、变更用途、哈希不同或会话不匹配的结果不进入本次上下文；有效的仅测量结果可用于回答确定的格式参数，但不冒称已完成语义分析。

风格摘要保留规则的适用范围，并提供已提取的正文、标题和表格字体字号、间距等参数。正文、目录、排版的阶段风格视图默认不另设字符截断，按完整请求容量检查；聊天摘要单独限长，完整分析文件保留。独立分析和当前目录的有效风格按附件 ID 合并，独立结果只覆盖同一份示例。依赖风格的助手回复绑定来源版本；后续意图及聊天历史同步过滤过期或不在本次选择范围内的旧结论，避免通过历史正文绕过版本检查。

核心原则：后台保存完整材料和工作记录；每次模型请求只读取完成当前动作需要的信息。业务任务与模型请求是两种不同的边界。

## 三层结构

1. **后台工作状态**：WorkPlan、WorkState、原始 Evidence、生成正文、事实、模型建议、完整检查报告。业务依赖、既有检索计数、V2 研究账本、执行记录、产物及节点版本均在这一层维护。
2. **动作工作视图**：`orchestration/context.py` 和 `requests.py` 按动作组装上下文。`select_context` 由当前启用且通过验证的判断模型判断相关性；未启用时使用 LLM。程序校验引用和来源类型，再读取所选原文。
3. **实际请求**：`RequestWorkflow.call_bounded()` 根据输入容量和输出工作量安排一次或多次调用，单批独立缓存、校验，最终汇集结果。

Agent 的交接与请求分批相互独立：`BusinessAssignment` 冻结任务、输入/目录版本和依赖结果；`BusinessResult` 记录已保存节点及对应审阅版本；`RepairAssignment` 限定原负责人和预期版本。角色交接由程序校验并归档，不增加模型请求，不把各 Agent 的自由聊天作为共享状态。

共享事实与依赖材料均从统一有效视图读取：排除记录仅适用于同一问题和被审阅版本，逐事实正向判定、引用及任务审阅通过版本共同决定事实可用性。原问题保留审计。每个任务在研究版本开始时固定全局事实快照，同时携带其引用的原始 Evidence；非显式依赖的共享事实也不能只有编号没有原文。本轮保留该快照策略，不新增事实订阅或实时广播；显式依赖按既有版本失效和复查处理，非依赖任务的潜在矛盾由最终全局审阅发现后局部修订，不自动级联重写所有使用者。

需求上下文来自 `RequirementSnapshot` 的正式要求及明确修订。已有意图分类同时标注 `active/discussion/clarification/pending`，咨询不进入写作要求，分类失败不静默丢弃；原始对话和分类原因保留后台。待确认补答以限定章节的用户依据追加新版本，目录与既有来源保持原契约。

一个“交易审批”任务可以对应多批证据阅读、多次缺口补全、多个节点写作和多批审阅。分批不会改变节点归属、依赖图或增加检索轮次。

## 各动作读取什么

| 动作 | 本次读取 | 后台保留但不自动随请求传送 |
| --- | --- | --- |
| 选择依赖资料 | 当前业务目标、候选事实/建议/风险原文的一页 | 其他页，其他任务的资料 |
| 理解证据 | 任务目标、节点要求、当前批完整证据、相关依赖结论 | 重复的旧业务记录、原始导入调试元数据 |
| 目录前资料研究 | 用户要求、文件短编号清单、本次完整工具历史、结构 Markdown、已读原文、全量研究笔记、未解问题及读取进度；完整请求超限后才缩减历史视图 | 精确 JSON 索引、长路径与哈希、未选正文、完整审计账本；超限退出视图的旧内容仍可取回 |
| V2 自主研究决策 | 当前任务与固定事实快照、原生工具定义、本次完整工具历史、已读原文、全量研究笔记和证据索引；完整请求超限后才缩减历史视图 | 完整工具账本、脚本／产物及超限退出请求的旧内容；持久记录始终保留 |
| 派生证据核验 | 实际脚本、执行与环境摘要、全部相关原文和结果 | 未提供原文不能假定已核验；超出核验容量时保持未核实 |
| 决定下一步、生成查询 | 业务记录、缺口、查询历史、证据 ID 索引 | 已读过的整段证据原文 |
| 补全缺口 | 当前待补缺口、相关原始证据、事实、已有方案和依赖约束；超限时才分批 | 整个任务累计的无关证据及事实；按本批缺口选资料，不能只拆缺口数量 |
| 单项缺口的材料阅读 | 每页最多 8 项完整来源，提取当前缺口必须遵守的简洁约束 | 其他页原文；约束保留来源引用和来源类型，未确认风险和模型方案不能提升为事实 |
| 补充内容整合 | 当前一项补写、当前节点正文、按该项选中的事实/约束与必要原文 | 其他补写方案、相邻章节正文和全任务累计资料；使用局部编辑保留未触及的块 |
| 写作、修复 | 当前节点、共享业务记录、选中的原始证据、适用建议和依赖 | 同任务其他节点整份正文、无关检索切片 |
| 抽取事实 | 当前正文及引用的证据，输出最多十二条关键一致性索引 | 同任务正文、依赖审阅报告；不逐句复制成多套字段 |
| 局部校验 | 当前正文、相关来源及事实；必要时分成事实判定、正文检查、来源覆盖 | 不属于当前校验动作的检查工作 |
| 业务任务审阅 | 节点正文、完成条件、业务记录和依赖；核对分工覆盖、流程衔接和同范围规则 | 节点已经独立校验过的累计证据；不重复逐条证据审计 |
| 问题精查 | 当前问题、受影响节点原文、按该问题选择的原始依据及相关约束 | 全任务同级正文、整份业务工作快照 |
| 跨任务审阅 | 当前节点组摘要、事实、事实锚定的完整正文块及模型建议 | 整本文档正文；块过大时明确延后精查，保留完整索引及归档原文 |
| 原始资料视觉核验 | 一页完整原图与拟提取文本；OCR 批量核验最多两页 | 独立核验通过的视觉证据带签名；局部描述可信不等于整页覆盖 |

研究按“先查看结构、选择需要的范围、读取完整所选章节”渐进执行。目录和业务 Agent 的 `fs_read` 默认返回该章节及子章节的全部正文；多个独立章节可在同一批原生工具调用中并行读取。内部段落、标题、表格行仍用于定位，但不再固定切成 2,000 字符，也不再默认每次返回 20 条或最多 100 条。新增原文与已有历史、笔记、工具定义共同接受完整请求容量检查，并为输出保留空间；多个工具共用剩余容量，不能各自独占一个输入窗口。全部结果放得下时完整返回，放不下时才对新增结果分页，返回精确续读游标与剩余范围。单个长段落也能从上次字符位置继续，不能把局部段落标成已读完整。显式分页参数仍兼容旧调用。

正常研究保留完整工具历史和全量笔记，不能为了预先给新结果腾空间就删除旧历史。生产 Runtime 默认输入预算为 600,000 Token，旧配置缺失或为 null 也使用此默认值；已知模型窗口更小时，还须满足实际窗口。兼容 Runtime 缺少 Token 计量时，按完整请求字符预算回退；600,000 字符不再是来源正文读取的另一层固定截断。研究通过 `Engine.call` 或目录 Runtime 复用容量检查，工具次数、执行时间及输出另设边界。业务本地最多三轮，每轮默认12个工具步骤；之后最多两轮联网补查，再不足转模型补全。目录前研究优先读取上传资料；启用并验证搜索服务后，可搜索影响目录安排的公开问题，不能补造私人资料。文件分页是轮内操作，不把一个工具调用当作一轮。完整机制见[文件研究与执行设计](agent-research.zh-CN.md)。

目录研究的 `PlanningResearchLimits.max_evidence_chars` 默认留空，不再把跨文件、跨轮累计读取的字符数作为强制结束研究的条件；只有用户显式设置该额度时才限制累计量。整场研究累计量与每次模型请求的输入容量分别管理，不能相互替代。

研究消息由 `research/transport.py` 统一组装：要求和清单用文本／Markdown，同次回复的全部调用保留在一条 `assistant.tool_calls` 中，对应原文或错误逐个用带 `tool_call_id` 的 `role=tool` 消息回传。目录与业务研究每批最多16个调用，独立只读工具最多4个并发，结果按原调用顺序保存；涉及共享状态的动作按序分隔并发组。一次模型回复计一次模型调用，各工具分别计入工具额度。动作不再放在回复文本中，也不再在系统消息重复一份动作 Schema。原生 `tools` 函数定义包含参数约束，目录结束通过单独的 `finish` 函数提交并由后台校验；内部 `ResearchStep` 只用于单个执行记录。

模型读取资料使用文件、节点或页码，笔记及目录要求使用 `E1` 等证据编号。`finish.requirements` 引用真实已发送的证据后，程序推导 `selected_ranges`，不再要求模型填写内部范围编号；来源版本、位置和实际交付继续核验。允许引用已读页段，不强制读完其所在的整个查询范围，`complete=false` 和未读摘要仍保留。`fs.inspect` 保留为导航工具，已定位并读取正文时不以缺少结构浏览记录单独阻塞结论。

工具流失败记录具体 `protocol_issue`、HTTP 状态、结束标记、是否已收到 `[DONE]`、已接收工具数量与字符数、失败片段的事件序号，以及参数 JSON 错误位置。多个工具调用本身不再视为协议错误；接收器分别检查索引、ID、函数名和参数。`finish_reason=missing` 表示截至停止接收时尚未收到结束标记，不推断上游后续是否还会发送。目录研究将安全诊断写入 `research/events/research_NNN-error.json`，失败输出单独保存到 `research/failed_outputs/research_NNN.json`，并关联同编号的原请求；业务研究沿用 `contexts/failed_outputs`。私有输出包含已拼接工具调用和最近四组工具片段；仅提取工具字段，长片段保留首尾，归档总量最多32,000字符并标记截断。不保存请求头、原始错误正文或模型思考内容。页面和普通日志只使用固定原因枚举及安全指标，不展示工具原文。这些诊断不增加失败重试次数。

预算依据最终实际发送的所有消息、历史工具调用参数、全量研究笔记及原生 tools 定义计算；内容生成任务另计独立输出 Schema，读取正文字符数只是分页起点，不代表完整请求大小。原来先按缩进 JSON 判断是否可装入、再按实际紧凑请求计数的两套门槛已统一为同一个传输视图。正常结构一次提供，正文或极大结构根据剩余预算分页；清单、结构和已归纳结果不会仅因发送过就自动移出历史，最新工具结果也不能被整体静默移除。完整请求确实超限后才压缩视图，优先让已留下带出处归纳的旧原文退出；缺少归纳时由同一个研究模型先整理已提供资料。必要时再缩减笔记和可导航的任务字段、明确分段最新结果，保留精确续读位置；最小必要上下文仍无法容纳时明确保留未完成状态。原始历史与完整笔记始终持久保存。

多调用批次的容量检查包含该批所有参数与结果。部分旧原文退出当前视图时，其调用 ID 仍得到明确的归档占位结果，不能留下未配对的调用；占位不包含原文，也不增加已提供证据。目录的并发正文读取共用预留的剩余证据额度；并发数不改变输入上下文或证据总上限。

读取记录区分“程序已提取”和“已随模型请求提供”。完整执行结果、实际发送视图及交付记录分别保存；目录校验不接受仅在后台存在、尚未发送的证据，也不把已发送的局部原文算作整个范围读完。业务 `model_deliveries` 记录观察的请求编号、文本哈希、已提供字符数和完整性，历史续读按可读文本位置取回，避免再读一层套一层的结果 JSON。记录发送不能证明模型理解，但可以核对它获得了哪些资料。

目录与业务的 `ResearchMemory` 将交付记录、增量研究笔记和原文证据分开保存。模型通过原生工具参数 `research_notes` 提交带 `evidence_ids` 的条目，不再要求 `request_ids`；程序核对证据确实已发送，并从账本恢复批次关联。只将所引用证据记为已归纳，不连带覆盖同批其余原文；模型推断和无关说明与资料陈述明确区分。没有更新保持旧笔记，指定条目才修订，重复调用幂等。目录笔记随该版本的研究报告保存，业务笔记按会话检查点恢复；目录重新规划建立新的研究，不凭旧报告直接继承完成状态。`research.md` 仅从权威状态导出，不是另一份事实库。后台完整审计、原生 `tool_call_id` 配对及历史请求编号继续保留，简化模型填写字段不改变时间和调用预算。

笔记不能和普通旧聊天记录一起按时间淘汰。正常请求携带全量笔记，只有完整请求超出本次容量后才保留主题索引及当前相关条目，并提供分页读取入口；当前未展示不等于笔记被删除，未解决问题也不能因视图缩短自动关闭。待归纳状态控制能否压缩原文，不因读过但未采用的证据尚无笔记单独阻塞目录 `finish`。历史导航同时给出文件、定位和证据编号，复核用准确范围和 `review_reason` 表达目的。连续无新增依据、有效笔记或缺口进展时按原有规则收敛研究。容量检查区分服务计数、本地估算和字符兜底，不另加摘要模型或实时事实同步层。

研究决策超容量时，事实、依赖、职责等可替换为可读取的导航引用，完整快照不变；工具可取回历史结果和全部证据。覆盖审查按完整章节职责分区并分页导航目录，不裁剪正式要求；单项正式职责仍超容量时保留明确未核定状态。研究、修复和重启不能清空原有总模型调用账。

最终 Jev 页面评分与自动优化已退出生成流程，不再为其预留逐页评分和复评调用。预生成配图仍有独立软额度和核心调用预留，由 Store 在每次模型尝试前原子计数，最终必需配图仍受主额度限制。

正文生成和修复均先按节点的对象、路径及写作要求选材，输入能放入容量也不跳过相关性筛选；容量充分不代表同任务全部材料都适用于本节。当前节点必须覆盖的项目来源、所选事实对应的原始依据由程序强制保留，不能被选择步骤删掉。来源文本和必要引用原样传送，原始版本、完整元数据可在后台追溯。

修订还必须保留 `current.blocks` 中已经引用的全部原文。这些材料不再重复评分，容量精筛时也不得移除；没有新的相关资料不等于原正文没有依据。输出引用白名单由实际原文闭包产生，不能通过放宽校验或仅放入编号来规避来源丢失。

共享记录的 `conflicts/open_questions/summary/terminology` 与 `known_gaps` 也进入同一相关性筛选，避免它们绕过选材、变成每节的补写清单。写作及单节校验的 `work_task` 只携带定位信息；完整目标、问题和完成条件仍保存在研究记录与 `review_work`。单节校验保留事实和冲突用于核对正文实际主张，不把整组未决问题当作本节覆盖义务。事实抽取的输出引用仅允许非 `model_proposal` 块，无此类块时不生成事实索引；完整正文仍用于摘要、实体和独立校验。

已经选入依赖任务的事实，不再通过 `global_facts` 重复发送。去重要求节点、版本和完整事实内容一致；不同版本、不同来源或冲突内容仍保留，后台全局事实索引不修改。

上游检查报告不会直接当作下游业务事实。`dependency_catalog()` 为事实、建议、风险建立有来源的引用；模型选择相关项。事实/建议读取原文，相关风险生成带 `source_refs` 的 `risk_briefs`，明确标记 `unresolved_risk`。无关排版、抽取诊断和重复报告留在后台。重复选择同一个引用按集合去重；程序仍拒绝未知引用、跨页引用、把 risk 当作 fact 的选择，以及没有引用的风险摘要。

## 输入与输出分别管理

资料筛选 `select_context` 的 LLM 路径按完整请求的 Token 容量装页，默认输入预算 600,000 Token，不再与旧 32,000 字符门槛取交集。独立判断服务或缺少 Token 计量能力的兼容 Runtime 使用 600,000 字符作为分页回退值；这是 Unicode 字符数，不能当作服务精确 Token 数。分页器在每次尝试装入候选项时计算完整请求，包含 LLM 的提示词/Schema 或判断服务的状态与 questions；不会先按裸材料装页，再把某页的额外开销从所有页面统一扣除。太长的单项仍按原引用无损分片，不能靠截断装入。

主 LLM 筛选不再受每批 24 项候选限制；所有独立判断模型统一每批最多 24 项判断。用户聊天及确认答复的浏览器和 API 文本上限统一为 600,000 字符，用于入口接收和存储；实际发送模型前仍计量完整上下文 Token，不能把字符额度视为 600,000 Token。

意图识别和普通聊天保留全部有效历史，不再按最近 8/16 条或 18,000 字符提前删除。普通聊天直接流式发送时也检查完整消息的本地 Token 估算及已知模型窗口；超限明确返回容量错误，不通过静默删除历史来发送。已经完成完整请求计量的任务复用该结果，避免再用本地估算覆盖服务的准确计数。

启用判断模型时，资料筛选超限、容量精筛、接口错误都不会转交主 LLM；接口不可用会明确失败并保留已有结果。意图分类的原有回退策略不变；下一步动作直接由主 LLM 原生函数调用决定。资料筛选的独立判断路由不改变正文生成、事实核验或精查使用主 LLM 的行为。

`select_reads` 将准备好的真实子页分别交给 `_call`，每页独立归档、校验和缓存，并发仍受原有模型调用上限控制。直接调用 runtime 也有相同的分页保护。超长单项保持同一 `context_ref`，用 `fragment` 记录分片信息；Jev 任一片相关性概率严格大于0.8才保留完整来源，等于0.8不选，无效评分拒绝本次筛选结果。LLM 路径按其有效选择结果保留完整来源，不把某片缺失解释为整份材料没有内容。子页结果按原引用去重，后续写作仍读取原始全文。共同问题/必要来源元数据本身过大、无法安全切分时明确报错，不截断指令。

Jev 的证据、事实、建议、风险选择统一要求相关性概率严格大于0.8，不再采用“不确定则保留”的低阈值。usage 中 decision_relevance 逐项记录 probability、accepted、threshold，分片按原引用汇集；选择策略版本变更使旧的宽松筛选缓存失效，不影响已生成正文缓存。

跨多个任务选择风险时，`apply_selection` 按 owner 恢复各自完整原始风险和 source_refs，禁止将混合摘要附到每个任务。单任务短摘要保留现有契约；原文读取标记继续还原完整风险。判断模型只选择风险引用，不要求它生成长摘要。短风险可直接保留原文；长风险或跨片风险使用明确的原文读取标记，由 `apply_selection` 将对应完整风险载入 `risk_briefs.originals`，保留 `unresolved_risk` 属性。不能为满足1200字符摘要限制而丢掉否定约束，也不再额外调用 LLM 改写风险。

审计 usage 包含 `selection_provider`、`selection_batches`、`selection_max_input_characters`、`selection_character_limit`；判断服务另计 `decision_calls`，LLM 子页保留各页 usage。资料选择策略版本仅进入 `select_context` 的缓存身份，不使其他写作和审阅结果失效。

如果 LLM 服务实际拒绝输入容量或截断输出，筛选器把被拒绝的页继续二分，最多3层；每个初始页最多15次尝试，不增加输出配额重发相同输入。已是分片的来源可继续切分，保留父片信息。任一子页未完成，不能把部分选择当作完整结果。`selection_page_audit` 记录实际尝试的大小、来源引用和状态，`selection_attempts` 记录次数；这类服务端拒绝后的内部子页仍归属原缓存任务，不能据父任务条数直接推断 HTTP 次数。

支持的服务通过 `/v1/models` 获取 `max_model_len`，通过 `/tokenize` 对实际消息及 tools 定义计数；传入与生成一致的 `enable_thinking` 和 generation prompt 设置。`max_input_tokens` 默认 600,000，可显式覆盖；`context_window` 是输入与输出合计窗口，`tokenizer_encoding` 可指定服务无法计数时的本地编码（`o200k_base` 或 `cl100k_base`）。切换模型、接口或接入方式时，未显式指定的输入预算恢复系统默认 600,000，不继承旧模型的窗口和编码。旧配置中的 null 也在加载时归一化，不需要改写密钥文件。

容量条件：

```text
输入 token 计量值 <= max_input_tokens（默认 600,000）
输入 token 计量值 + 当前动作的输出预留 tokens + 512 tokens 余量 <= 模型上下文窗口（已知时）
```

窗口来自服务元数据或显式配置；两者都有时取较小值，不固定为某台部署的 32,768 Token。所有 LLM 动作统一使用 `max_tokens`，默认 128,000 Token，连接测试也沿用此额度；不再为意图、资料选择、研究、证据理解等动作单独压低输出。目录规划和修正的 `planning_max_tokens` 默认留空，仅在用户显式填写时覆盖。设置界面、配置文件和实际请求采用相同默认值，不再有 65,536 的应用层输出封顶。输出额度是允许的上限，不要求模型填满；对同时计入推理与正文的服务，两者共享该额度。

600,000 是应用默认输入预算，不代表每个模型都具备这一容量。不同连接的模型窗口必须独立配置或查询，不能从其他模型的设置推断。服务公布或显式配置了更小窗口时，实际输入、输出预留和余量必须满足该窗口；缺少窗口信息时保持未知，不伪造模型能力。

长请求的单次模型调用默认最多 900 秒，使用 `Limits.call_timeout_seconds`；作业配置通过异步任务作用域传入 Runtime，不再被传输层额外的固定 180 秒截断。显式设置更小或更大的单次额度都按该配置执行，未经过作业协调器的普通聊天流默认同为 900 秒。生成流不再设置独立的 60 秒无数据读取截止（仅该 HTTP 请求使用 `read=None`），推理期间暂未返回 SSE 也受同一个总截止控制；连接、写入和连接池的短超时保留，不修改共享客户端或容量探针的超时。整作业仍受 `run_timeout_seconds`（默认 7200 秒）约束；风格分析等独立阶段显式设置的更短截止仍生效。输出 128,000 Token 是允许额度，不保证在截止前生成完；超时保留现有诊断与检查点，不接纳残缺结果。

正文写作、修复、校验和审阅仍尊重服务真实总窗口。只有计量发现剩余窗口不足以容纳用户的完整输出额度时，才可按实际剩余空间调整本次输出；模型窗口未知或足够时完整发送 128,000 Token 的默认额度。模型请求与容量检查使用同一个额度，审计同时记录 `requested_output_tokens` 和实际 `output_tokens`，不修改用户配置、不截断输入。其他动作在真实窗口不足时调整输入批次或报容量错误；收到服务明确的上下文超限错误时，可按其返回容量减少输出重试。审阅若实际发生输出截断，继续使用分批恢复，不接受不完整结果。

服务不能计数时，显式编码使用 `local_tokenizer_estimate`；未指定编码使用默认 `o200k_base` 并标记 `default_tokenizer_estimate`。估算值写入 `estimated_input_tokens`，代表服务计数的 `input_tokens` 保持为空；不能宣称默认编码等于供应商实际 tokenizer。生产研究不再使用 `character_fallback`。工具结果的文件分页与兼容 Runtime 的字符回退值均不等于整个模型的上下文窗口。

计量接口的临时连接错误、限流或服务端故障不等于“不支持计数”。这些错误最多尝试 4 次（间隔 2/4/8 秒）；仍失败则保留检查点，记录 `capacity_unavailable`，不永久关闭 token 计量，也不靠字符门槛放行可能超限的请求。恢复后继续使用真实 token 数。

缺口补全、证据理解和局部事实判定不再因超过 3 项、20 条或 24 条就强制分批；先按完整请求的真实或估算 Token 容量判断。输入放得下仍不代表输出一定能完成：模型真实返回 `length` 的可分批动作会改变请求边界，丢弃不完整 JSON，不原样反复重试。写作的重复段落保护及有限修正仍保留。

## 图像请求

资料研究、视觉释义核验和风格分析仍可通过 `supports_image_input` 使用实际图片。上下文保存图片路径、定位与文件哈希，运行时发送前核对文件并构造真实多模态输入；请求审计不重复保存 Base64 图片。图片的 Token 估算采用保守预留，不能把文字 tokenizer 的结果当成图片准确计量。

图像输入用于资料研究、视觉提取核验和风格分析；正常文档生成不执行逐页审美评分。

## 分批合并与校验

- 证据阅读：整条证据分批；汇集全部带来源事实，不以最后一批覆盖前面。事实按陈述与来源生成稳定 ID，去重后保存，汇集记录不受单次输出的 50 条事实限制。
- 缺口补全：先按缺口拆分，再以本批缺口为目的选择完整证据、局部事实、全局事实及已有方案。被选中局部事实的原始证据强制随请求保留，相关冲突不丢弃。较早批次生成的方案可被后续批次读取以避免冲突；合并后验证每个 gap_id 恰好出现一次，保留目标节点和模型建议属性。若该批仍超限，继续拆分并重新选择资料，而不是反复携带整个任务的累计材料。
- 单项缺口仍超限：通过 `read_gap_materials` 分页阅读全部已选来源，每页输出带 `source_refs`、`source_kind` 的业务约束，然后仅将这些约束交给补写步骤。逐页保留原文、阅读结果及缓存；程序拒绝未知引用和来源类型变化。阅读笔记不写入证据库或已确认事实，补写结果仍是模型方案。正文写作、事实抽取和校验继续使用原始证据，不用这些笔记替代校验来源。如果笔记合并后仍超限，明确保留检查点并失败，不无限压缩或假装完成。
- 补充内容整合：`supplement_integration.py` 对每项补充分别选材，`integrate_supplement` 只返回 updates/remove_block_ids/resolved_pending_items，程序保留未编辑的正文块和配图。新增模型方案不得冒充有据事实；仅检索已回答的问题通过 evidence_refresh 分支使用原文引用。界面使用“正在将补充内容整合到《章节名》”。
- 整合超限兜底：实测请求过大或服务返回容量/输出截断时，`supplement_conflicts.py` 分拆已选材料及方案，逐批判断同一适用范围内的冲突。每页必须覆盖所有本批方案，冲突必须提供可在原文中核对的逐字引文，兼容时也保留适用的关键约束。超长单项按原引用和位置无损分片；不确定的跨片关系不能当作已通过。汇总全部约束后统一修正，最多两轮，每轮重新检查全部已选材料，不能后页覆盖前页结论。返回必要原文引文及修正方案进行局部整合；兜底核对通过后，补写正文必须逐字沿用已核对方案，不让最后一次排入正文的调用改变业务含义。采用修正方案后，在任务锁内按原版本比对更新后台 proposal 内容，使审阅缓存失效，保留并发更新的章节归属、兄弟方案和检索计数；并发版本已变化则不覆盖，保留待确认。后续正文校验仍用完整原始证据。每节共享32次实际模型调用和120秒截止，最多4批并发；缓存命中不重新收费，取消会排空子请求。核对不完整、约束冲突、预算用完或最终最小编辑仍超限时保留当前正文并记录待确认，不以半份结果通过，也不让本项容量错误中断整份交付。
- 事实抽取：按完整正文块拆分，合并时重命名局部 claim_id，保留 block_ids 和 evidence_ids。
- 局部校验：小请求可一次完成；大请求/输出截断时拆为事实判定、正文块检查、逐项项目来源覆盖。事实判定保留本批断言锚定的正文和引用原文，正文检查逐块覆盖原文；递归分批时同步收窄正文及证据，保留该范围的必需项目来源。无锚点的旧断言保守保留父页正文，表格行未提供逐行来源映射时保留整表引用。项目来源覆盖读取本节点完整正文。最后验证每个事实恰好一个判定，保存逐事实判定和核验是否完成；问题按具体内容及定位去重，同键但不同问题不得覆盖。
- 业务任务审阅：通过下述按问题阅读流程控制所有资料的规模，不再用拆正文、保留整包资料的方式兜底。
- 跨任务审阅：保留相邻窗口，按同一范围/主体/属性的事实、共同主题及显式业务依赖补组。每组最多配置宽度的节点，宽泛实体不再生成两两全连接；同一事实键的不同原样取值在宽度内一起比较；超过宽度则产生一个完整事实组的精查候选，候选或未声明单值的断言也参与；不展开全部值对。已覆盖的宽事实组不再重复生成规则候选。精查无法完整容纳其证据关系时保留待确认。被已有组覆盖的关系复用同一检查请求。请求保留本批事实锚定的完整正文块；过大时可标记 `comparison_originals_deferred_to_drill_down=true`，保留全部事实和建议索引，将原文留待精查，不能裁掉大块后声称已读。仍超限再拆分事实/建议；候选必须定位两章真实块并返回共同条件和不相容理由，不能因本批缺少其他部分而误报全文遗漏。

### 按问题读取原始资料

入口为 `orchestration/focused_review.py`。任务审阅与问题精查的完整材料能放入实测模型窗口时直接调用，不再因可选材料超过 32,000 字符而强制筛选。完整请求超限时再按当前疑点选择材料。被正文或疑点明确引用的原文、任务完成条件始终必读，不送入选择器再强行加回。选后原文能放入时仍直接核对，不额外生成阅读笔记。此处不改变正文生成、修复始终先按节点选材的规则。

1. **确定检查重点**：`plan_review` 只接收任务问题、完成条件和目录索引。通用完整审阅保留每节点检查；生产任务的 `task_consistency` 审阅复用已经执行的节点校验，不再重复建立同样的单节点检查。LLM 提出最多 8 项有实际业务关系的跨节点问题，每项最多关联 4 个节点，不自动枚举所有节点对。
2. **按问题选资料**：选择目的包含具体问题及目标节点的标题、路径和写作要求。事实、证据、方案、风险作为独立资料进入分页选择。当前节点正文、目录要求、完成条件必读；正文或所选事实引用的原始依据强制保留，相关节点的补写方案保留。无关资料仍留在后台。
3. **阅读原文**：已选原文合起来能放入窗口时直接核对，不先生成笔记。仍超限时，正文、要求、证据、待核事实、模型方案、风险分类型读取，输出 Schema 将来源类型限定为当前页类型。正文及要求逐项读取并强制返回带引用的笔记；其他来源每页最多 8 项。兼容分片默认以 600,000 字符为界，以规范 JSON 的连续片段完整传送超长单项，保留父来源与字符区间，不丢弃尾部、表格行或否定条件。
4. **汇总候选问题**：每页最多 8 条、每条最多 400 字的笔记，保留来源引用及类型。汇总保留当前问题涉及节点的原始正文，只将辅助资料替换为带来源的阅读笔记，不重复整任务资料包。原始正文仍超限时使用带节点归属的正文阅读笔记，此模式只能发现候选冲突，不能推断原文遗漏。事实和方案不会因写入笔记而升格为证据；笔记中未提及某内容不能证明正文遗漏或无依据。
5. **回到原文裁决**：候选问题进入原有 `drill_down`。其上下文按具体问题选择原始资料，保留受影响节点正文及必要的引用依据，不附带整任务的同级正文。无法从原始依据裁决时保留待确认，不凭阅读笔记授权改写。

单页输出过长则拆页；单项输出仍被截断时，最多尝试一次最多两条笔记的简洁输出，输入原文不变。不接受半份 JSON。最终笔记仍不能容纳时，记录明确的“审阅未完成”待确认项，不能当作审阅通过。来源记录、阅读页和各阶段结果均可追溯和复用。

同一任务的问题检查复用 `max_parallel_reviews` 的并发上限；每个问题内部顺序读取材料，子页不额外创建并发池。异常或取消时等待在途协程退出。

三轮检索得到的不同切片继续累积保存；`evidence_chars` 用于单次资料读取/检索预算，不再充当整个任务的累计证据上限。

其他尚不支持继续拆分的动作，最小安全单元连同必要上下文仍超限时，会明确失败并保留检查点；不会截断原文或接受半份 JSON。上述问题审阅支持原始资料按区间阅读，但不代表所有动作都能处理任意大的单项材料。

## 恢复和审计

失败任务的 `usage.diagnostics` 仅记录允许的数字和枚举：首个响应/正文时间、已接收字符数、结束原因、token用量等；可沿外层超时的异常原因链恢复，避免只剩空的 `TimeoutError`。已收到但未完成的模型正文单独存入本地 `contexts/failed_outputs/`，最多保留32,000字符头尾并注明是否截断，不进入错误消息、界面或usage，也不采用为正文。HTTP/SSE服务错误体和推理内容不写入该正文审计；这些本地记录随业务数据目录保持不入库。

审阅阶段恢复且所有节点已保存时，直接进入审阅，不重新启动已完成任务的写作/研究循环；依赖版本变化仍由任务审阅入口检查。后台完整依赖快照仍用于研究版本和审阅有效性判断；改变模型工作视图不会把旧任务的三轮检索计数清零。已保存节点跳过，成功的模型子请求继续使用原有 `tasks` 缓存；调用入口先校验成功缓存，只有未命中才进行容量测量，因此可用的本地结果不会被容量服务暂时故障挡住。已记录的容量/输出截断父请求可直接进入分批，不重新消耗相同调用。

已经完成研究的任务在审阅时发现上游版本、事实或问题清单变化，只使审阅缓存失效，不自动重启知识检索，也不清空已有补写记录。审阅读取最新依赖及其中已支持事实对应的原始证据；如果发现正文需要修订，再由明确的修复动作处理。尚未完成研究的任务仍从研究检查点恢复。

对程序确认的已指定表头缺失，修复只使用已保存的材料，明确列名和保留已有内容的要求，不因表头缺失重新检索。修复完成后立即检查同一条件。若仍未满足，不采用该次候选正文，不触发下游审阅循环；失败候选存入 `contexts/rejected_repairs`，保留原正文和问题清单，输出 `needs_confirmation` 草稿。该状态不代表审阅通过。

模型调用次数预算耗尽与输入容量不足分别处理；受支持的服务异常/超时也可触发完整正文降级。发生这些中断时，若全部目录节点已保存，停止新增模型请求，保留当前正文、原疑点和明确的“检查尚未完成”记录，令 `review_passed=false`，导出 `needs_confirmation`。已有有效配图可复用，尚未完成的配图保留缺图标记，排版保留安全版式。正文不完整时仍失败并保留检查点。这一降级仅防止完整正文随审阅中断而无法下载，不等于技术验收通过，也不把超时、缺图或未执行校验伪装成完成。暂停/取消、存储故障和程序错误不走该降级；导出自身失败仍报告。用户可显式补答或不填答复而重试，并设置1～10000次的新轮额度，默认200；累计调用不清零且上限100000，重复请求不会重复授权。详见[待确认续跑](confirmation-and-resume.zh-CN.md)。

本地审计路径：

```text
.folio/jobs/<job_id>/contexts/
  agent_assignments/<hash>.json  确认计划/输入版本、任务归属和依赖快照
  agent_results/<hash>.json      已保存正文版本、审阅版本与有效问题
  agent_repairs/<hash>.json      原负责人、修复要求和预期正文版本
  sources/<hash>.json    当前动作可访问的完整后台快照
  views/<hash>.json      按动作整理的视图及容量测量
  requests/<hash>.json   实际请求上下文、task_key、输入/输出预算和计数方式
  review_plans/<hash>.json   本轮顶层分组、节点版本和并发上限
  review_results/<hash>.json 分组结果及所属计划引用
  review_deduplication/<hash>.json 完全重复疑点的原记录及相同问题键的区分依据
  gap_reads/<hash>.json      单缺口分批阅读的完整来源目录与带来源约束
  focused_review_plans/<hash>.json 问题清单、完整资料目录与源快照引用
  review_reads/<hash>.json         当前问题实际选取的原始资料及区间
  review_read_results/<hash>.json  已读页面清单、带来源笔记及汇总上下文
```

完整模型结果、usage、错误仍在 SQLite `tasks`/`decisions` 中。资料选择也作为独立任务缓存；选择请求中的候选项可还原风险来源。普通日志和界面不展示 API Key 或推理原文。原生工具消息返回的 `reasoning_content` 可随私有检查点保存，用于后续同一工具历史的协议续接。

精查返回固定的完整结构：是否确认问题、说明、是否需要人工确认、受影响节点和修复指令均须返回。程序再检查需要自动修复时的目标节点和指令，避免条件分支约束导致模型只返回部分字段。修复指令中的临时引用在持久化前还原成后台引用，下次请求再按该次上下文映射，不能跨请求复用临时编号。

[review_scope](../src/folio/orchestration/review_scope.py) 为生成、校验、审阅和精查提供当前相关节点的真实职责、父子关系、`figure_policy` 和已保存子图定位。带该契约的精查还需返回结构化 `repair_targets`，不能给已委派绘图职责的父节重复添加不符合分工的图。针对已定位事实块的来源、冲突和遗漏疑点，`applicability_checks` 必须核对正文主体、来源主体、资料角色及适用性，并提供可回查原文的引文；将供应商产品能力、性能测试或外部参考作为本项目要求时，还须有明确的项目采纳依据。同数值或引用存在均不足以证明适用，不确定结论保留待确认。程序校验定位与引用，语义判断仍依赖模型；字段兼容旧存档，当前请求按适用范围动态要求，不增加额外模型调用。

新生成和修订的 `record_only_pending` 通过 [pending_metadata](../src/folio/runtime/pending_metadata.py) 收窄为具体人员及文档元数据，并定位真实空白表格单元；通用“备注”、业务日期约束和功能要求不能伪装为文档日期等元数据绕过补查。旧存档仍可读取。这些范围与来源保护已有离线回归，后续完整实跑在选材阶段失败，尚无其后半程的真实成品验收结论。

本节事实段落若与已知补写方案整段或较长完整句子逐字重合，会按正文块及字符区间提出来源候选；精查强保被点名的方案原文及引用依据。编号合法不证明引用支持内容；后来取得的真实依据可以支持同样的设计，因此候选可被驳回，不能自动把整段改红。精查须先对照节点定义核实职责，不能仅因候选声称“缺少范围”就给另有职责的章节新增要求。

审阅过程事件使用兼容原有 `work_update.text` 的可选 `review` 字段，落盘到 SQLite，并写入 `jobs/<job_id>/review.jsonl` 和服务日志。每轮有独立 `round_id`，每个组或问题有 `unit_id`。前端依据这两个字段更新同一条记录，展开后可查看涉及章节及版本、实际分组原因（相邻、具体事实、共同主题或业务依赖）、候选问题、精查理由、耗时和调用明细。分组原因同时进入模型的 `review_topics`，要求只比较同一适用条件，不将同义表达或省略重复说明当作矛盾。

调用计数使用随异步任务传播的作用域，拆分后的子请求、准备精查的资料选择也归入所属检查项；并发组相互隔离。本轮汇总分别记录 `model_calls`、`cache_hits`、`failed_calls`，每个动作另有分项统计。成功验证缓存才计为复用，真正取得模型并发名额并进入 runtime 才计为调用；引擎内重试逐次计数。这是模型任务调用次数，底层服务内部重试或 HTTP 子调用须结合原有 usage 查看，不能直接当作 HTTP 次数。

精查日志区分模型判定成立、不成立、无法确定和硬规则仍失败四种情况。错误和取消不会输出通过结论；模型认为不成立但结构或来源校验仍失败时，仍明确保留待确认。精查结论与随后保存修订的日志分开，不能把“模型确认疑点”显示成“已经修好”。本轮跨章节检查汇总另记录原始候选数、去重数、已排除数和剩余疑点，复用结果也明确标记，不再用重复的组完成进度暗示又调用了一轮模型。

## 回归验证

`tests/test_agent_collaboration.py` 覆盖任务/修复交接的版本及归属拒绝、误报处置同步事实与依赖、不能因排除问题晋升负向/未知/建议事实、非依赖全局事实的原文闭包、风险归属与同键问题保留。

`tests/test_request_context.py` 覆盖：大量上游报告的语义选择与原文留存；跨批全部事实及中断恢复；缺口精确覆盖；局部校验分工和父失败不重放；跨节点全部组合；写作强制保留项目来源；token 门槛和字符门槛的区别；服务不支持计数时的回退；风险引用不能升格为事实。

跨任务审阅按主题建立有界分组并保留相邻窗口、具体事实与依赖关系；不因双方都有模型建议而配对，也不为宽泛实体建立全连接。顶层组默认16路并发（`limits.max_parallel_reviews`），业务任务执行期间主模型最多32路，后续审阅等阶段16路，跨阶段合计受主服务32路总上限保护；已验证并启用的判断服务统一使用独立16个并发名额，主模型与判断服务合计上限48路。相同请求复用缓存；并发失败/取消会等待所有在途协程退出。界面显示实际进度和详情，组检查结束不表示每项疑点均已通过。

`tests/test_review_optimization.py` 覆盖宽泛实体分组线性增长、已有窗口覆盖复用、远距离同范围事实、长短不对称依赖、精确去重与问题键碰撞，以及不同取值跨窗口、重复副本、不同适用范围和同任务首代表等反例。当前 `citation_review` 在局部及任务审阅入口要求缺引用指控定位真实事实块，不接受仅因红字补写缺引用而报错；混合事实、来源冲突与内容遗漏仍须独立精查，不能按关键词或红字标签一概豁免。

`tests/test_focused_review.py` 覆盖整任务资料过大的失败形态、按真实关系检查而非全节点配对、引用证据强制保留、原始材料无损分片、来源类型不可升格、正文不可漏读、未完成不能放行，以及重跑复用缓存。

写作阶段的筛选目的以当前 `section` 为准，不把 `work_task` 当成本次请求范围。超量时共同筛选业务记录事实、全局事实和原文，并按当前节点筛选依赖事实；保留强制项目材料、选中事实的原文及已有约束。修复指令参与筛选，完整来源仍在请求归档中。此边界同时用于 `generate` 和 `repair`。

### 跨章节陈述与范围核对

跨章 `review` 的候选必须带两节真实存在的 `block_refs`、共同适用条件 `comparison_scope` 和具体不相容关系 `incompatibility`；Schema 与结果校验约束真实定位，语义是否成立仍交给独立精查。不能截掉正文块内“虚拟/真实、当日/隔日”等否定与例外来满足容量；明确延后原文阅读时也必须保留原索引，不能把候选视为最终裁决。

单节来源不足、内部矛盾和遗漏由 `validate` 与 `review_work` 负责，跨章步骤不重复这两类审计。不同业务对象的合法差异、相同陈述位于不同章节，不应生成冲突。界面中仍保留每项候选、精查结论和来源，不在本地按红字或关键词删除疑点。
