# LLM Outline Planning Design

> 中文版: [中文版](outline-planning.zh-CN.md)

Plans the outline based on writing requirements and source materials, with support for an optional user-provided DOCX template and on-demand web supplementation. The legacy mandatory-template workflow, pseudo-outline, and outline-reference protocol have been removed.

## Inputs and Workflow

The GUI uploads files and submits writing requirements. Files default to ordinary source materials, `source`; one DOCX file can be explicitly designated as the document template, `template`. The CLI uses `--request` or `--request-file` with `--knowledge`; the job API uses `user_request`, `knowledge_path`, or an existing knowledge base configuration. The legacy public input parameters `template_path` and `outline_path` are not restored. No `outline.md` masquerading as an outline is created, and user requirements are not assigned reference identifiers such as `o1`. The optional template is supplied through the workbench's file-purpose setting, and trusted template constraints are passed along with the document plan.

A completed sample document can be explicitly designated as `style_reference`. Before outline planning, the program collects structural, body-text, and formatting statistics from style examples. The main model reads all extractable text in batches according to request capacity and summarizes the writing style, generating `style/style.md` and the corresponding `style/profile.json` from the same sources. Originals are stored separately in `style-references/` and do not enter the business research Manifest or original-text evidence. The primary sample's structural organization and heading conventions are passed into the planning context as concise Markdown. Specific headings, business rules, and chapter counts in the samples must not be elevated into requirements for the current task. A lack of style samples does not mean a lack of business source materials, and style analysis must not be used to bypass source research.

Style analysis is jointly constrained by `StyleAnalysisConfig`, actual capacity, and the total call budget for outline planning. Three sampling passes are no longer treated as completion of full-text analysis. Text coverage and visual gaps requiring page images are recorded separately; see [Request Context and Capacity Design](context-and-capacity.md) for specific limits. Roles, file hashes, and style parameters are frozen with the confirmed version. `SourceDirectoryDrafts.load` returns `sample_paths` and `writing_profile` from the same version, and `Store.create(..., writing_profile=...)` validates and freezes them into the job. Body writing reuses this result rather than extracting style again for each chapter.

The outline workflow is: writing requirements and file snapshot → shared index of ordinary source materials and optional template-constraint extraction → main LLM browses the Manifest, selects relevant files, and inspects internal structure, reads original text, and performs follow-up reading as needed → extract outline requirements supported by original-text evidence and unresolved issues → complete `plan` model request → checks of structure, template constraints, and source-requirement placement → Word layout preview → user confirms the current outline version after research is sufficient and checks pass → business task planning and body research and writing. Without a template, the confirmed style and formatting parameters are used and supplemented by built-in rules. With a template, both the preview and body are based on the frozen original DOCX.

`planning_context(requirements, source_catalog)` still provides the complete writing requirements and source navigation; research results are passed separately as a basis for planning. The research entry point before outline generation uses the shared SourceIndex and existing file tools, allowing the main LLM to select files based on the objective, browse headings/Sheets/actual PDF bookmarks, read relevant original text, search, and continue paging. It no longer proceeds directly to planning after taking a fixed excerpt of the first 8 headings and first 12,000 characters of each source. Listings and structures are only navigation aids. Programmatic parsing does not mean the model has read the original text, and a search hit does not mean the relevant range has been read in full. Research tools return truncation, next-page, and unread status; the model must continue reading or explicitly retain the gap.

After upload validation, program-generated `structure.json` and `structure.md` files are saved alongside each original. When creating an outline-source snapshot, `SourceIndex` reuses shared parsed objects to generate `structures/<file_id>.json` and the corresponding `.md`. JSON preserves precise locations and versions; Markdown describes only the actual internal structure. `fs.inspect` directly provides this Markdown, returning normal-sized structures in full and paging only extremely large structures at complete-node boundaries. Word/Markdown preserve heading hierarchies; Excel preserves Sheets, ranges, and candidate headers; PDF uses actual bookmarks or compact page ranges; PPT uses slide titles. Parsing status is explained in the relevant body-text reading results, not mixed into structure files.

The model reads materials by file, node locations such as `F1/N005`, or page number. Original paths, node IDs, source versions, and evidence references are still verified by the backend. Research inputs are organized as text/Markdown, and tool actions invoke functions such as `fs_read` through native `tool_calls`. The program returns actual results with matching `tool_call_id` values rather than parsing action JSON from response text. Research concludes by submitting findings through native `finish`, where `requirements` cites read original text using evidence identifiers such as `E1`. The program derives the selected ranges, `selected_ranges`, from evidence and actual reading records; the model no longer supplies range identifiers. The backend continues to check requirements, original-text support, actual delivery, and unresolved issues without repeatedly embedding the complete `finish_contract` into every round of source context. A page that has been read may be cited without requiring the entire query range containing it to be read. The range's `complete=false` and unread summary remain accurate; partial evidence must not be presented as full-chapter coverage.

`fs.inspect` is the recommended navigation tool, but a complete structural inspection is not required for every selected file. Once body text has been read through search, explicit page numbers, or node locations, conclusions are not blocked solely because `fs.inspect` was not called, provided the corresponding evidence is genuine, version-consistent, and has been sent in full. Structural inspection records still reflect actual execution. Skipping navigation does not mean the structure has been browsed, nor does it turn search summaries or unsent content into read original text.

A single research response may contain up to 16 tool calls. Streaming reception fully assembles each call before validation and execution; up to 4 independent file tools may run concurrently. The next request retains the complete batch of `assistant.tool_calls` and each result with its `tool_call_id`. File evidence, reading progress, and short identifiers are registered in call order. Reads that depend on a preceding result must be placed in the next request round. `finish` must be called on its own; if mixed into a batch, the entire batch returns an error. Research cannot be declared complete based on results not yet sent to the model. Model calls and tool operations are counted separately: outline research defaults to at most 36 model calls, 3 research rounds, and 120 tool operations. Before concurrent reads, the original-text allowance is reserved by batch so that each tool cannot independently reuse the entire remaining allowance.

Outline research checks capacity against the complete request, including system messages, source text, native call records, all notes, and tool definitions. Runtime defaults to an input budget of 600,000 Tokens and an output budget of 128,000 Tokens, supports missing/null legacy input configuration, and does not revert to the old character limit when switching models. When the service cannot count tokens, local estimates are explicitly marked. If a smaller total context window is known, the actual window is enforced. Individual body-text reads may still be paginated; page size does not represent the limit for the entire research history. The cumulative original-text character allowance, `max_evidence_chars`, is left unset by default and limits cumulative reading only when explicitly configured. Ranges actually extracted by tools and ranges actually delivered are recorded separately. An unsent tail must not be marked as read. `finish` may cite only original text that was actually provided. See [Request Context and Capacity Design](context-and-capacity.md#manage-input-and-output-separately).

File short identifiers, internal paths, and unique display filenames can all be used for reading. Ambiguous duplicate names return candidate short identifiers. Continuation identifiers already include a location; resubmitting the same file or location is accepted, and only conflicting locations are rejected. The persistent reading-progress display provides directly executable continuation entry points. When the same evidence appears across batches, both delivery and summarization status are carried forward based on the evidence identifier, source, version, and location together, avoiding a state that remembers only “summarized” but requires the content to be sent again.

On tool errors, repeated lack of progress, or budget exhaustion, results are saved first. If original text has been delivered and calls and time remain, at most one finalization request allowing only `finish` may be added, counted against the original budget. Normal reading reserves one call and part of the original time allowance for finalization. No finalization model request is initiated after user cancellation, model timeout, or model unavailability. Finalization still validates actual delivery, ranges, references, and unfinished items; an empty conclusion cannot pass validation. The report adds `termination_reason`, `failure`, `conclusion_submitted`, `finalization_attempted`, and `working_findings`. The latter preserves notes supported by actually delivered evidence; inferences do not become confirmed facts.

Outline planning receives formal requirements, valid research notes, and relevant original text that has been delivered. When research is incomplete, delivered materials are retained; research results are not discarded merely because `finish` is missing. Coverage checks distinguish incomplete research, tool/model execution failures, genuine source gaps, outline omissions, and insufficient review capacity. Outline generation is retried only when research is ready and the outline truly omits requirements. Upstream research failures cannot be fixed by repeatedly rewriting the outline. `confirmation_issues` is saved with the outline version and passed to the interface to display specific blocking reasons.

Outline research and business research share `ResearchMemory`: the program records actual delivery ranges, and the model includes incremental `research_notes` in its next tool call, accumulating findings, task impacts, original-text references, and unresolved issues as individual entries. Notes use `evidence_ids`; `request_ids` is no longer required. The program verifies request-batch associations against actual delivery records. Omitting notes does not clear existing content; an existing entry is revised only when `note_id` is specified, and retries do not append duplicates. Each batch of original text must be summarized before leaving the current context. If there are no relevant findings, `no_relevance` may be submitted; the same range must not be read repeatedly merely because no conclusion was found. Pending-summarization status only determines whether original text may be compressed. Evidence that was read but not used does not block `finish` merely because it lacks notes, nor is an item-by-item explanation of irrelevance required to end research. Research notes are persisted in the report and exported as `research.md`; see [Shared Research Memory](agent-research.md#shared-research-memory) for the detailed contract.

Normal requests retain the complete tool history, all notes, and unresolved questions from the current research session. Manifest and structure results do not automatically leave the context merely because they have already been sent. History is reduced only when the complete request exceeds the model's input capacity, with older original text that has been summarized removed first. If the limit is still exceeded, notes are then replaced with a paginated index. Complete backend records are always retained, and history entry points identify files, page ranges, and evidence rather than asking the model to guess from bare identifiers. Rereading a previously read range requires a specific verification reason. Repeated rounds without new evidence, useful notes, or progress on gaps preserve an incomplete status under the original budget. Research is complete when it sufficiently supports the current outline; not all original text must remain in the final context at once, and model inferences are not promoted to global facts.

Research has tool, call, time, and context budgets. It does not require unconditional reading of every attachment in full, nor does it force chapter selection based on fixed domain terms. If key evidence affecting the outline is insufficient, the budget is exhausted without a valid conclusion, relevant materials cannot be parsed, or the user's scope remains undetermined, the research report remains `partial`. A draft and specific gaps may be shown, but confirmation cannot lead directly into body writing. When there are no ordinary source materials, `no_sources` is recorded and planning based on user requirements and an optional template is allowed, without fabricating reading records. The outline research report and reading records preserve original file versions, locations, evidence, and requirement identifiers. These represent actual source requirements, not the removed pseudo-outline.

When a template is selected, a `template` context is added containing only actual fixed sections, completion instructions, permitted expansion locations, and required table headers. It does not provide sample business body text, data rows, or local file paths. The template does not enter the ordinary source materials' `source_catalog` or research directory. Duplicate source materials with content identical to the template trigger an error before planning to prevent examples from being reused as facts.

The complete outline proposal is not split into batches or pre-grouped by fixed business terms; source reading and source-requirement review may be paginated or batched. Without a template, the model determines chapter titles, hierarchy, order, writing instructions, and container relationships. With a template, the model preserves the fixed template structure and adds chapters only where explicitly permitted. The writing guide is provided with the outline request, but it is not business evidence and does not introduce a dedicated guide-review call. Exceeding the planning input budget produces an explicit error rather than silently truncating writing requirements or switching to a fixed-rule outline.

## On-Demand Web Supplementation

Outline research decisions remain with the same Agent, which first understands the user requirements and relevant uploaded materials. When the selected search service (Tavily or DeepSeek Search) in the model configuration is enabled and validated, the native `search_web(query, purpose, summary)` tool is provided. Searches are performed only when specific public questions affect the outline's scope or chapter arrangement. If the materials are already sufficient, local research is completed directly, without adding a fixed search phase. A user request not to access the web is honored. Missing private materials such as bidder information, pricing, and personnel certificates remain pending supplementation; searches must not be used to fabricate them, and sensitive original text must not be sent as queries.

The tool returns public webpage excerpts with `W` references, URLs, titles, and retrieval times, explicitly identifying them as neither verified full webpage text nor project facts. The model summarizes them separately in `finish.web_findings`; requirements from uploaded materials may still cite only `E` original-text evidence. Public references do not override tender documents or template constraints and cannot replace local-file coverage checks. The program checks that public references actually exist and that excerpts were sent to the model; source-identity validation is not treated as verification of content truthfulness.

Web and file tools share the current research session's time, tool-count, model-call, and context budgets, with at most four tools executing concurrently. No additional fixed search-round limit is imposed. Identical normalized queries reuse results saved in the current research directory. Failures save their status and safe error codes while retaining existing materials, and the model decides whether to record a gap or retry within the original budget. Results are paginated only when they exceed the current request capacity. Full text is retained and can be read further through `fs_read(scope='history', request_id=..., offset=...)`; excerpts not displayed cannot be cited as read.

`research/web-research.json` saves queries, purposes, result statuses, source excerpts, and conclusions. A separate `web_research` field in `research/report.json` summarizes these records. The interface reuses the existing progress panel to display search purposes and results and shows source links in the source-research records. Outline planning receives the public references, which are frozen into the body-writing job along with outline research after confirmation. The business Agent receives previously researched questions, conclusions, and source navigation. Complete excerpts enter its evidence pool and can be read locally for verification; further searches are needed only for new questions or genuinely necessary freshness checks. These conclusions do not automatically become global facts. Local outline research remains available when no search service is configured.

## Data Contracts

`PlanProposal` contains only `sections` and `notes`. Each `PlanItem` contains:

- `node_id`: A stable outline-node identifier used for local revisions and section identity.
- `title`, `level`: The heading and hierarchy level.
- `instruction`: Writing requirements for this chapter.
- `content_mode`: `generate` requires body text; `container` only organizes child sections.

Model output does not contain the legacy `outline_refs`, `mapping_reason`, template field/table references, or a list of unused template fields. `build_plan(document_id, proposal, template=...)` computes stable `section_id` values, parent-child relationships, section paths, and display numbering. `Section.node_id` identifies a generated outline node and does not claim correspondence to an original source.

When a template is present, the program validates and binds the plan using a trusted `TemplateContract`: `DocumentPlan.template` stores the frozen original's path, hash, and structural constraints; `Section.template_section_id` links to an actual template section; `required_tables` stores required-table constraints; and `allow_subheadings` controls lower-level headings in the body. These fields are derived by the program and cannot be independently declared or deleted by `PlanProposal`. This differs from the removed mandatory template-field matching protocol and does not require tasks without templates to provide fictitious mappings.

Business sources continue to use independent Evidence, `source_id`, locator, `evidence_ids`, and research records. Removing pseudo-outline references does not affect factual provenance, shared facts, research coverage checklists, or body citation verification.

## Validation Boundaries

The code checks JSON/schema, required fields, unique node IDs, nonempty titles, hierarchy starting at level one without skipping levels, duplicate sibling titles, writing instructions for body-text nodes, and the requirement that containers have children. The complete result is rechecked after outline changes.

No outline-number existence or original-outline coverage checks are performed. When a template is explicitly selected, additional checks validate fixed titles, levels, parent-child relationships, order, and whether new sections are placed in permitted expansion locations. Sections containing required tables must generate body text. Template sections are not expanded by default; explicit completion instructions in the template can permit subsections. See [User Template Design](templates.md) for specific rules.

`review_directory_research` uses the main model to compare each researched `requirement_id`, its complete corresponding original-text evidence, and the entire outline, returning `covered`, `not_applicable`, or `missing`. Coverage must be explicitly tied to the title or writing instructions of a node that actually generates body text. Multiple requirements may share a chapter; one chapter per requirement is not required. Exclusions must explain the user scope or applicability conditions in the original text. An unselected bid lot is not grounds for unilateral exclusion. The program checks that every item appears exactly once, uses a real `node_id` and that item's actual `evidence_ids`, and provides a nonempty rationale. It rejects fabricated IDs, omitted items, and references pointing only to containers. This result is saved separately; fields such as `outline_refs` are not restored to `PlanItem`.

Coverage review packages all requirements and their original text according to the budget. Each batch receives the complete outline, and original text is not truncated. The default maximum is 12 batches, also constrained by the current call allowance. If a single item's complete context is still too long, or reviewing all items exceeds the batch budget, a gap is explicitly returned rather than declaring success after checking only the first requirements. Model failures, truncated responses, missing items, or invalid references cannot count as a pass. Omissions trigger bounded outline repair and rechecking; if gaps remain, the outline stays an unconfirmable draft. Each batch's input is saved to disk before the request, and results, usage, and elapsed time are saved after the response. Completed batches are retained even on failure or cancellation.

Passing the source-requirement placement check means only that the researched requirements have explicit places in the outline. Issues such as research being `partial` or scope remaining undetermined still independently block confirmation. The body-writing phase continues to review actual content coverage, original-text citations, facts, and consistency. The outline phase does not claim that the body already satisfies the requirements.

If JSON cannot be parsed or schema validation fails, the error and raw response are returned to the model with a request to output the complete outline again. Only when the schema is valid but structural checks fail may the model modify only the explicitly identified error paths while keeping other nodes unchanged. An invalid repair response does not overwrite the last schema-valid outline baseline; subsequent repairs continue from that baseline. A new preview is published only after the complete outline passes revalidation. Corrections are constrained by call-count, time, and input budgets; limited additional corrections are allowed only when the number of errors decreases. Transport errors are not presented as outline-structure errors, and timeouts do not automatically trigger outline correction. Truncated output is not accepted as a valid outline.

Errors in fixed template structure may require restoring an entire subtree, so the complete proposal is retried when there is no safe local repair path, without relaxing template constraints. If the template itself cannot be parsed or contains unsupported structures, the user is explicitly prompted to correct the original template rather than silently switching to free-form generation.

## Revision, Recovery, and Preview

`revise_plan` uses stable node IDs to update titles/instructions and to insert, move, and delete nodes. Moving a node carries its subtree, avoiding accidental changes to unrelated chapters based on array positions. With a template, the complete revised result remains subject to fixed-structure and expansion-boundary constraints, and source-requirement placement is rechecked. On failure, the previous version is retained, but confirmability still depends on the current requirements, source versions, research status, and check results. Confirmation includes the outline version and verifies requirements, the writing guide, all uploaded file IDs, and `source_roles: [{id, role}]`. Confirmation of an old version or a role change cannot start body writing. Historical metadata without `source_roles` is supported only for outlines whose files are all ordinary source materials.

Generated previews are written to `previews` and accessed through `/previews/{id}`, PDF, page-image, and download endpoints. There are no template-listing or recommendation APIs. Legacy previews on disk can be loaded read-only. Deprecated fields are removed from old jobs and saved outlines through an explicit migration layer for persistent reads; new model and API inputs still strictly reject legacy fields.

The output directory retains `planning-input.json`, `planning-attempts.json`, `planning-proposal.json`, `document-plan.json`, `writing-guide.json`, and the Word preview. Pre-outline research is saved separately in `research/report.json` and actual tool-reading records. Per-batch inputs and outputs for source-placement review are saved in `research-review-attempt-*.json`. An optional template is saved separately as frozen `template.docx` and `template-contract.json`; style examples are saved separately in `style-references/`, with descriptions and analysis records in `style/`. File purposes are written to `source_roles` in `metadata.json`, and all originals that are not factual sources are kept separate from the ordinary source directory.

After confirmation, `Store.create(..., directory_research=...)` freezes outline research and review results into the job's `inputs/directory-research/`. Body-writing tasks refer to original-text evidence from the same version and requirements corresponding to their own outline nodes, while continuing to read further as needed. Research summaries are not automatically promoted to global facts, nor do they bypass body verification. The body-writing job separately copies the template and validates its hash, checking during generation and final delivery that its structure and formatting have not been damaged. Call records include elapsed time, usage, and error diagnostics. Parsing, binding, and programmatic structural validation do not add model requests; outline research and semantic coverage review add actual main-model calls.

The CLI `generate` and direct job API also perform the same outline research and placement review before saving a formal plan when no confirmed plan exists but local materials or DOCX reference files are provided. A `partial` status or failed coverage repair does not proceed to body writing. They route model actions through `JobPlanningRuntime` to `Engine.call`; actual calls, format retries, and recovery all count toward the job's overall ledger and persistent stage allowance. They do not use separate, unaccounted Runtime requests or generate an additional Word preview for this purpose. Existing plans do not repeat outline research. When only remote retrieval is configured and no local materials exist, the original remote-retrieval boundaries are retained, without claiming that remote full text has been researched.
