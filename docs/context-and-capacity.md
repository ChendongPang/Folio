# Request Context and Capacity Design

> 中文版: [中文版](context-and-capacity.zh-CN.md)

Model-facing system prompts, tool descriptions, and task instructions are uniformly written in English; the prompt language does not determine the output language. `runtime/language.py` provides shared rules: document headings, body text, tables, and illustration text default to the language of the user's input, with an explicitly specified output language taking precedence. Multi-stage tasks retain the original user requirements as the basis for language selection, rather than switching to the language of English system instructions, reference materials, examples, or internal notes. For mixed Chinese-English input, the latest explicit language preference takes precedence; otherwise, use the language of the user's primary instructions. `ui_language` separately controls process-facing task titles, step explanations, status labels, and temporary placeholders; it does not change the confirmed document language. Original user text and reference materials are not translated in advance; protocol keys, enums, tool names, numbering, code, verbatim quotations, and labels that templates require to remain unchanged are preserved.

## Bounded Analysis of Style Examples

`style_analysis` uses readable Markdown input, and only this dedicated step may read the original example text; business context receives only style rules detached from the example's business facts. All extractable text is segmented in source order and packed according to the Token capacity of the complete request; a fixed sample count is not treated as representative of the entire text. The default input budget is 600,000 Tokens; for compatible Runtimes without Token measurement, `StyleAnalysisConfig.max_prompt_chars` uses a fallback of 600,000 characters. `max_total_chars` is unset by default, so analysis no longer stops early when cumulative analysis exceeds 2,000,000 characters; an explicitly configured value still enforces that resource quota. The entire analysis remains limited to 128 requests, 10,000 consecutive text segments, 1,200 characters per segment, and 90 seconds per call. Consecutive segmentation does not mean discarding the remaining source text, and call and time policies are not equivalent to the input window of a single request. The main job and total outline budget may still limit analysis earlier, and JobInput's `style_analysis` may narrow the configuration. Image input is separately constrained by a maximum of two pages per request and reserved model-window capacity; reserved image Tokens must not be misrepresented as text characters. Style rules are no longer truncated to 10K/16K characters when entering writing and layout context; the complete request is subject to unified capacity measurement.

The program schedules a finite set of batches covering all extractable text; an empty follow-up reading list returned by the model cannot terminate analysis early. Each batch's source text remains in the dedicated analysis audit, observations are retained across batches, and conclusions are checked dimension by dimension at the end. One targeted recheck is allowed for missing textual dimensions. Multi-batch text also undergoes one comprehensive synthesis check of all observations, verifying that every observation ID has been reviewed, merging duplicates, and delimiting the applicability of different writing styles across sections; the original batch observations are retained. The final synthesis request also includes measured native formatting, full-text structure, and length statistics, so missing source elements cannot be inferred from rule summaries alone. If the complete observations do not fit or synthesis validation fails, the analysis remains incomplete; it must not be truncated and then claimed to have been synthesized. `style.md` stores conclusions, evidence locations, text coverage, per-dimension completion status, and programmatic measurements. Only aspects that genuinely require page images may be listed as visual gaps; when capacity is insufficient, parsing fails, or the model does not finish, partial results and unread ranges are retained without claiming completion.

DOCX style reading includes the table of contents, cover, headers and footers, text boxes, footnotes, and endnotes; native formatting in these areas is observed separately and does not contaminate body-text defaults, and their source text does not enter business facts. Digital PDFs are measured using native fonts, color profiles, and drawing information; colors are converted using the ICC profiles actually embedded in the file, without guessing arbitrary color spaces. Original Word editing settings not preserved in the source file and visual properties requiring page images are described separately; images are not used to guess original editing parameters. Native page parsing failures must be marked as incomplete.

The analysis cache is bound to the complete source-file hash, extraction version, revision view, and budget; a semantically incomplete cache must not be reused as a successful analysis. After outline confirmation, the adopted style and source hash are frozen into the task. Resumption uses the confirmed result and verifies the hash, without charging again to analyze the same confirmed style. Layout values are validated by the program; model-generated prose descriptions of style cannot directly modify numeric Word parameters.

Chat `analyze_style` uses the same analyzer and cache, independently of outline planning. Intent detection selects an existing `style_reference` ID from the attachment list; the program validates the purpose and actual ID, while the model interprets filenames, prior discussion, and negation in context. Originals and audits are stored in `conversation-styles/<revision>/`, and successfully produced style results are bound to the conversation. The number of analysis requests is determined by full-text batching and completion checks; entry-point intent detection and the ordinary streamed response after analysis are billed separately and are not included in the style-analysis call count. Subsequent responses' `workflow.style_analysis` is limited to 6,000 characters, with space reserved by dimension, retaining filenames/IDs, text coverage, ten-dimensional rules, reliable measurements, and unconfirmed items. When too long, it explicitly points to `style.md` for the complete content and does not send the example source text, location index, or complete audit. Results that are missing, repurposed, have different hashes, or do not match the conversation do not enter the current context. Valid measurement-only results may answer questions about established formatting parameters, but must not be presented as completed semantic analysis.

Style summaries preserve the scope of each rule and provide extracted parameters such as fonts, font sizes, and spacing for body text, headings, and tables. Stage-specific style views for body writing, outline planning, and layout have no separate default character truncation; complete-request capacity applies. Chat summaries remain separately bounded, and complete analysis files are retained. Valid styles from independent analysis and the current outline are merged by attachment ID, and independent results override only results for the same example. Style-dependent assistant responses are bound to the source revision; subsequent intent detection and chat history also filter out outdated conclusions or those outside the current selection, preventing history text from bypassing version checks.

Core principle: retain complete materials and work records in the backend; each model request reads only the information needed to complete the current action. Business tasks and model requests are two distinct boundaries.

## Three-Layer Structure

1. **Backend working state**: WorkPlan, WorkState, original Evidence, generated body text, facts, model proposals, and complete check reports. Business dependencies, existing retrieval counts, the V2 research ledger, execution records, artifacts, and node versions are all maintained at this layer.
2. **Action working view**: `orchestration/context.py` and `requests.py` assemble context by action. `select_context` uses the currently enabled and validated decision model to assess relevance; when it is not enabled, the LLM is used. The program validates references and source types, then reads the selected source text.
3. **Actual request**: `RequestWorkflow.call_bounded()` schedules one or more calls according to input capacity and output workload, independently caches and validates each batch, and finally aggregates the results.

Agent handoffs and request batching are independent: `BusinessAssignment` freezes the task, input/outline versions, and dependency results; `BusinessResult` records saved nodes and their corresponding review versions; `RepairAssignment` constrains the original owner and expected version. Role handoffs are validated and archived by the program, do not add model requests, and do not use free-form chat among Agents as shared state.

Shared facts and dependency materials are read from a unified valid view: exclusion records apply only to the same issue and reviewed version, and fact availability is jointly determined by positive per-fact judgments, citations, and task versions that passed review. The original issue is retained for audit. Each task fixes a global fact snapshot at the start of its research version and also carries the original Evidence cited by that snapshot; shared facts outside explicit dependencies likewise cannot contain only IDs without source text. This iteration retains the snapshot strategy without adding fact subscriptions or real-time broadcasts. Explicit dependencies follow existing version invalidation and recheck handling; potential contradictions in non-dependent tasks are locally revised after final global review identifies them, without automatically cascading rewrites to all consumers.

Requirement context comes from the formal requirements and explicit revisions in `RequirementSnapshot`. Existing intent classification also labels items as `active/discussion/clarification/pending`; consultation does not enter writing requirements, and classification failures are not silently discarded. Original conversations and classification reasons remain in the backend. Answers to pending confirmation items are appended as a new version of user-provided grounds scoped to specific sections, while the outline and existing sources retain their original contract.

A “transaction approval” task may involve multiple batches of evidence reading, multiple rounds of gap completion, writing multiple nodes, and multiple review batches. Batching does not change node ownership or the dependency graph, or add retrieval rounds.

## What Each Action Reads

| Action | Read for this request | Retained in the backend but not automatically sent with the request |
| --- | --- | --- |
| Select dependency materials | Current business objective and one page of original candidate facts/proposals/risks | Other pages and materials from other tasks |
| Understand evidence | Task objective, node requirements, complete evidence for the current batch, and relevant dependency conclusions | Repeated old business records and raw import-debugging metadata |
| Pre-outline source research | User requirements, short file-ID list, complete tool history for the current research session, structural Markdown, source text already read, all research notes, unresolved questions, and reading progress; the history view is reduced only after the complete request exceeds capacity | Exact JSON indexes, long paths and hashes, unselected body text, and the complete audit ledger; old content removed from the view due to capacity remains retrievable |
| V2 autonomous research decisions | Current task and fixed fact snapshot, native tool definitions, complete tool history for the current research session, source text already read, all research notes, and evidence index; the history view is reduced only after the complete request exceeds capacity | Complete tool ledger, scripts/artifacts, and old content removed from the request due to capacity; persistent records are always retained |
| Verify derived evidence | Actual scripts, execution and environment summaries, all relevant source text, and results | Verification cannot be assumed without the source text; items remain unverified when verification capacity is exceeded |
| Decide next steps and generate queries | Business records, gaps, query history, and evidence ID index | Complete evidence passages already read |
| Complete gaps | Current gaps to fill, relevant original evidence, facts, existing proposals, and dependency constraints; batching occurs only when capacity is exceeded | Irrelevant evidence and facts accumulated across the entire task; materials are selected for the current batch's gaps, rather than merely splitting the number of gaps |
| Read materials for a single gap | Up to 8 complete sources per page, extracting concise constraints that the current gap must satisfy | Source text on other pages; constraints retain source references and source types, and unconfirmed risks and model proposals cannot be promoted to facts |
| Integrate supplementary content | One current supplement, current node body text, facts/constraints selected for that supplement, and necessary source text | Other supplementary proposals, neighboring section text, and materials accumulated across the entire task; local edits preserve untouched blocks |
| Write and repair | Current node, shared business records, selected original evidence, applicable proposals, and dependencies | Complete body text of other nodes in the same task and irrelevant retrieval slices |
| Extract facts | Current body text and cited evidence, producing at most twelve key consistency index entries | Other body text in the same task and dependency review reports; no sentence-by-sentence copying into multiple sets of fields |
| Local validation | Current body text, relevant sources, and facts; split into fact adjudication, body checks, and source coverage when necessary | Check work outside the current validation action |
| Business task review | Node body text, completion criteria, business records, and dependencies; checking responsibility coverage, process handoffs, and rules within the same scope | Accumulated evidence already independently validated for nodes; no repeated item-by-item evidence audit |
| Focused issue inspection | Current issue, original text of affected nodes, original supporting materials selected for that issue, and relevant constraints | Peer-level body text across the entire task and the complete business working snapshot |
| Cross-task review | Summaries of the current node group, facts, complete body blocks anchored to those facts, and model proposals | The entire document body; when blocks are too large, explicitly defer focused inspection and retain the complete index and archived source text |
| Visual verification of original materials | One complete original page image and proposed extracted text; batch OCR verification uses at most two pages | Independently verified visual evidence carries a signature; trustworthy local descriptions do not imply full-page coverage |

Research proceeds incrementally: “inspect structure, select the required range, read the complete selected sections.” The outline and business Agents' `fs_read` returns the full body text of the selected section and its subsections by default; multiple independent sections may be read in parallel in the same batch of native tool calls. Internal paragraphs, headings, and table rows are still used for location, but are no longer split into fixed 2,000-character chunks, nor limited by default to 20 entries per response or a maximum of 100. New source text is checked against complete-request capacity together with existing history, notes, and tool definitions, with space reserved for output; multiple tools share the remaining capacity rather than each occupying a separate input window. All results are returned in full when they fit; only when they do not fit are new results paginated, with exact continuation cursors and remaining ranges returned. Even a single long paragraph can resume from the previous character position; a partially read paragraph must not be marked as fully read. Explicit pagination parameters remain compatible with older calls.

Normal research retains complete tool history and all notes; old history must not be deleted merely to make room for new results in advance. The production Runtime's default input budget is 600,000 Tokens, and missing or null legacy configurations also use this default; when a smaller model window is known, the actual window must also be respected. Compatible Runtimes without Token measurement fall back to a complete-request character budget; 600,000 characters is no longer a separate fixed truncation layer for source-text reading. Research reuses capacity checks through `Engine.call` or the outline Runtime, with separate boundaries for tool counts, execution time, and output. Local business research allows at most three rounds, each with 12 tool steps by default; this is followed by at most two web-search rounds, then model completion if still insufficient. Pre-outline research starts with uploaded materials; verified and enabled search may address public questions affecting the outline, without inventing private information. File pagination is an operation within a round, not a separate round for each tool call. See [File Research and Execution Design](agent-research.md) for the complete mechanism.

The outline research setting `PlanningResearchLimits.max_evidence_chars` is unset by default; cumulative characters read across files and rounds no longer force research to end. Cumulative volume is limited only when the user explicitly sets this quota. Total volume across the entire research session and input capacity for each model request are managed separately and cannot substitute for each other.

Research messages are assembled uniformly by `research/transport.py`: requirements and lists use text/Markdown, all calls from the same response remain in one `assistant.tool_calls` message, and corresponding source text or errors are returned individually as `role=tool` messages with `tool_call_id`. Outline and business research allow at most 16 calls per batch and at most 4 concurrent independent read-only tools; results are saved in original call order, and actions involving shared state separate concurrency groups sequentially. One model response counts as one model call, while each tool counts separately against the tool quota. Actions are no longer placed in response text, and an action Schema is no longer duplicated in the system message. Native `tools` function definitions include parameter constraints; outline completion is submitted through a separate `finish` function and validated by the backend. Internal `ResearchStep` is used only for a single execution record.

The model reads materials using files, nodes, or page numbers, while notes and outline requirements use evidence IDs such as `E1`. After `finish.requirements` cites evidence actually sent, the program derives `selected_ranges`; the model no longer needs to fill in internal range IDs. Source versions, locations, and actual delivery remain subject to verification. Citations may refer to page segments already read without requiring the entire enclosing query range to be read; `complete=false` and unread summaries are retained. `fs.inspect` remains a navigation tool; when body text has already been located and read, the absence of a structural browsing record alone does not block a conclusion.

Tool-stream failures record the specific `protocol_issue`, HTTP status, finish marker, whether `[DONE]` has been received, the number of tools and characters received, the event sequence number of the failed fragment, and the parameter JSON error position. Multiple tool calls are no longer considered a protocol error in themselves; the receiver checks indexes, IDs, function names, and arguments separately. `finish_reason=missing` means no finish marker had been received when reception stopped; it does not infer whether the upstream service would subsequently send one. Outline research writes safe diagnostics to `research/events/research_NNN-error.json`, saves failed output separately to `research/failed_outputs/research_NNN.json`, and links it to the original request with the same number; business research continues to use `contexts/failed_outputs`. Private output includes assembled tool calls and the latest four groups of tool fragments; only tool fields are extracted, long fragments retain their beginning and end, and the archive is limited to 32,000 characters in total with truncation marked. Request headers, raw error bodies, and model reasoning content are not saved. Pages and ordinary logs use only fixed reason enums and safe metrics, without displaying tool source text. These diagnostics do not add failure retries.

Budgets are calculated from all messages actually sent, historical tool-call arguments, all research notes, and native tools definitions; content-generation tasks additionally account for a separate output Schema. The number of source-text characters read is only a pagination starting point, not the complete request size. The former two thresholds—first checking whether indented JSON fits, then counting the actual compact request—have been unified into the same transport view. Normal-sized structures are provided in one pass, while body text or exceptionally large structures are paginated according to the remaining budget. Lists, structures, and summarized results are not automatically removed from history merely because they have already been sent, and the latest tool results cannot be silently removed in their entirety. The view is compressed only after the complete request actually exceeds capacity, prioritizing removal of old source text that already has attributed summaries; where summaries are absent, the same research model first organizes the materials already provided. If necessary, notes and navigable task fields are then reduced, and the latest results are explicitly segmented while preserving exact continuation positions. If even the minimum necessary context cannot fit, the incomplete status is explicitly retained. Original history and complete notes are always persisted.

Capacity checks for multi-call batches include all arguments and results in the batch. When some old source text leaves the current view, its call IDs still receive explicit archived-placeholder results, so no calls are left unpaired; placeholders contain no source text and do not add to the evidence provided. Concurrent body-text reads in outline research share the reserved remaining evidence quota; concurrency does not change the input context or total evidence limit.

Reading records distinguish “extracted by the program” from “provided with a model request.” Complete execution results, actual sent views, and delivery records are saved separately. Outline validation does not accept evidence that exists only in the backend and has not been sent, nor count partially sent source text as a fully read range. Business `model_deliveries` records the observed request number, text hash, character count provided, and completeness. Historical continuation reads retrieve content by readable-text position, avoiding repeated nesting of result JSON. A sending record does not prove model comprehension, but it allows verification of which materials the model received.

Outline and business `ResearchMemory` store delivery records, incremental research notes, and source evidence separately. The model submits entries with `evidence_ids` through the native tool parameter `research_notes`; `request_ids` are no longer required. The program verifies that the evidence was actually sent and recovers batch associations from the ledger. Only cited evidence is marked as summarized, without also covering other source text in the same batch; model inferences and unrelated explanations are clearly distinguished from statements in the materials. Without updates, existing notes remain unchanged; only specified entries are revised, and repeated calls are idempotent. Outline notes are saved with that version's research report, while business notes are restored from conversation checkpoints. Outline replanning starts new research and does not inherit completion status directly from an old report. `research.md` is exported only from authoritative state and is not a separate fact store. Complete backend audits, native `tool_call_id` pairings, and historical request numbers remain retained; simplifying fields filled in by the model does not change time or call budgets.

Notes must not be evicted chronologically together with ordinary old chat records. Normal requests carry all notes; only after the complete request exceeds the current capacity are they reduced to a topic index and currently relevant entries, with a paginated reading entry point provided. Notes not currently displayed have not been deleted, and unresolved questions cannot automatically close merely because the view has been shortened. Pending summarization status controls whether source text may be compressed; evidence that has been read but not used does not independently block outline `finish` merely because it has no notes. Historical navigation provides files, locations, and evidence IDs together, and rechecks use exact ranges and `review_reason` to express their purpose. When there is no new supporting material, valid note, or gap progress for consecutive steps, research converges according to existing rules. Capacity checks distinguish service counts, local estimates, and character fallbacks, without adding a separate summarization model or real-time fact synchronization layer.

When research decisions exceed capacity, facts, dependencies, responsibilities, and similar content may be replaced with readable navigation references, while the complete snapshot remains unchanged; tools can retrieve historical results and all evidence. Coverage review partitions complete section responsibilities and paginates outline navigation without trimming formal requirements. If a single formal responsibility still exceeds capacity, it remains explicitly unverified. Research, repairs, and restarts must not clear the existing total model-call ledger.

Final Jev page scoring and automatic optimization have been removed from the generation workflow, and per-page scoring and rescoring calls are no longer reserved for them. Pre-generated illustrations still have an independent soft quota and core-call reserve, counted atomically by Store before each model attempt; final required illustrations remain subject to the main quota.

Body generation and repair both first select materials according to the node's subject, path, and writing requirements; relevance filtering is not skipped even when the input fits within capacity. Sufficient capacity does not mean all materials for the same task apply to the current section. The program forcibly retains project sources the current node must cover and original supporting materials for selected facts; the selection step cannot remove them. Source text and necessary citations are sent unchanged, while original versions and complete metadata remain traceable in the backend.

Revisions must also retain all source text already cited in `current.blocks`. These materials are not scored again and must not be removed during capacity-driven refinement; the absence of new relevant materials does not mean the original body text lacks support. The output citation allowlist is generated from the closure of actual source text; missing sources cannot be bypassed by relaxing validation or including IDs alone.

Shared records' `conflicts/open_questions/summary/terminology` and `known_gaps` also undergo the same relevance filtering, preventing them from bypassing material selection and becoming a supplementary-writing checklist for every section. For writing and single-section validation, `work_task` carries only location information; complete objectives, questions, and completion criteria remain in research records and `review_work`. Single-section validation retains facts and conflicts to check claims actually made in the text, without treating the entire set of unresolved questions as coverage obligations for that section. Fact-extraction output references may target only non-`model_proposal` blocks; without such blocks, no fact index is generated. The complete body text is still used for summaries, entities, and independent validation.

Facts already selected from dependency tasks are not sent again through `global_facts`. Deduplication requires matching node, version, and complete fact content; different versions, sources, or conflicting content are retained, and the backend global fact index is unchanged.

Upstream check reports are not directly treated as downstream business facts. `dependency_catalog()` creates attributed references for facts, proposals, and risks, and the model selects relevant items. Facts/proposals are read as source text; relevant risks produce `risk_briefs` with `source_refs`, explicitly marked as `unresolved_risk`. Irrelevant formatting information, extraction diagnostics, and duplicate reports remain in the backend. Repeated selections of the same reference are deduplicated as a set; the program still rejects unknown references, cross-page references, selections that treat risk as fact, and risk summaries without references.

## Manage Input and Output Separately

The LLM path for material selection in `select_context` packs pages according to the Token capacity of the complete request, with a default input budget of 600,000 Tokens, no longer intersected with the old 32,000-character threshold. An independent decision service or compatible Runtime without Token measurement uses 600,000 characters as the pagination fallback; this is a Unicode character count and must not be treated as an exact service Token count. Each time the paginator attempts to add a candidate, it calculates the complete request, including LLM prompts/Schema or the decision service's state and questions; it does not first pack raw materials and then uniformly deduct one page's extra overhead from every page. An oversized individual item is still split losslessly under its original reference, not truncated to fit.

Primary-LLM selection is no longer limited to 24 candidates per batch; all independent decision models use at most 24 judgments per batch. Browser and API text limits for user chat and confirmation responses are unified at 600,000 characters for entry-point reception and storage; the complete context is still measured in Tokens before being sent to the model, and the character quota must not be treated as 600,000 Tokens.

Intent recognition and ordinary chat retain all valid history, no longer deleting older content in advance based on the latest 8/16 messages or 18,000 characters. Directly streamed ordinary chat also checks local Token estimates for complete messages and the known model window; exceeding capacity returns an explicit capacity error instead of silently deleting history to send the request. Tasks that have already measured the complete request reuse that result, avoiding replacement of an accurate service count with a local estimate.

When the decision model is enabled, material-selection capacity overruns, capacity-driven refinement, and API errors are not handed off to the primary LLM; an unavailable API causes an explicit failure while preserving existing results. The existing fallback strategy for intent classification remains unchanged; next-step actions are determined directly by native function calls from the primary LLM. The independent decision route for material selection does not change the use of the primary LLM for body generation, fact verification, or focused inspection.

`select_reads` passes prepared real subpages individually to `_call`; each page is independently archived, validated, and cached, while concurrency remains subject to the existing model-call limit. Direct runtime calls have the same pagination protection. Oversized individual items retain the same `context_ref`, with `fragment` recording fragment information. Jev retains the complete source only if the relevance probability of any fragment is strictly greater than 0.8; a value equal to 0.8 is not selected, and an invalid score causes rejection of the current selection result. The LLM path retains complete sources according to its valid selections and does not interpret a missing fragment as meaning the entire material has no content. Subpage results are deduplicated by original reference, and subsequent writing still reads the original full text. If shared questions/necessary source metadata are themselves too large to split safely, an explicit error is raised rather than truncating instructions.

Jev selection of evidence, facts, proposals, and risks uniformly requires a relevance probability strictly greater than 0.8, replacing the low-threshold “retain if uncertain” policy. In usage, decision_relevance records probability, accepted, and threshold for each item, with fragments aggregated by original reference. A selection-policy version change invalidates old permissive selection caches without affecting caches of generated body text.

When risks are selected across multiple tasks, `apply_selection` restores each owner's complete original risks and source_refs; attaching a mixed summary to every task is prohibited. Short single-task summaries retain the existing contract, and original-text reading markers continue to restore complete risks. The decision model selects only risk references and is not asked to generate long summaries. Short risks may retain their original text directly; long or cross-fragment risks use explicit original-text reading markers, allowing `apply_selection` to load the corresponding complete risks into `risk_briefs.originals` while preserving the `unresolved_risk` property. Negative constraints must not be dropped to satisfy the 1200-character summary limit, and no additional LLM call is made to rewrite risks.

Audit usage includes `selection_provider`, `selection_batches`, `selection_max_input_characters`, and `selection_character_limit`; the decision service separately counts `decision_calls`, while LLM subpages retain per-page usage. The material-selection policy version enters only the cache identity of `select_context` and does not invalidate other writing or review results.

If the LLM service actually rejects input capacity or truncates output, the selector continues bisecting the rejected page up to 3 levels, with at most 15 attempts per initial page, rather than increasing the output quota and resending the same input. Already fragmented sources may be split further, retaining parent-fragment information. If any subpage is incomplete, partial selections cannot be treated as a complete result. `selection_page_audit` records the sizes, source references, and statuses of actual attempts, and `selection_attempts` records the attempt count. These internal subpages after service-side rejection still belong to the original cache task; HTTP call counts cannot be inferred directly from the number of parent tasks.

Supported services obtain `max_model_len` through `/v1/models` and count actual messages and tools definitions through `/tokenize`, passing the same `enable_thinking` and generation prompt settings used for generation. `max_input_tokens` defaults to 600,000 and may be explicitly overridden; `context_window` is the combined input and output window, and `tokenizer_encoding` may specify a local encoding (`o200k_base` or `cl100k_base`) when the service cannot count. When switching models, APIs, or access methods, an input budget not explicitly specified returns to the system default of 600,000, without inheriting the previous model's window and encoding. Null values in legacy configuration are also normalized on load, without requiring the credentials file to be rewritten.

Capacity conditions:

```text
Measured input tokens <= max_input_tokens (default 600,000)
Measured input tokens + reserved output tokens for the current action + 512 tokens of headroom <= model context window (when known)
```

The window comes from service metadata or explicit configuration; when both are available, the smaller value is used, rather than being fixed to a particular deployment's 32,768 Tokens. All LLM actions uniformly use `max_tokens`, defaulting to 128,000 Tokens, and connection tests use the same quota; output is no longer independently reduced for actions such as intent detection, material selection, research, and evidence understanding. `planning_max_tokens` for outline planning and correction is unset by default and overrides the value only when explicitly supplied by the user. The settings interface, configuration files, and actual requests use the same default, with no application-level output cap of 65,536. The output quota is an allowed maximum, not a requirement to fill it; for services that count reasoning and body text together, both share this quota.

600,000 is the application's default input budget, not a claim that every model has this capacity. Each connection must discover or configure its own context window; another model’s settings do not establish this capability. When the service advertises or configuration explicitly specifies a smaller window, actual input, reserved output, and headroom must fit that window; when window information is unavailable, it remains unknown rather than fabricating model capabilities.

A single model call for a long request defaults to a maximum of 900 seconds, using `Limits.call_timeout_seconds`; job configuration is passed into the Runtime through the asynchronous task scope and is no longer cut short by an additional fixed 180-second transport timeout. Explicitly configured shorter or longer per-call limits are honored, and ordinary chat streams outside the job coordinator also default to 900 seconds. Generation streams no longer have a separate 60-second no-data read deadline (`read=None` is used only for that HTTP request); reasoning periods without SSE responses are controlled by the same total deadline. Short connection, write, and connection-pool timeouts remain, without changing timeouts on the shared client or capacity probes. The entire job remains subject to `run_timeout_seconds` (default 7200 seconds); explicitly shorter deadlines for independent stages such as style analysis still apply. An output of 128,000 Tokens is an allowed quota, not a guarantee of completion before the deadline; timeouts retain existing diagnostics and checkpoints without accepting incomplete results.

Body writing, repair, validation, and review still respect the service's actual total window. Only when measurement shows that the remaining window cannot accommodate the user's full output quota may output for the current request be adjusted to the actual remaining space. When the model window is unknown or sufficient, the full default quota of 128,000 Tokens is sent. Model requests and capacity checks use the same quota, and audits record both `requested_output_tokens` and actual `output_tokens`, without modifying user configuration or truncating input. Other actions adjust input batches or report capacity errors when the actual window is insufficient; on an explicit context-limit error from the service, output may be reduced according to the returned capacity before retrying. If review output is actually truncated, batch recovery continues to be used, and incomplete results are not accepted.

When the service cannot count, an explicit encoding uses `local_tokenizer_estimate`; without an explicit encoding, the default `o200k_base` is used and marked as `default_tokenizer_estimate`. Estimates are written to `estimated_input_tokens`, while `input_tokens`, which represents a service count, remains empty; the default encoding must not be claimed to equal the provider's actual tokenizer. Production research no longer uses `character_fallback`. File pagination for tool results and character fallback values for compatible Runtimes are not equivalent to the entire model's context window.

Temporary connection errors, rate limits, or server failures from the counting API do not mean “counting unsupported.” These errors allow at most 4 requests (the initial attempt plus 3 retries, with 2/4/8-second delays); if they persist, the checkpoint is retained and `capacity_unavailable` is recorded, without permanently disabling token measurement or allowing potentially oversized requests through a character threshold. Actual token counts are used again after recovery.

Gap completion, evidence understanding, and local fact adjudication no longer force batching merely because there are more than 3 items, 20 entries, or 24 entries; they first assess the real or estimated Token capacity of the complete request. Input fitting within capacity still does not guarantee output completion: batchable actions for which the model actually returns `length` change request boundaries and discard incomplete JSON instead of repeatedly retrying unchanged. Repeated-paragraph protection and bounded corrections for writing remain.

## Image Requests

Source research, visual interpretation verification, and style analysis may still use actual images through `supports_image_input`. Context stores image paths, locations, and file hashes; the runtime verifies files and constructs actual multimodal input before sending, while request audits do not duplicate Base64 images. Image Token estimates use conservative reserves, and text tokenizer results must not be treated as accurate image measurements.

Image input supports source research, visual extraction verification, and style analysis. Normal document generation does not perform per-page aesthetic scoring.

## Batch Merging and Validation

- Evidence reading: batch whole evidence items and aggregate all attributed facts, without allowing the last batch to overwrite earlier ones. Facts receive stable IDs based on their statements and sources and are saved after deduplication; aggregate records are not subject to the single-output limit of 50 facts.
- Gap completion: first split by gap, then select complete evidence, local facts, global facts, and existing proposals for the gaps in the current batch. Original evidence for selected local facts is forcibly retained in the request, and relevant conflicts are not dropped. Proposals generated in earlier batches may be read by later batches to avoid conflicts; after merging, verify that each gap_id appears exactly once, retaining target nodes and model-proposal attributes. If the batch still exceeds capacity, split it further and reselect materials instead of repeatedly carrying all accumulated materials for the entire task.
- A single gap still exceeds capacity: use `read_gap_materials` to read all selected sources page by page, with each page outputting business constraints carrying `source_refs` and `source_kind`, then pass only those constraints to the supplementary-writing step. Retain source text, reading results, and caches for every page; the program rejects unknown references and source-type changes. Reading notes are not written to the evidence store or confirmed facts, and supplementary-writing results remain model proposals. Body writing, fact extraction, and validation continue to use original evidence rather than replacing verification sources with these notes. If merged notes still exceed capacity, explicitly retain a checkpoint and fail, rather than compressing indefinitely or pretending completion.
- Supplementary content integration: `supplement_integration.py` selects materials separately for each supplement, and `integrate_supplement` returns only updates/remove_block_ids/resolved_pending_items; the program preserves unedited body blocks and illustrations. New model proposals must not masquerade as supported facts; only questions answered through retrieval use original-text citations through the evidence_refresh branch. The interface displays “Integrating supplementary content into ‘Section Title’.”
- Integration capacity fallback: when the measured request is too large or the service returns a capacity/output-truncation error, `supplement_conflicts.py` splits selected materials and proposals, checking conflicts within the same scope batch by batch. Every page must cover all proposals in the current batch; conflicts must provide verbatim quotations verifiable against the source text, and applicable key constraints are retained even when materials are compatible. Oversized individual items are split losslessly by original reference and position; uncertain cross-fragment relationships cannot be treated as passed. After all constraints are aggregated, corrections are made uniformly for at most two rounds, each rechecking all selected materials, without allowing later pages to overwrite earlier conclusions. Necessary source quotations and corrected proposals are returned for local integration. Once fallback verification passes, the supplementary body text must reuse the verified proposal verbatim, preventing the final body-insertion call from changing its business meaning. After adopting a corrected proposal, backend proposal content is updated under the task lock using a comparison against the original version, invalidating review caches while preserving section ownership, sibling proposals, and retrieval counts from concurrent updates. If the concurrent version has changed, it is not overwritten and remains pending confirmation. Subsequent body validation still uses complete original evidence. Each section shares a limit of 32 actual model calls and a 120-second deadline, with at most 4 concurrent batches; cache hits are not billed again, and cancellation drains child requests. If verification is incomplete, constraints conflict, the budget is exhausted, or the final minimal edit still exceeds capacity, the current body text is retained and a pending-confirmation item is recorded. Partial results do not pass, and this item's capacity error does not interrupt delivery of the entire document.
- Fact extraction: split by complete body blocks; when merging, rename local claim_id values and preserve block_ids and evidence_ids.
- Local validation: small requests may complete in one call; large requests/output truncation are split into fact adjudication, body-block checks, and item-by-item project-source coverage. Fact adjudication retains body text anchored to the current batch's claims and cited source text; body checks cover source text block by block. Recursive batching narrows body text and evidence together while preserving required project sources for that range. Legacy claims without anchors conservatively retain the parent page's body text, and whole-table citations are retained when table rows lack per-row source mappings. Project-source coverage reads the complete body text of the current node. Finally, verify that each fact has exactly one judgment, and save per-fact judgments and verification-completion status. Issues are deduplicated by specific content and location; different issues with the same key must not overwrite each other.
- Business task review: control the scale of all materials through the issue-based reading process below, rather than falling back to splitting body text while retaining the entire materials package.
- Cross-task review: retain adjacent windows and add groups based on facts sharing the same scope/subject/attribute, common topics, and explicit business dependencies. Each group contains at most the configured width of nodes, and broad entities no longer create fully connected pairs. Different unchanged values for the same fact key are compared together within the width; exceeding the width produces one focused-inspection candidate for the complete fact group, including candidate assertions or assertions not declared single-valued, without expanding all value pairs. Already covered wide fact groups do not generate duplicate rule candidates. If focused inspection cannot fully accommodate the evidence relationships, the item remains pending confirmation. Relationships covered by an existing group reuse the same check request. Requests retain complete body blocks anchored to the current batch's facts; when too large, `comparison_originals_deferred_to_drill_down=true` may be set, retaining all fact and proposal indexes and leaving source text for focused inspection, rather than trimming large blocks and claiming they were read. If still over capacity, facts/proposals are split further. Candidates must locate actual blocks in two sections and return shared conditions and reasons for incompatibility; they must not falsely report omissions in the full document merely because other parts are absent from the current batch.

### Read Original Materials by Issue

The entry point is `orchestration/focused_review.py`. When complete materials for task review and focused issue inspection fit within the measured model window, they are passed directly to the model, without forcing selection merely because optional materials exceed 32,000 characters. Materials are selected for the current concern only when the complete request exceeds capacity. Source text explicitly cited by the body or concern, along with task completion criteria, is always mandatory and is not passed through the selector only to be forcibly added back. If selected source text fits, it is still checked directly without generating additional reading notes. This does not change the rule that body generation and repair always select materials by node first.

1. **Determine review focus**: `plan_review` receives only task questions, completion criteria, and the outline index. General comprehensive review retains per-node checks; `task_consistency` review for production tasks reuses node validation already performed rather than creating the same single-node checks again. The LLM proposes at most 8 cross-node issues with actual business relationships, each linked to at most 4 nodes, without automatically enumerating all node pairs.
2. **Select materials by issue**: the selection objective includes the specific issue and the target nodes' titles, paths, and writing requirements. Facts, evidence, proposals, and risks enter paginated selection as independent materials. Current node body text, outline requirements, and completion criteria are mandatory; original supporting materials cited by body text or selected facts are forcibly retained, as are supplementary proposals for relevant nodes. Irrelevant materials remain in the backend.
3. **Read source text**: when selected source text fits together within the window, check it directly without first generating notes. If it still exceeds capacity, read body text, requirements, evidence, facts to verify, model proposals, and risks by source type, with the output Schema restricting source types to the current page's type. Body text and requirements are read item by item and must return cited notes; other sources are limited to 8 items per page. Compatibility fragmentation defaults to a 600,000-character boundary, transmitting oversized individual items completely as contiguous fragments of canonical JSON, preserving the parent source and character range without dropping tails, table rows, or negative conditions.
4. **Aggregate candidate issues**: each page produces at most 8 notes, each at most 400 characters, preserving source references and types. Aggregation retains the original body text of nodes involved in the current issue and replaces only supporting materials with attributed reading notes, without duplicating the entire task's materials package. If the original body text still exceeds capacity, use body-reading notes with node ownership; this mode can identify only candidate conflicts and cannot infer omissions in the original text. Facts and proposals are not promoted to evidence by being written into notes; absence from notes does not prove omission or lack of support in the body text.
5. **Return to source text for adjudication**: candidate issues enter the existing `drill_down`. Its context selects original materials for the specific issue, retaining affected node body text and necessary cited supporting materials without attaching all peer-level body text from the entire task. If the issue cannot be adjudicated from original supporting materials, it remains pending confirmation; reading notes do not authorize rewriting.

If a single page's output is too long, split the page; if output for a single item is still truncated, allow at most one concise-output attempt with at most two notes, keeping input source text unchanged. Partial JSON is not accepted. If the final notes still cannot fit, record an explicit “review incomplete” pending-confirmation item rather than treating the review as passed. Source records, reading pages, and results from each stage are traceable and reusable.

Issue checks within the same task reuse the `max_parallel_reviews` concurrency limit; materials within each issue are read sequentially, and subpages do not create additional concurrency pools. On exceptions or cancellation, wait for in-flight coroutines to exit.

Different slices obtained over three retrieval rounds continue to accumulate and remain saved; `evidence_chars` is used for a single material-reading/retrieval budget, no longer as the cumulative evidence limit for the entire task.

For other actions that do not yet support further splitting, if the minimum safe unit together with necessary context still exceeds capacity, they explicitly fail and retain a checkpoint; they do not truncate source text or accept partial JSON. The issue-review process above supports range-based reading of original materials, but this does not mean every action can handle arbitrarily large individual materials.

## Recovery and Audit

For failed tasks, `usage.diagnostics` records only permitted numbers and enums: time to first response/body text, characters received, finish reason, token usage, and similar metrics. These may be recovered through the exception-cause chain of an outer timeout, avoiding an empty `TimeoutError` as the only remaining information. Model body text received but not completed is saved separately in local `contexts/failed_outputs/`, retaining at most 32,000 characters from the beginning and end and noting whether it was truncated. It does not enter error messages, the interface, or usage, and is not adopted as body text. HTTP/SSE service error bodies and reasoning content are not written to this body-text audit; these local records remain in the business data directory and are not entered into the database.

When resuming at the review stage with all nodes saved, proceed directly to review without restarting completed tasks' writing/research loops; dependency-version changes are still checked at the task-review entry point. Complete backend dependency snapshots remain in use for research versions and review validity checks; changing the model working view does not reset an old task's three-round retrieval count. Saved nodes are skipped, and successful model subrequests continue to use the existing `tasks` cache. The call entry point validates successful caches first and measures capacity only on a cache miss, so usable local results are not blocked by temporary capacity-service failures. Parent requests already recorded as exceeding capacity or having truncated output may proceed directly to batching without consuming the same call again.

When a task that has completed research discovers changes to upstream versions, facts, or issue lists during review, only the review cache is invalidated; knowledge retrieval is not automatically restarted, and existing supplementary-writing records are not cleared. Review reads the latest dependencies and the original evidence corresponding to their supported facts; if body text needs revision, an explicit repair action handles it. Tasks with unfinished research still resume from research checkpoints.

For program-confirmed missing specified table headers, repair uses only saved materials and explicitly states column names and the requirement to preserve existing content, without retrieving again because of the missing headers. The same condition is checked immediately after repair. If it is still unmet, the candidate body text is not adopted and no downstream review loop is triggered; the failed candidate is saved in `contexts/rejected_repairs`, the original body text and issue list are preserved, and a `needs_confirmation` draft is output. This status does not indicate review passage.

Exhaustion of the model-call budget and insufficient input capacity are handled separately; supported service exceptions/timeouts may also trigger a complete-body fallback. When these interruptions occur and all outline nodes have been saved, stop new model requests, retain the current body text, original concerns, and an explicit “checks incomplete” record, set `review_passed=false`, and export `needs_confirmation`. Existing valid illustrations may be reused, unfinished illustrations retain missing-image markers, and layout uses safe formatting. If the body text is incomplete, the task still fails and retains a checkpoint. This fallback only prevents complete body text from becoming unavailable for download due to interrupted review; it does not constitute technical acceptance or disguise timeouts, missing illustrations, or unperformed validation as completion. Pause/cancellation, storage failures, and program errors do not use this fallback; export failures are still reported. Users may explicitly provide answers or retry without filling in responses, and set a new round quota of 1–10000 calls, defaulting to 200; cumulative calls are not reset and have a maximum of 100000, and repeated requests do not authorize the quota again. See [Pending-Confirmation Resumption](confirmation-and-resume.md).

Complete model results, usage, and errors remain in SQLite `tasks`/`decisions`. Material selection is also cached as an independent task; candidates in selection requests allow risk sources to be reconstructed. Ordinary logs and the UI do not display API keys or reasoning text. Native-tool `reasoning_content` may be retained in private checkpoints for subsequent tool-history protocol continuation.

Focused review returns a fixed, complete structure: whether the issue is confirmed, an explanation, whether human confirmation is required, affected nodes, and repair instructions must all be returned. The program then checks the target nodes and instructions when automatic repair is required, preventing conditional branch constraints from causing the model to return only some fields. Temporary references in repair instructions are converted back to backend references before persistence and remapped according to the context of the next request; temporary identifiers must not be reused across requests.

[review_scope](../src/folio/orchestration/review_scope.py) provides generation, validation, review, and focused review with the actual responsibilities, parent-child relationships, `figure_policy`, and saved subfigure locations of the currently relevant nodes. Focused review using this contract must also return structured `repair_targets` and must not add duplicate figures to parent sections that have delegated drawing responsibilities, in violation of that division of responsibilities. For concerns about the sources, conflicts, and omissions of located factual blocks, `applicability_checks` must check the subject of the body text, the subject of the source, the role of the material, and its applicability, and provide quotations traceable to the original text. Treating vendor product capabilities, performance tests, or external references as project requirements also requires explicit evidence that the project has adopted them. Neither matching numeric values nor the mere presence of a citation is sufficient to establish applicability; uncertain conclusions remain pending confirmation. The program validates locations and references, while semantic judgment still relies on the model. Fields remain compatible with older archives, and requirements are imposed dynamically according to the applicable scope of the current request, without additional model calls.

Newly generated and revised `record_only_pending` entries are narrowed through [pending_metadata](../src/folio/runtime/pending_metadata.py) to specific personnel and document metadata, with actual blank table cells located. Generic “remarks,” business date constraints, and functional requirements must not be disguised as metadata such as document dates to bypass follow-up checks. Older archives remain readable. These scope and source safeguards have offline regression coverage. A subsequent full end-to-end run failed during material selection, so there is not yet a real final-output acceptance conclusion for its latter stages.

If factual paragraphs in this section match an entire paragraph or a long complete sentence in a known supplemental-writing plan verbatim, source candidates are raised by body block and character range. Focused review must retain the original text of the named plan and its citation evidence. A valid identifier does not prove that a citation supports the content. Authentic evidence obtained later may support the same design, so candidates may be rejected; entire paragraphs must not automatically be marked red. Focused review must first verify responsibilities against node definitions and must not add requirements to a section with a different responsibility merely because a candidate claims that “scope is missing.”

Review process events use an optional `review` field compatible with the existing `work_update.text`, are persisted to SQLite, and are written to `jobs/<job_id>/review.jsonl` and service logs. Each round has an independent `round_id`, and each group or issue has a `unit_id`. The frontend uses these two fields to update the same record. Expanding it shows the sections and versions involved, the actual grouping reason (adjacency, specific facts, a shared topic, or business dependencies), candidate issues, focused-review rationale, elapsed time, and call details. Grouping reasons are also included in the model's `review_topics`, with instructions to compare only statements under the same applicable conditions and not to treat synonymous wording or omitted repeated explanations as contradictions.

Call counting uses a scope propagated with asynchronous tasks. Split subrequests and material selection in preparation for focused review are also attributed to their respective check items; concurrent groups are isolated from one another. The round summary records `model_calls`, `cache_hits`, and `failed_calls` separately, with additional per-action statistics. Reuse is counted only after a cache entry has been successfully validated. A call is counted only when it actually acquires a model concurrency slot and enters the runtime; retries within the engine are counted individually. These are model task call counts. Retries internal to the underlying service or HTTP subcalls must be examined alongside the existing usage data and cannot be treated directly as HTTP request counts.

Focused-review logs distinguish four cases: the model finds the issue substantiated, unsubstantiated, or indeterminate, or hard-rule checks still fail. Errors and cancellations do not produce a passing conclusion. If the model finds an issue unsubstantiated but structural or source validation still fails, it remains explicitly pending confirmation. Focused-review conclusions are logged separately from subsequent saved revisions; “the model confirmed the concern” must not be displayed as “already fixed.” The cross-section check summary for the round also records the original candidate count, deduplication count, excluded count, and remaining concerns. Reused results are explicitly marked, rather than using repeated group-completion progress to imply another round of model calls.

## Regression Validation

`tests/test_agent_collaboration.py` covers version and ownership rejection in task/repair handoffs, synchronization of facts and dependencies when handling false positives, preventing dismissed issues from promoting negative/unknown/suggested facts, original-text closure for non-dependency global facts, risk ownership, and retention of issues with the same key.

`tests/test_request_context.py` covers: semantic selection and original-text retention for large volumes of upstream reports; all facts across batches and recovery after interruption; precise gap coverage; division of responsibilities in local validation and avoiding replay after parent failure; all cross-node combinations; mandatory retention of project sources during writing; the distinction between token and character thresholds; fallback when the service does not support counting; and preventing risk references from being promoted to facts.

Cross-task review creates bounded groups by topic while retaining adjacent windows, specific facts, and dependencies. It does not pair items merely because both contain model suggestions, nor does it create fully connected groups for broad entities. Top-level groups default to 16-way concurrency (`limits.max_parallel_reviews`). The primary model allows at most 32 concurrent calls during business task execution and 16 during subsequent stages such as review, with a combined cross-stage cap of 32 enforced by the primary service. Verified and enabled decision services share a separate limit of 16 concurrent calls per job. The combined main-model and decision-service limit is 48. Identical requests reuse the cache. On concurrent failure/cancellation, all in-flight coroutines are awaited until they exit. The interface displays actual progress and details; completion of a group check does not mean every concern has passed.

`tests/test_review_optimization.py` covers linear growth in broad-entity grouping, reuse of existing window coverage, distant facts within the same scope, dependencies with asymmetric lengths, precise deduplication and issue-key collisions, as well as counterexamples involving different values across windows, duplicate copies, different applicable scopes, and the first representative from the same task. At the local and task review entry points, `citation_review` currently requires missing-citation allegations to locate actual factual blocks and does not accept errors reported solely because red-text additions lack citations. Mixed facts, source conflicts, and content omissions still require independent focused review and must not be categorically exempted based on keywords or red-text labels.

`tests/test_focused_review.py` covers failure modes caused by oversized whole-task materials, checking based on actual relationships rather than pairing all nodes, mandatory retention of citation evidence, lossless splitting of original materials, preventing source-type promotion, ensuring the body text is read in full, preventing incomplete reviews from passing, and cache reuse on reruns.

The filtering objective during writing is based on the current `section`; `work_task` is not treated as the scope of the current request. When capacity is exceeded, business-record facts, global facts, and original text are filtered together, while dependency facts are filtered according to the current node. Mandatory project materials, the original text of selected facts, and existing constraints are retained. Repair instructions participate in filtering, and complete sources remain in the request archive. This boundary applies to both `generate` and `repair`.

### Cross-Section Statement and Scope Checks

Candidates from cross-section `review` must include actual `block_refs` from both sections, shared applicable conditions in `comparison_scope`, and a specific incompatibility in `incompatibility`. The Schema and result validation enforce actual locations, while semantic validity remains the responsibility of independent focused review. Negations and exceptions within body blocks, such as “virtual/real” and “same day/next day,” must not be truncated to fit capacity limits. Even when reading the original text is explicitly deferred, the original index must be retained, and candidates must not be treated as final judgments.

Insufficient sourcing, internal contradictions, and omissions within a single section are handled by `validate` and `review_work`; the cross-section step does not repeat these two types of audit. Legitimate differences between distinct business objects, or the same statement appearing in different sections, should not generate conflicts. The interface continues to retain every candidate, focused-review conclusion, and source, without locally deleting concerns based on red text or keywords.
