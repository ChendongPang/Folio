# Business Agent File Research and Execution Design

> 中文版: [中文版](agent-research.zh-CN.md)

This document describes shared source preprocessing, pre-outline research, V2 file research, isolated execution, derived evidence, and recovery mechanisms. Outlines, body nodes, business tasks, global fact snapshots, review, and Word delivery continue to use the existing architecture.

## Overall Collaboration

At the coordination layer, the LLM still proposes a WorkPlan, which `BusinessCoordinator` validates and executes, managing the DAG, concurrency, cancellation, and delivery. The Business Agent independently determines its research path; the scheduler does not mandate reading Word before Excel. Each body node retains a single owner. Tools can access only the current task's inputs and artifacts and cannot directly modify the body, task state, or shared facts.

Style examples are processed through a separate `style_analysis` task, counted separately from the three local business research rounds and two web-search rounds. The program supplies all extractable text in batches based on request capacity, retains cross-batch observations, and checks whether each textual dimension has an evidence-backed conclusion or an explicit statement that it was not observed. It does not stop early merely because the model has not requested additional reading. Directly readable DOCX/PDF formatting properties are measured programmatically; only information that genuinely requires page images may be listed as a visual gap. When image input is supported, bounded samples of original pages are still used. `structure.md` describes the original document's structure, while `style.md` describes ten dimensions, text coverage, supporting evidence, and unconfirmed items; the two are not mixed.

Original style documents do not enter the Business Agent's source catalog, `Evidence`, shared facts, or retrieval library. Research, business understanding, node generation, and repair receive only the style summary appropriate to their stage: outlines reference organization and headings; body text references tone, level of detail, chart explanations, and expression patterns; Word generation and proofreading reference verified, effective formatting parameters. All summaries come from the same frozen `profile.json`, rather than each Agent independently inferring its own style. Style rules cannot override hard template constraints or generate nonexistent business facts, and numerical statistics do not become chapter or word-count quotas.

```text
Upload validation, shared native parsing cache, and per-file structure.json / structure.md
  → Source snapshot preprocessing: manifest + authoritative structure JSON / derived Markdown + content
  → Pre-outline research by the main LLM: browse Manifest → inspect structure, read source text, and read further as needed
  → Source-backed outline requirements, actual reading records, and unresolved questions
  → Complete outline planning → structure/template checks → review of source requirement placement in the outline and bounded repair
  → Sufficient research, clear scope, and passed checks → user confirms outline
  → WorkPlan, task dependencies, and fixed global fact snapshot
  → Autonomous research by the Business Agent
      Shared structural navigation → read source text by chapter, Sheet, page range, etc.
      Each research_step → file tools / original images / Python / conversion / verification → observations
      At most 3 local rounds, at most 12 tool steps per round; stop early when evidence is sufficient for writing
      understand_work distinguishes executable verification actions from items requiring user input
      Public-information verification actions available → at most 2 web-search rounds, reassessed each round
      No executable verification actions remain → prepare body text; retain gaps as pending confirmation, explicitly label permitted design recommendations as model suggestions
  → understand_work → write by node → extraction and source validation
  → Business review, detailed cross-chapter review, and local repair
  → Visual Agent, Word, format protection, and final pagination
```

Pre-outline research and body research share the source index and file-reading capabilities, moving research before outline generation. The program no longer treats the first 8 headings and first 12,000 characters of each file as the outline model's entire source material. The main LLM selects files and ranges to read based on the user's goals, within call, tool, time, and context limits. In the report, `ready` means the current outline research is sufficient; `partial` retains unread content, budget gaps, or scope gaps; and `no_sources` means there are no ordinary source materials. Without source materials, planning may still follow user requirements and an optional template, but must not claim to have researched nonexistent attachments. A draft may be displayed when the status is `partial` or the scope remains unclear, but confirmation to proceed to body writing is blocked.

Outline `finish` can use `local_research_actions` to explicitly identify local verification actions that remain executable: a nonempty value continues research; an explicitly empty value, together with passed checks on actual reading, citations, and source selection, allows the current round to end while retaining scope questions requiring user input. Older responses without this field retain the previous research-continuation logic. Scoring, technical, and other sections that remain readable cannot automatically be treated as fully researched because of a single `finish`. Missing company information, pricing, or personnel credentials generally remain body-writing gaps and do not block the outline structure; genuinely unresolved scope still retains `blocking_gaps` and `partial`.

The source requirement placement review reads actual evidence and the complete outline, then determines item by item whether each requirement is explicitly addressed in the heading or writing instructions of an actual body node. It does not require one chapter per requirement, nor permit broad headings to conceal omitted specific requirements; exclusions require a scope-based justification. When there are many requirements, all are checked in batches without truncating any individual requirement's source text; gaps that exceed the budget are explicitly retained. The program validates requirements, evidence, node IDs, and exactly one disposition per requirement. If omissions still fail after bounded repair, the outline remains a draft. Structural validity and sufficient actual reading are independent conditions; outline checks do not replace body acceptance.

The outline research report is saved in the outline version's `research/report.json`, together with actual tool actions, source versions, locations, and source evidence. Each coverage-review batch's inputs, results, usage, duration, and failure/cancellation status are saved separately in `research-review-attempt-*.json`. After confirmation, `Store.create(..., directory_research=...)` freezes these records into the job's `inputs/directory-research/`. Body tasks use the corresponding node requirements and same-version source evidence, continuing deeper research as needed. Research summaries and template examples do not automatically become global facts; shared facts still follow the existing body extraction and verification path. Pre-outline research does not consume the quota of a body task that has not yet been created; the two stages retain separate bounded budgets and reading records.

When writing reveals gaps, the current business task's remaining follow-up research rounds are used. Ordinary repair, interruption recovery, and new research versions cannot reset the three local rounds or two online rounds. Three rounds means three bounded research rounds, not three file-tool calls. Aggregate tool, model, and time limits may still terminate research early. The existing `understand_work` also returns `research_actions`: `local_sources` identifies local ranges that still need reading or checking, while `public_web` identifies questions that can be publicly verified. Only corresponding actions trigger further retrieval. Gaps involving company names, pricing, certificates, internal environments, and solution decisions remain in `open_questions`; files are not repeatedly reread or the web searched when no usable evidence exists. If online access is unavailable, its status is recorded, and information pending confirmation continues to the body and completion workflows without inventing project facts. For older checkpoints that submitted `finish` but reentered local research because of missing information, existing evidence is first evaluated once under the new rules. Fact snapshots remain fixed by research version; no live broadcast or fact subscriptions are added. Registering a research artifact or successfully executing a script does not automatically qualify it as a shared fact.

New GUI jobs and LLM CLI generation enable `JobInput.research`; historical jobs without research capabilities configured and offline demos retain the original research path. `research_step` and `verify_derivation` use the main model through the existing `Engine.call`, obtaining caching, model budgets, capacity checks, and auditing. Jev/luna retain their limited decision-making responsibilities, such as intent and source selection. Intent has seven categories: `chat/analyze/analyze_style/generate/resume_generation/requirements/clarify`; the decision model is not asked to generate Python.

## Tool Protocol

All model-initiated tool actions use the native Chat Completions `tools` / `tool_calls` protocol. Requests declare the functions permitted in the current stage and use `tool_choice="required"`. Outline and business research enable `parallel_tool_calls=true`, supporting at most 16 calls in one response; other single-decision tasks still require one call. Streaming responses are assembled separately by call index, allowing interleaved fragments. After all fragments arrive, the system checks that indices are contiguous, IDs are nonempty and unique, and function names and arguments are valid before execution begins. Responses must complete with `finish_reason="tool_calls"`. Ordinary response text is not treated as a command; custom action JSON and “take only the first JSON” tolerance are no longer accepted.

Independent file browsing, search, and reading operations in the same batch execute with at most 4-way concurrency. Operations that depend on a preceding result must wait for the next model request. Actions involving shared state, such as scripts, dependency installation, OCR registration, and artifact modification, execute in their original order. These actions also separate the read-only groups before and after them to avoid conflicts over shared temporary files, evidence, or registration state. Result presentation, short source IDs, and research records are committed in call order, not renumbered by completion order. `finish` must be submitted alone. If mixed with other calls in the same batch, the entire batch returns errors for the corresponding IDs without executing any tools, requiring the model to decide again.

A single model response is saved as one `assistant.tool_calls` message containing the complete list. Each execution result is returned through `role="tool"` with the matching `tool_call_id`. One tool's failure does not discard other tools' results; every accepted call has a corresponding result or explicit error. Body text and structure are still supplied as source text/Markdown and sent only once. If capacity limits move some results out of context, an archive note retains the batch calls and corresponding IDs, leaving no calls without returned results and not counting placeholders as delivered source text. Excessively long latest results are explicitly paginated. Errors and `finish` calls that fail validation also return corresponding tool results. Before execution, business research persistently saves the entire batch of pending operations, then registers each operation's execution identity and quota usage. Restarts reuse completed results. Previously executed history from older versions may be referenced as archived material without fabricating native call IDs. New requests use the new protocol's cache identity, while persisted pending operations retain their original quota usage and execution identity to avoid duplicate execution after restart.

Native function names use `fs_list`, `fs_inspect`, `fs_read`, and so on; the backend tool ledger retains existing identifiers such as `fs.read`. `ResearchStep` is only an internal execution record that retains actual native calls for auditing and recovery, not a protocol the model must generate in text. Function arguments directly contain the actual reading/execution parameters and a public `summary`, with optional `research_notes` increments; business research may also include missing source materials. No separate small fixed quotas are imposed on note text, note count, or evidence citation count; these follow actual request capacity. If `topic` is missing, a navigation heading is generated only from the first line of that entry's existing text, without adding facts. Historical `notes` are compatibility supplements only; default empty values cannot overwrite existing notes. Requirements in outline `finish` cite source evidence such as `E1` through `evidence_ids`. The program derives `selected_ranges` from evidence and actual reading records; the model no longer fills it in. The backend still validates citations, ranges, source selection, and unparsed content item by item; function calls cannot bypass business checks. If the model returns only ordinary text, that response is included within the existing retry allowance, with an explicit notice that no tools were executed and no conclusions saved, and a request to call a currently available function. The text itself is not converted into executable actions.

Migration covers outline research, business file/Python/artifact operations, next-step actions in the legacy workflow, source retrieval, Tavily search, and follow-up reading for coverage review. Intent classification, relevance scoring, outline and body content, and style analysis remain content/decision results with their existing result validation. Tool definitions are not duplicated in system prompts and are separately included in the complete request budget. Function arguments use ordinary parameter Schema (`strict=false`) with strict local validation, without an additional `response_format`. If the API does not return native calls, it reports an explicit error rather than silently falling back to text actions. For protocol details, see [OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling).

| Tool | Actual capabilities |
| --- | --- |
| `fs.list` | Lists short file IDs, names, and types for the model; full paths, versions, and status remain in the backend; can also inspect existing artifact directories |
| `fs.inspect` | Directly supplies persisted structure Markdown: actual heading trees, Sheets/header candidates/ranges, PDF bookmarks/page numbers, and slide titles; selects body content through short node IDs |
| `fs.search` | Paginated local lexical search or existing knowledge-base retrieval; the coordinator advances to the online stage after local research ends |
| `fs.read` | Reads source text and execution artifacts by `node_id`, location, Sheet/cell, or page number; `scope=history/evidence/context` supports paginated queries of complete tool history, all evidence, and fixed context |
| `fs.view` | Views original PDF/image pages or normalized local regions; Office files must be bound to controlled conversion execution records; uses a research model with image input enabled |
| `sandbox.exec` | Isolated Python, fixed Office/OCR conversions, and requests for allowlisted dependencies |
| `artifact.save` | Registers and verifies derived results, reuses valid artifacts, and builds coverage inventories; `extraction.verify` requests independent visual verification, 1–2 pages per batch |
| `research.save` | Saves research notes only for source text already read; native function name is `research_save`; no new sources are read during synthesis |
| `finish` | Ends the current research round while retaining all unresolved questions; does not mean the full document has been approved |

File paths must belong to the current source snapshot; absolute paths, parent-directory traversal, and symbolic links are rejected. Paginated results provide `total/offset/next_offset/complete/truncated`. Reading the complete paginated range and the original file being fully readable are different states; the latter is represented separately by `source_complete`. A search proves only that relevant content was found, not that all clauses have been covered.

## Shared Research Memory

Outline and business research reuse `ResearchMemory`, with each outline version or business task maintaining its own records. Compatible follow-up research sessions for the same business task inherit existing results without adding real-time fact synchronization across tasks. Source text may leave the current model context, but the corresponding reading results and provenance must remain. Memory has three layers:

| Layer | Stored content | Write responsibility |
| --- | --- | --- |
| Reading and delivery records | Source versions, files and page/text ranges, request IDs, character ranges actually supplied, evidence IDs, and completeness | Recorded by the program from actual tool results and model requests |
| Research notes | Relevant findings, implications for the outline or task, inferences, irrelevance explanations, and unresolved questions | Model submits increments; program validates and saves them |
| Source evidence | Normalized source text, original locations, complete tool outputs, and source versions | Fully retained by the program and reread by citation or range |

The next native tool call may carry `research_notes` for the preceding batch of material, saving notes before executing the next step. Normal research does not require an extra summarization-model call after every batch read. When capacity pressure requires synthesis first, `memory_checkpoint_required` restricts the currently allowed tools to `research_save`; the same research model saves notes before continuing. Such synthesis requests still count toward the original call allowance. Each entry includes `topic`, `text`, `kind`, `evidence_ids`, and `unresolved`; revisions to existing entries provide `note_id`. The model no longer fills in `request_ids`. `kind` distinguishes `source_statement` (a statement in the source), `inference` (model inference), and `no_relevance` (the cited source text is irrelevant to the current task). The latter may be registered when irrelevant source text needs to leave context; conclusions must not be fabricated to satisfy synthesis requirements.

The program accepts evidence citations only for material actually delivered in the current research version; successful backend extraction is not a substitute for delivery. The program reconstructs batch associations from `evidence_ids` and the delivery ledger. Synthesis status covers only the cited evidence, does not mark other uncited source text in the same batch as complete, and does not prove semantic completeness of the synthesis. “Synthesized” status does not mean source coverage or content acceptance has passed; undelivered tails remain pending. Notes are appended by entry, and explicit revisions preserve prior entry history. Duplicate submissions are handled idempotently by call and content identity. Omitting `research_notes`, passing an empty list, or defaulting `notes` does not clear existing records. If a revised entry omits `unresolved`, its existing questions are retained; only an explicit empty list clears that entry's questions. Notes, delivery records, and pending-synthesis state are saved with the outline report or business checkpoint. `research.md` is generated from the same records for human reading, not maintained as a second independently editable authoritative state. Request IDs in historical notes and ledgers remain for traceability, but the model is no longer required to maintain these internal IDs.

Normal context retains user requirements, template constraints, relevant fixed facts, all tool exchanges from the current research, reading progress, all notes, and unresolved questions. Previously sent manifests and structures, synthesized source text, or notes exceeding a fixed length are not reasons to reduce history prematurely. The complete request, including tool definitions, is checked first. The view is reduced only when it exceeds the current model's input capacity, prioritizing removal of older source text that already has provenance-backed synthesis. If synthesis is missing, the same research model first organizes the material already supplied. A synthesis request may focus on one batch while other batches remain pending; they are not marked complete merely because they are not displayed this time. Only an actual capacity overrun triggers a note-topic index; complete entries can be retrieved through `fs_read(scope='context', field='research_notes')`, and the complete history index through `field='research_history'`. The complete raw records always remain in the backend; undisplayed content must not be misreported as deleted or resolved. Research notes neither replace body citation verification nor prove that unmentioned clauses do not exist.

When body writing discovers new `writing_gaps`, or a new research session is created after the user explicitly continues, the new session inherits old notes, native tool history, evidence, delivery records, and reading progress if it is still the same business task and the task responsibilities, chapters, dependencies, instructions, tool policy, sources, and global fact snapshot are consistent. The first follow-up research request includes this memory and the new gaps. If compatibility validation fails, old archives are retained without carrying old conclusions into the new research scope. Older sessions may inherit after validation against the existing assignment and session identity.

Compatible follow-up research uses the original task workspace, preserving evidence IDs, pagination cursors, OCR, and artifact verification records. Each session's task input is saved separately in `context/sessions/<round_id>/assignment.json`. Only knowledge and history are inherited—not completion status, stop status, consecutive no-progress counts, or `pending_*` operations. Resuming an existing session always takes precedence over inheritance; unfinished tool batches still follow the original recovery rules. Tool and model quotas remain ledger-managed; inheriting old results incurs no new charges and does not automatically grant new quota. A newly authorized session receives readback permission only for inherited history record IDs, not access to other business tasks or the entire previous authorization scope.

History entries include file names, actual page numbers or locations, evidence IDs, and synthesis status, rather than bare `request_id` values. Rereading a previously read range should use `review_reason` to explain the specific verification question. The program permits reasonable rechecking; if there is persistently no new evidence, useful notes, or progress on gaps, the current round ends under the existing rules and retains the gaps. Continuing pagination is a new range and is not treated as rereading merely because it is in the same file. Reasonable rechecking also cannot remove existing call and time limits.

Research is complete when the evidence and gaps required for the current task are sufficiently clear; it does not require the full text of all attachments to appear simultaneously in the final request. Pending-synthesis status governs whether source text can be compressed; evidence that was read but not used and has no notes does not by itself block outline `finish`. The outline must still submit requirements backed by actual, same-version, delivered source text, while retaining unread content and actual requirement coverage checks. Inferences in notes, business content from style examples, and unverified OCR or calculation results do not thereby enter global facts. Confirmed facts continue to use the existing extraction, review, and fixed-snapshot mechanisms.

## Shared Source Preprocessing and Reading

`prepare_uploaded_source` in `research/source_index.py` reuses the parsed object from `cached_source` during upload validation, generating `structure.json` and human/model-readable `structure.md` beside the uploaded original. Before a source snapshot enters planning or research, `SourceIndex` generates a unified manifest and structure/body copies bound to that snapshot version; underlying reading is handled by `research/formats.py`. These are all local deterministic operations: they do not call models or generate business conclusions. Ordinary chat, outline planning, LocalKnowledge, and Workspace reuse the same version rather than independently reopening and reparsing Office/PDF files. Chat supplies excerpts within structure and body budgets, rather than reading PDFs, Excel files, or images as UTF-8 text. All entry points share `source-cache/` under the data directory. Cache keys include the complete file SHA-256, format, and reader version; identical content can still be reused after renaming or copying to a new snapshot. Changes to content or reader version trigger reparsing. Corrupt caches are rebuilt, and originals are reparsed only when no valid parsed object is available for reuse.

The `sources.index/` beside each source snapshot contains `manifest.json`, `structures/<file_id>.json`, `structures/<file_id>.md`, and a separate `content/`. JSON is the authoritative index for precise locations, versions, ranges, and parsing status. Markdown is generated deterministically from JSON and describes internal structure only, without parsing warnings, research recommendations, or business summaries. Older indexes missing Markdown generate it directly from existing JSON without reparsing originals. The manifest records file versions, parsing status, and cache hashes; body content preserves normalized original text blocks. Cache writes use file locks and atomic replacement, and reads check original versions and cache integrity. Moving an outline revision preserves both originals and indexes. Business tasks share same-version native structure and body text, while keeping their own research notes, evidence selections, and OCR results separately. Legacy direct `LocalKnowledge(directory)` calls remain read-only; the engine explicitly passes the shared cache path.

Internal structure nodes retain `node_id`, `parent_id`, heading level, and body ranges. The model uses short IDs such as file `F1` and node `N005`, with `N000` representing the full text. Mappings are bound to the current snapshot; real file paths, long node IDs, and hashes need not reappear in every request. Reading a parent chapter includes its subchapters, ending at the next heading of the same or higher level. `fs.inspect` does not open the entire body cache or generate Evidence. Normally sized structures are returned in full rather than truncated to 50 nodes by default. Pagination by complete nodes occurs only when the full text exceeds the current budget or `limit` is explicitly requested; the budget includes headings and continuation links. If a single node cannot fit, an explicit error is returned rather than an empty page that can never advance. Consecutive pages in PDFs without bookmarks may be merged into page ranges, while the backend retains separate locations for every page.

Structure browsing is the recommended progressive research approach, not a mandatory step before every body read. Files, nodes, and page numbers locate content; evidence IDs such as `E1` are used for citations in notes and conclusions. The program manages internal reading ranges and request IDs. Body text that has been precisely located and read does not block outline completion merely because no structure-browsing record exists; actual source versions and delivery are still verified. An outline may cite delivered page/text ranges without requiring the entire containing query range to be read. Range completeness and unread status remain accurate; a partial citation is not counted as whole-chapter coverage.

`fs_read(file=..., node=...)` returns the complete selected chapter and subchapters by default. The model may call `fs_read` multiple times in parallel to select multiple chapters. The program retrieves the body text concurrently, then checks their combined capacity using the actual request formed from these results and the existing context. Fixed 2,000-character slices, the default 20 entries, and the 100-entry cap are removed. Pagination occurs only when selected content exceeds the remaining request capacity, rather than allocating the entire input window again for each tool. Source blocks retain original locations. Pagination state uses block index `offset` and in-block `character_offset`, encapsulated in a persisted cursor; `read_segments` records character ranges actually returned. When only part of a paragraph is returned, its unread tail is not counted as fully covered, and reading can resume accurately after recovery. Tool outputs also describe the remaining range; explicit legacy pagination parameters remain supported.

Task-local `.workspace/navigation-references.json` persistently stores short node IDs: initial IDs follow the native index, and newly added OCR pages only append IDs. Even if a later-added page 1 precedes an already recognized page 2, the latter's existing ID does not change. Removed node IDs are not reassigned, and restarts restore the original mapping. The source index's static Markdown is unaffected by task OCR.

`fs.read` returns source text, short source IDs, and continuation links, preserving necessary structure such as headings and table rows without having another model rewrite or summarize the body. The backend generates Evidence IDs from the original file version, original location, and character fragment, then resolves model-side short references to their original identities for validation. Reading relevant content includes actual parsing status; structure Markdown itself does not mix in these warnings. New structural navigation does not rewrite source text or source identity, and the model cannot self-declare source identity.

Program extraction results and results actually received by the model are tracked separately. Outline research counts only source text actually sent with a request as delivered ranges. `finish` may cite delivered evidence, but cannot claim that undelivered pages have been read. Business research also saves `model_deliveries`, recording observations supplied in each request, text digest hashes, character counts, and completeness; the tool ledger still retains complete execution results. The latest tool result cannot be silently dropped in its entirety because wrapper overhead increases its size. Excessively long results are explicitly segmented and provide a history continuation link. Here, “delivered” is an auditable transmission fact, not a claim that the model understood all content.

| Format | Native reading | Explicit boundaries |
| --- | --- | --- |
| DOCX | Body order, actual heading hierarchy, table rows, revision reading view, and comment metadata | Images/text boxes are marked unread and require isolated conversion and OCR |
| MD/TXT | UTF-8 text and original line numbers; Markdown ATX/Setext heading hierarchy | Code-block content is not treated as headings; non-UTF-8 files are explicitly rejected |
| XLSX | Sheets, headers from the first nonempty row, cells and limited merge information, hidden/empty Sheets, formulas, and cached values | Header selection rules are explicitly marked and do not mean business fields have been understood; reading does not calculate formulas, and cached values are unverified |
| PDF | Native text, actual bookmark hierarchy, page numbers, and block locations | Without bookmarks, navigation uses actual page numbers only, without inferring chapters; bookmarked chapters are read by page, and boundary pages may contain adjacent chapters; textless pages are marked `needs_ocr`, and encrypted PDFs are explicitly rejected |
| PPTX | Slide text, tables, and notes | Unread visual content such as images and charts requires conversion |
| PNG/JPEG/TIFF/WebP | Dimensions, page count, and format validity | Image text may be read through isolated OCR or independently verified visual extraction, not guessed from file names |

File-byte-size limits are no longer imposed on uploads, original parsing, or style-original reading; the total decompressed-byte limit for Office files has also been removed. The GUI still allows at most 200 files per session. Readers retain independent content-range limits, including 5000 Office entries, 8 million text characters per file, 100,000 text blocks, 2000 PDF/PPTX pages, and 500,000 cells in an expanded Excel range. Exceeding these ranges explicitly requires splitting the material; truncated results are not presented as complete sources. Removing original-file size limits does not change model context quotas, image input rules, or tool pagination. Pre-outline research obtains source navigation from the same-version Manifest, then uses tools to inspect complete structures and actual source text through pagination. Short catalogs and chat excerpts are for navigation only and cannot replace pre-outline research. PDFs without bookmarks retain a no-outline notice; page-number labels cannot masquerade as chapters. Complete page navigation is provided by research tools.

If a native file cannot be parsed, the index retains `unreadable` and the reason. If the format is valid but contains unread ranges such as scanned pages or images, structure and gaps are retained; cache completion is not interpreted as the Agent having read everything. Every readback checks the original version; changed materials require a new research version. Excel range reads generate exact character fragments from original rows that remain traceable to the original cell rows. Local lexical retrieval continues to use the same Evidence blocks; this structure index is not a Wiki or vector RAG.

PDF pages containing both native text and images/vector drawings still record unread visual ranges; headings or page numbers do not prove whole-page completeness. Excel drawings retain unread status under their owning Sheet. Only objects explicitly marked as decorative may be directly excluded; business importance is not inferred from image size. Completeness is assessed for the pages, chapters, or Sheets selected in the current operation, so unread pages outside the scope do not block completed ranges.

File SHA-256 values are reused within a bounded in-process cache keyed by device, inode, size, mtime_ns, and ctime_ns. Modifying a file triggers revalidation even if mtime is restored; the first access after a process restart still requires hashing. Lexical indexes use a bounded cache, and each task's Evidence is independently copied. Source preparation runs in a thread and counts toward the job's total timeout. Cancellation takes effect between files, chunks, and lock waits; the job lock is released only after the current parsing/atomic write completes.

## Task Directories and Containers

```text
<data directory>/
├── source-cache/                    Parsed objects reused by content, format, and reader version
├── directory-drafts/<revision>/
│   ├── sources/                     Originals for the outline version
│   ├── sources.index/               Source index saved with the outline version
│   ├── research/report.json         Pre-outline research, source evidence, and scope gaps
│   ├── research/research.md         Provenance-backed research notes exported from the same report
│   └── research-review-attempt-*.json  Per-batch inputs and outputs for source requirement placement review
└── jobs/<job>/research/
    ├── sources/                     Snapshot of research originals
    ├── sources.index/
    │   ├── manifest.json            File versions, status, and cache references
    │   ├── structures/              Precise JSON indexes and same-name Markdown navigation
    │   └── content/                 Same-version normalized body text
    ├── ledger.sqlite                Tool-call and quota ledger
    └── tasks/<task>/<initial_round>/ Compatible follow-up research sessions share this workspace
        ├── research.md              Readable notes exported from current persistent research memory
        ├── context/                 Current assignment and fact snapshot, mounted read-only
        │   └── sessions/<round>/assignment.json  Task input for each session
        ├── scripts/                 Workspace script entry points
        ├── scratch/                 Temporary files for the current task
        ├── artifacts/<execution>/   Separate artifacts for each execution
        ├── .workspace/              Task-local OCR/conversion reading cache
        └── .research/               Host-managed script, execution, and artifact records
```

Task-local OCR body text and structure are saved as the same generation, followed by an atomic update of the commit pointer. New files not committed before interruption are not recovered as successful results. After checking original hashes and extraction identities, legacy `v2.1/v2.2` OCR caches are migrated to current native body text plus existing OCR blocks, preserving already cited OCR evidence identities. The shared original-file cache is not migrated or rewritten by OCR.

Directories persist, while containers are allocated per execution. Source directories, context, and previously committed artifacts are mounted read-only; the current execution can write only to its own temporary and artifact directories. Model code does not run in host Python and cannot access the Docker socket, host secrets, or other task directories. Missing Docker/images produce explicit tool errors, with no fallback to host execution.

Containers disable networking, use a read-only root filesystem and non-root user, drop capabilities, prohibit privilege escalation, and limit CPU, memory, process count, file size, output, and execution time. Cancellation and recovery clean up the corresponding containers. Input and output hashes are checked again after completion; abnormal artifacts cannot be registered as complete. An output file does not become trusted merely because a file with that name exists.

Build four environments:

```bash
docker build --target base -t folio-research-base:v2 -f docker/research/Dockerfile .
docker build --target data -t folio-research-data:v2 -f docker/research/Dockerfile .
docker build --target office -t folio-research-office:v2 -f docker/research/Dockerfile .
docker build --target ocr -t folio-research-ocr:v2 -f docker/research/Dockerfile .
```

`base` provides basic file and spreadsheet libraries; `data` adds pandas/NumPy/SciPy; `office` provides LibreOffice and PDF tools; and `ocr` adds Chinese and English Tesseract. Each execution records the final image's immutable digest. Modifying an image under the same name prevents reuse of results that depend on the old digest.

Operational policy comes from `settings/research.json` in the data directory, or a path specified by `FOLIO_RESEARCH_CONFIG`. Common settings include `profile_images`, `max_concurrent`, `cpu_limit`, `memory_mb`, `pids_limit`, `max_output_bytes`, and dependency policy. User materials and model actions cannot modify these settings.

Dynamic dependencies must match package names, pinned versions, and wheel SHA-256 values in the operational allowlist, with an explicit dependency closure. Only the fixed installer may use controlled networking; model Python always remains offline, and sources are not mounted during installation. Dependency caches are bound to the image digest and complete locked set, rejecting arbitrary URLs, mutable versions, and unapproved dependencies. Image builds and approved dependency downloads may access the network but do not call paid models.

## Source, Calculation, and OCR Verification

Ordinary source evidence contains the source file, version, location, and text. Registering a calculated artifact must additionally bind the actual execution record, input evidence, script hash, image and dependency digests, output file hash, calculation method, and business claim. Artifact records have backend signatures; the model cannot change verification status by filling in `passed=true`.

`verify_derivation` independently reads original ranges, the actual script, and results, checking source validity, calculation, and business interpretation separately. The model must confirm all three before the backend records verification. Incomplete materials, source text exceeding verification capacity, or an unclear interpretation leave the result unverified. A valid body citation proves only that the source exists; subsequent extraction, local validation, and global review still run.

For example, “there are 58 required fields” requires more than successful execution: verification must also check whether row count was mistaken for field count, whether duplicates were removed, whether the correct Sheet was selected, and how empty values and formula caches were handled.

Fixed conversions include `office_pdf`, `office_recalculate`, `ocr`, and `office_ocr`. The latter performs Office→PDF→OCR in the same trusted script, taking the page count from the actual conversion result while remaining bound to the original Office file hash. OCR text is registered as `extracted:` evidence, retaining the execution ID, image digest, and page numbers, with `requires_extraction_review` set. This version does not treat key text as confirmed merely because OCR returned normally. OCR evidence that has not been independently verified blocks shared facts and publication, though it may remain in drafts pending confirmation; explicit user answers continue through the existing confirmation workflow.

OCR may specify at most 20 original page numbers, for example processing only `[180]` from a 300-page document. Without explicit page selection, whole-document processing remains limited to 100 pages. Office OCR saves the actual converted PDF for viewing and verification; original page images are bound to the original file, conversion script, and execution artifact hashes. `verify_extraction` independently compares each page's complete native/OCR text with the original image, checking values, negations, table relationships, and flow arrows. After it passes, code signs an immutable receipt bound to the original file version, extraction blocks, page numbers, original-image hash, and review request identity. OCR in verified ranges may participate in coverage and subsequent fact validation; source or extracted-content changes invalidate it. Blank/decorative pages also require explicit verification. Viewing an original image is not approval, and the Business Agent cannot self-declare a pass. When native Office chapters cannot be reliably mapped to rendered pages, no correspondence is inferred; whole-document Office visual gaps are cleared only after all rendered pages are verified.

For information that OCR cannot fully express, such as flow arrows, branch return locations, and relationships between prototype controls, the Business Agent may view the original image and request `artifact.save(operation="visual.extract", path, page, text)`. Independent `verify_visual_extraction` checks the description sentence by sentence against the complete original page; only a pass generates signed `visual:` evidence. “Description is trustworthy” and “covers the entire page” are assessed separately; a partially trustworthy description cannot clear a whole page's unread status. A complete visual interpretation may serve as that page's coverage entry; incorrect or ambiguous descriptions are not registered as evidence. Verified visual evidence may be cited across tasks, but another task's receipt cannot silently close the current task's scope coverage.

OCR additions update only the current task's reading overlay and do not write back to the public `SourceIndex`. PDF extracted text remains readable by actual page numbers and bookmark ranges. Office conversion pages are navigated as separate page nodes; when they cannot be reliably mapped to original Word chapters, Sheets, or slides, OCR text is not forcibly assigned to those native nodes. Shared parsing caches do not cause unverified recognition results to be mixed across tasks.

For requirements covering all fields/clauses, research begins with an independent check of formal requirements, actual chapter responsibilities, and the source catalog to establish a coverage scope contract. The backend enforces creation of required inventories. Ranges that cannot be located or read remain pending confirmation; the research Agent cannot bypass this by omitting inventory creation. Chapters without full-coverage requirements acquire no such obligation. CoverageManager enumerates entries from the complete parsed range and finally rechecks each entry against actual body citations. Multiple actual character fragments of long source text must collectively cover the entire entry; one missing fragment still means incomplete coverage. “Not applicable” declarations require independent review before exclusion. Unread scanned pages, visual ranges, truncated content, and unprocessed entries cannot be offset by search results or model summaries.

Scope review receives the complete file list and structures by default, paginating only when actual capacity is insufficient and retaining continuation navigation. Structure requests may locate content by heading, `node_id`, or `locator_prefix`, with support for explicitly equivalent `structure_node` / `structure_id` aliases. Missing file IDs are filled in only for a single file or a unique location; ambiguity and out-of-range requests still produce errors. Each responsibility partition receives at most three reviews, and large tasks may be divided into at most eight responsibility partitions, each retaining the complete formal requirements. Independently confirmed coverage obligations are not cleared by omissions in subsequent navigation responses or review failures. Scope contracts are reused for the same formal responsibilities and source snapshot, with coverage records inherited across research rounds. Ordinary text repair, writing gaps, or newly read evidence do not trigger a whole-scope rereview. Review runs again when formal responsibilities, the source snapshot, or newly explicit scope changes. Once scope is confirmed, selected source text and independently verified OCR/visual content are re-enumerated. When an automatic inventory for the same formal scope is updated, the old automatic inventory leaves the current checks but retains its signed history; manually registered scopes always remain. Online sources or model suggestions cannot fabricate complete coverage of original files.

Failed derivation verification or verification-capacity overruns are persisted as separate issues and cannot be cleared by an empty gap list at research completion. An issue can be cleared only when the same artifact later passes verification, or an independent review confirms that the actual body does not use the claim and that other original evidence satisfies the task responsibility. Changes to body or source versions require rechecking.

## Budgets, Recovery, and Acceptance

Local research allows at most three rounds, with 12 tool steps per round by default (`max_steps_per_round`). Each business task is also subject to total limits of 50 tool operations, 60 research steps, and 40 research-model calls, with 600 cumulative script seconds and at most 120 seconds per execution, while reserving model quota for subsequent body writing and review. Research-model requests and failed retries register both research quota and the document-wide ledger in the same Store transaction; cache hits are not charged. At most two web-search rounds follow, with each online attempt persistently registered before the request. Query generation and evidence interpretation remain subject to the document-wide model ledger. Tool counts, research rounds, and time are counted independently by the persistent ledger. Ordinary retries and repairs do not clear accumulated usage. Explicit user answers that resume execution provide a new bounded local research allowance and enter a new research-version identity; existing online attempts retain their cumulative count.

When one model response contains multiple tools, the model call counts once, while tool operations and within-round steps are counted individually. Concurrency does not increase the total available quota. Cancellation waits for in-flight tools to exit and preserves registered results before releasing the workspace or resuming the next round.

All research and business actions use a default output allowance of 128,000 tokens; steps such as evidence interpretation no longer receive separately reduced output limits. A single file-tool result allows 600,000 characters by default, with progressive pagination. Cumulative source-text limits `max_evidence_chars` for outline research and `max_total_chars` for style analysis have no hard limit by default and take effect only when numeric values are explicitly configured. Every request remains subject to the complete-context budget of 600,000 tokens and the service's actual window; call, round, and time quotas continue to apply independently.

Current research includes complete tool history and all notes by default. The backend always retains complete raw history, and evidence, notes, and history remain available through paginated reads by file, location, or request_id. Research requests reuse actual capacity checks, counting native tool definitions, messages, notes, and reserved output. Runtime's default input budget is 600,000 tokens, including when older configurations omit the setting or set it to null; switching models does not revert to old character limits. When a smaller `context_window` is known, input, output, and headroom are still checked against that window. If the service cannot count tokens, an explicitly configured encoding uses `local_tokenizer_estimate`; otherwise, `o200k_base` is used by default and marked `default_tokenizer_estimate`. Estimates are not equivalent to accurate provider metering. When the complete request exceeds the limit, older source text leaving the window must first be synthesized. Working views such as notes, facts, responsibilities, and dependencies are then replaced with paginated navigation as needed, without rewriting fixed snapshots or deleting persistent notes. If even minimal navigation exceeds the limit, the capacity constraint is explicitly recorded and passed to subsequent gap handling; responsibilities or conflicts cannot be silently discarded. For specific parameters and deployment instructions, see [Request Context and Capacity Design](context-and-capacity.md).

Tools register requests before execution and commit after completed results are saved. Interrupted requests are not treated as successful, and old requests with side effects are not silently rerun. The Agent may use failure records to adjust and propose new operations. Completed results with matching identities may be recovered and reused. Cross-task reuse accepts only verified records whose sources, environments, and artifacts still match.

When a user explicitly continues a paused or failed job, failed requests receive one bounded retry window, including parallel subtasks that had already failed before the pause. Successful caches, body text, research checkpoints, total call counts, and stage-specific quotas are all retained. Repeatedly clicking continue, or toggling pause without a new failure, does not stack quota. Service startup does not automatically resume tasks deliberately paused by the user.

Changes to repair prompts produce only new research questions. When formal tasks, sources, facts, and dependency versions remain unchanged, existing notes, reading records, and coverage ranges are still inherited. Legacy memory keys containing repair prompts are migrated after checking original task records, without directly relaxing version checks. The new coverage review also permits one recheck of legacy failed contracts, retaining confirmed ranges and actual usage. Successful contracts are reused directly; new-version failures cannot be repeatedly reset by restarting.

Fact extraction requests retain the complete body and use `fact_extraction_scope` to explicitly list paragraphs eligible for fact extraction and model-suggestion paragraphs used only for summaries. Claims citing both model suggestions and actual evidence are still rejected from the fact store. Correction feedback explains that the factual portion should be retained while solution recommendations remain in the summary; invalid citations must not simply be deleted to make facts appear supported.

Validation is divided into format and permission-boundary tests, real local container/Office/OCR execution, complete workflow regression with simulated models, and separately authorized real-model document acceptance. Passing the first three does not mean the model can reliably analyze arbitrarily complex materials, nor that OCR or complex Excel formulas are inherently correct. For test methods and acceptance boundaries, see [Testing](testing.md).

## Coverage Reports and Error Summaries

Complete coverage results are saved under the task directory at `.research/coverage_reports/<coverage_id>.json`, including every missing item, location, reason, and the section revisions checked. `Finding.description` allows at most 3,500 characters; coverage findings contain only counts, the inventory ID, and a short explanation, without embedding missing-item JSON. Read-only publication checks do not overwrite saved reports. Missing coverage remains pending confirmation; shortening its description does not waive validation. Local data validation errors are reported as internal validation failures. Only output validation failures attributable to a model call are classified as model-output errors.
