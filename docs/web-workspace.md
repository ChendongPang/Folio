# Frontend GUI Design

> 中文版: [中文版](web-workspace.zh-CN.md)

## Current Interaction

Folio is a document workbench for working with multiple source files. Users first collect materials and describe the document they need in the conversation. The system then plans the complete table of contents and starts generating the body only after user confirmation.

```text
Batch upload materials → Describe document requirements → Complete table of contents → Confirm → Generate and download
                                                                  ↑                    │
                                                                  └─ Revision advice / Replan
```

The GUI does not provide the legacy template recommendation, template library selection, outline purpose assignment, or cover confirmation workflows. Users can upload a DOCX directly and set its role to “Document template” in the materials library. They can also mark an uploaded file as a “Style reference” to use only its writing style and formatting. When a template is provided, its specified structure and formatting are preserved. Without a template, the system plans independently based on the requirements and business materials, applies confirmed style parameters, and uses built-in formatting for everything else. The “Document type / General document” selector has been removed from the interface; users describe the required type in the conversation. Session creation does not pass `guide_id` and retains the backend default for general documents. The backend API and CLI still support optional URD/SRS writing guides, and guides frozen in existing sessions are not cleared by this interface change. For template preparation and current support, see [User Template Design](templates.md).

## Implementation and Visual Design

The frontend uses Vue 3, TypeScript, and Vite, with source code in `frontend/src/`. FastAPI serves the API and build artifacts. The interface uses a white canvas, black-and-white hierarchy, thin borders, and monospaced annotations, with green and red indicating states such as success and failure. Session history is on the left, material entry points and the conversation are in the center, and the table-of-contents preview on the right can be expanded or collapsed. On mobile, table-of-contents confirmation remains in the conversation so that the preview layer does not obscure it.

The product brand is “Folio.” The sidebar uses the title-case `Folio` wordmark, and a geometric symbol formed from a book spine and folded page is used consistently for navigation, the assistant avatar, and the browser icon. Icons use native SVG to remain sharp at small sizes. The page title, assistant signature, and assistant self-references use the same name. Internally, `folio` is used consistently: the Python package and CLI are `folio`, the default data directory is `.folio`, the database is `folio.sqlite3`, browser storage keys use the `folio.` prefix, and environment variables use the `FOLIO_` prefix. Existing workspaces must have their directories and active paths handled according to the [Migration Instructions](workspace-migration.md). Consistent branding alone does not mean historical data has been migrated.

The input area retains only the message input, add-materials control, and circular send button. Decorative text at the top and the separate “Generate table of contents” button have been removed. After document requirements are sent, existing intent recognition initiates table-of-contents planning; confirmation remains a separate action. While a task is running, a circular control button appears in the same position: document generation uses a pause icon, paused generation uses a resume icon, and ordinary answers use a stop icon.

On desktop, users can drag the left edge of the right-hand preview pane to adjust its width while preserving usable space for the central conversation. The preview pane is divided vertically: the complete table-of-contents structure is above, and page-by-page layout previews are below, with independent scrolling. The divider between them can be dragged up or down. It supports keyboard arrow keys, Home/End, and Escape to cancel a drag. The width and vertical split ratio are saved as local interface preferences and restored after refresh. On narrow screens, the preview uses a viewport-constrained overlay without a horizontal resize handle.

- `App.vue`: Main canvas, upload entry point, input area, navigation, and workflow state.
- `useWorkspace.ts`: Sessions, material upload queue, drafts, table-of-contents versions, and SSE lifecycle.
- `MaterialsPanel.vue`: Materials library; business material / document template / style reference role selection; search, filtering, pagination, removal, and retry after failure.
- `WorkflowActions.vue`: Complete table of contents, confirmation, revision advice, regeneration, and access to style notes.
- `DocumentPreview.vue`: Table-of-contents tree, actual Word structure / page previews, and table-of-contents download.
- `MessageList.vue`: Messages, processing progress, errors, reviews, and final Word download.
- `ConfirmationPanel.vue`: Answers to pending confirmation questions, the current run's call allowance, rechecking, and access to earlier drafts.
- `ModelSettings.vue`: Model configuration, connection testing, and optional services.

```bash
npm --prefix frontend ci
npm --prefix frontend run build
uv run folio serve --port 8765
```

For routine development, use `npm --prefix frontend run dev`. The API is proxied to local port `8000` by default. The build includes type checking and writes artifacts to `src/folio/web/dist/`. HTML is not cached, and asset filenames contain content hashes. If build artifacts are missing, the home page displays build instructions while the API remains accessible.

## Material Uploads and File Research

Uploaded files default to business materials, `source`. Supported formats are DOCX, MD, TXT, XLSX, PDF, PPTX, PNG, JPEG, TIFF, and WebP. All saved files can be assigned “Business material” or “Style reference”; DOCX files can also be assigned “Document template.” Templates use `template`, with at most one per session, and style references use `style_reference`. When multiple style references are present, the first in the attachment list is the primary reference. Other examples are recorded separately, and conflicting styles are not automatically blended. Filenames do not determine roles. Each session supports up to 200 files in total, with no per-file upload size limit. Both frontend and backend still reject empty files and unsupported formats. The frontend uploads at most 3 files concurrently and queues the rest. The backend receives and writes the originals as streams, then returns success after parsing and structural preprocessing finish. The materials library supports filename search and status filtering, displaying up to 50 files per page.

“Queued,” “Uploading,” “Upload failed,” and “Saved” indicate only file transfer and persistence status. Failed uploads can be retried or removed. A successful upload is immediately bound to its original session, and saving a draft does not overwrite the materials list. Switching sessions cancels the unfinished queue; saved files are restored from the server, and old requests cannot write to the new session.

Roles are saved through separate PATCH requests rather than overwriting file bindings through text drafts. Until a request completes, the saved role remains in effect and “Saving” is displayed; sending, deletion, and other role changes are blocked. On failure, the original selection is retained and the reason is shown. A second template returns an explicit error. The user must first remove the old template or explicitly change its role to ordinary material; the system does not automatically downgrade templates. Roles are saved and restored with files. Historical files without a role default to ordinary materials.

Before table-of-contents generation, a snapshot of the originals is fixed. The main LLM browses the Manifest, then inspects complete internal structures, searches, and reads relevant source text in pages as needed. Table-of-contents research runs for at most three rounds, records the actual reading scope, and distinguishes gaps affecting the table of contents from information to be supplied during body generation. It no longer substitutes excerpts from the beginnings of files for research. Templates are frozen separately, and fixed sections, completion requirements, and mandatory tables are extracted without treating example business content as a factual source. After confirmation, the body-generation stage inherits source evidence from the corresponding file versions. The Business Agent continues autonomous file research and can perform precise reads and searches, and execute Python, Office conversion, and OCR in an isolated container. The research materials directory contains only ordinary materials. Successful uploads of images and scanned pages do not mean OCR is complete; unverified extraction results remain pending confirmation. The workbench has no knowledge-base selection, pending Wiki/RAG integration, or knowledge-engineering workflow; local search uses uploaded materials directly. For deployment and source boundaries, see [File Research and Execution Design](agent-research.md).

When style references are present, programmatic statistics and batched analysis of the full text are first performed on an independent snapshot to generate `style/style.md` and executable parameters in `style/profile.json`, before planning the table of contents. Reference text enters only dedicated style-analysis requests, not ordinary chat excerpts, table-of-contents research, or global facts. Business attachments with identical content but different names are also isolated by hash. The interface shows the current step for batched reading and completion checks, and the notes record actual text coverage and missing visual information. Style analysis has limits on calls, cumulative characters, and segments. If a limit is reached or semantic checks fail, the analysis remains incomplete; completed text reading is not treated as a visual review of the entire document. Unchanged, reusable analysis results are read from cache. Legacy sampling caches cannot serve as the new full analysis.

Users can also directly say “Analyze this style reference,” “Look at the sample document's formatting,” or ask about specific aspects of its style. The `analyze_style` intent runs style analysis independently without creating a table-of-contents or body-generation task. Targets are selected by current attachment IDs, and only files marked `style_reference` are accepted. On completion, the system sends a result card and a viewable `style.md`, then streams an answer to the user's question based on the extracted results. Ordinary chat can also read the style summary for the current file version. Chat input remains available during table-of-contents confirmation; sending a message does not confirm the table of contents. Analysis inquiries are marked `discussion` and do not change the requirements version or revoke an existing table of contents.

Adding or removing files, changing roles, or changing the writing guide invalidates the old table of contents. Removal only detaches the reference from the current session; it does not delete originals or snapshots referenced by other historical tasks. Running or paused tasks retain their original inputs, and the current task must finish before adjustments can be made. The server uses the same session lock to protect upload binding, removal, role changes, and generation confirmation.

## Table-of-Contents Confirmation

The session stores `directory_review`, containing `revision`, `phase`, the user requirements version, material references, rationale, and `directory.sections`. The generated table-of-contents preview is stored in `directory.preview`. When style notes exist, `directory.style_url` points to the Markdown viewing endpoint for the current table-of-contents version. The confirmation area displays “View style notes,” which opens them as plain text in a new tab. The frontend saves table-of-contents snapshots for individual messages. Only the generation and revision buttons for the current version are actionable; historical style notes remain viewable.

`directory.research` shows the files and section ranges actually read, character counts, and unresolved issues. “Material research record” can be expanded above the table-of-contents preview, and the complete JSON record can also be downloaded. Statistics indicate only that source text was returned to the model, not that the entire text was read or any level of understanding achieved. When `directory.confirmable=false`, the draft table of contents is shown with confirmation disabled, and the server also rejects attempts to confirm directly by bypassing the frontend. Revision advice and regeneration remain available. Legacy tables of contents without pre-planning research records remain viewable but must be regenerated before confirmation. The coverage review checks whether each researched requirement is addressed in a table-of-contents node or writing instruction; remaining omissions are shown as unresolved issues.

User requirements are stored independently in the session's `requirements`. Each original-text entry records its source, type, and order, and the complete collection has a content-hash `revision`. Existing intent recognition also distinguishes formal requirements, ordinary inquiries, and messages requiring clarification, adding only formal requirements and explicit revision advice to the complete requirements without additional model requests. Explicit subsequent revisions override the requirements they modify; all other original constraints remain in effect. Table-of-contents and body planning no longer use only the latest 8 messages or the last 11,800 characters, and the model does not compress this record.

A message's `requirement` audit record contains `status/kind/source`, and `intent` is saved separately when intent classification completes. `generate/requirements` become `active` initial requirements or revisions, respectively; ordinary chat becomes `discussion`, ambiguous intent becomes `clarification`, and pure interface commands are marked `command`. Existing Jev / luna-decisions intent routing continues to support these classifications. Failed classification leaves the record `pending`; uncertain messages are neither directly treated as requirements nor silently discarded. While such messages exist, table-of-contents generation and confirmation are blocked. After the user resends the same content and classification completes, the old record is marked `resolved` with its association retained. Historical constraints without classification records from before the upgrade are conservatively retained, and frozen requirements are not automatically removed. Inquiries and clarification messages do not themselves change the requirements version.

Table-of-contents revision advice is persisted in the session and requirements records. Replanning discards the old proposal but inherits all user requirements and revisions. Fixed labels for the confirmation and regeneration buttons and greetings are not written into requirements; the original text from the revision-advice field is recorded only once. When accumulated requirements exceed 600,000 characters, the system returns an explicit capacity error, retaining the original text and old table of contents rather than truncating the text and continuing to call the model. The user must create a new session and provide a consolidated, complete set of requirements. Complete planning requests are also subject to the table-of-contents capacity budget in the model configuration.

| Action | Result |
| --- | --- |
| `chat` | Ordinary streaming conversation; directly plans a table of contents when explicit writing requirements are recognized |
| `generate` | Plans a complete table of contents from current materials and requirements without generating the body |
| `revise_directory` | Saves the original `advice` text and revises the current table of contents; binds the new requirements and table-of-contents versions on success |
| `regenerate_directory` | Replans from the complete requirements, all revisions, and current materials without reusing the old proposal |
| `confirm_directory` | Verifies that requirements, files, and roles still match the table-of-contents snapshot, creates a body-generation job, and freezes business materials, the optional template, style references, and adopted style notes |

Revision, replanning, and confirmation must include the current `selection_revision`. The server validates session ownership, the table-of-contents version, requirements version, file IDs, roles, writing guide, and task state. Old buttons, concurrent duplicate confirmations, or invalidated inputs cannot start new tasks. If new requirements are added or revision fails, the previous table of contents remains available for viewing, and the new revision requirements are retained. The old table of contents cannot serve as confirmation of the new requirements; successful revision or replanning is required before confirmation.

Table-of-contents metadata and `JobInput.requirements` use the same requirements snapshot. `JobInput.user_request` matches its complete text, and `requirements.json` is saved separately in the job input directory for traceability. Legacy tables of contents generated before the upgrade without requirements snapshots return HTTP 409 with a prompt to regenerate. Already-created jobs can still read their original inputs and checkpoints. Partial table-of-contents revisions use stable node IDs and include the complete requirements context; there is no original-outline or outline-reference protocol.

Table-of-contents metadata also stores `source_roles: [{id, role}]`. Historical tables of contents missing this field allow only ordinary materials. When a template is selected, `template.docx` and `template-contract.json` are saved separately. The program binds trusted constraints to `template_section_id`, `required_tables`, and `allow_subheadings` in the plan, rather than requiring the frontend or model to invent bindings. Fixed sections are not expanded by default; subsections may be added only when the template explicitly permits them. Body-generation jobs independently freeze the template and check its hash. Changing the template's role or original file version requires replanning.

Original style-reference files are saved separately in attachment order as `style-references/{index}/filename`. Table-of-contents metadata preserves the primary-reference order through relative paths in `sample_paths`. At confirmation, the system reads the examples and `style/profile.json` from the frozen directory, verifies each file's content hash, and saves them to the job's `inputs/samples/` and `inputs/style/`. Body generation and recovery reuse the confirmed style rather than reanalyzing it to produce different results. Neither templates nor style references are included in the `sources` or `knowledge` snapshots used for business research.

The table-of-contents confirmation view directly displays the complete tree, with scrolling to read all nodes. The confirmation area contains a generation button, revision-advice field, regeneration entry point, and optional style notes; it is no longer hidden behind a mandatory template or cover workflow. The Word table-of-contents preview and final document use the same frozen layout policy: when a template exists, its original structure and formatting are retained; without a template, reliable parameters from the primary reference and explicit formatting requirements are applied, with default styles retained for unspecified aspects. If Office / PDF-to-image components are unavailable, a structural preview is shown. The table-of-contents preview must not be described as a generated body.

Placeholder notes in the table-of-contents preview indicate only that the body has not yet been generated; they do not fabricate business questions requiring confirmation. When restoring an old session, outdated previews are laid out again from the saved authoritative table of contents into a separate cache, without calling the model, changing requirements, table-of-contents versions, or section IDs, or overwriting historical files. PDF and page images are generated from the new preview.

## Interfaces

| Endpoint | Purpose |
| --- | --- |
| `POST /conversations` | Creates a session, optionally with a writing guide |
| `GET /conversations` | Reads historical sessions with pagination, pinned sessions first and sorted within each group by content update time; returns names and pinned status |
| `GET /conversations/{id}` | Restores messages, materials, input drafts, the table of contents, and tasks |
| `PATCH /conversations/{id}` | Updates `title` (1–200 characters after trimming leading and trailing whitespace) or `pinned`; custom names are not overwritten by subsequent messages |
| `DELETE /conversations/{id}` | Deletes only the session, messages, drafts, and material associations, retaining files; adding `?delete_files=true` also cleans up exclusively owned uploads and task files while retaining shared resources; returns 404 if nonexistent and 409 if processing has not stopped; executed after frontend confirmation, and deleting the current session opens the new-session page |
| `POST /conversations/{id}/sources?filename=...` | Uploads a raw file stream and binds it to the session |
| `PATCH /conversations/{id}/sources/{source_id}` | Saves `{role: "source" \| "template" \| "style_reference"}`; validates template type and count, and invalidates the old table of contents |
| `DELETE /conversations/{id}/sources/{source_id}` | Removes the material reference from this session and invalidates the table of contents |
| `PUT /conversations/{id}/draft` | Saves `{text}` without overwriting the materials list |
| `PUT /conversations/{id}/writing-guide` | Backend writing-guide endpoint retained; updates invalidate the old table of contents; the current GUI has no selection control |
| `POST /conversations/{id}/messages` | `{text, action, selection_revision?, advice?}`, returns SSE |
| `GET /conversations/{id}/directories/{revision}/style` | Validates that the table of contents belongs to the session and displays `style/style.md` for that version; returns 404 if no style notes exist |
| `GET /conversations/{id}/styles/{revision}` | Validates session ownership and frozen originals, and displays `style.md` generated by independent chat analysis; returns 404 if no valid result exists |
| `POST /jobs/{id}/pause` / `resume` | Stops or resumes a task belonging to the specified session |
| `GET` / `POST /jobs/{id}/confirmation` | Reads current questions and version; submits optional answers, an idempotent request ID, and the current run's allowance to continue execution |
| `GET /jobs/{id}/confirmations/{request_id}/artifact` | Downloads the Word file archived before the corresponding continuation |
| `GET /jobs/{id}/stream` | Actual task events and historical replay |

Upload responses include the file's `id/name/size/role` and `directory_invalidated`. Role-change responses include the authoritative `files` list and `directory_invalidated`; saving the same role again does not invalidate the table of contents. Deletion responses include the removed ID and updated status. Compatible low-level upload and Word preview resource endpoints remain available. The template role is set through the file PATCH endpoint, not through the old template library or preview recommendation endpoints.

SSE uses `message.delta/completed/failed`, `directory.update/review`, `job.created`, `job.paused/resumed/failed`, `work.update`, and `artifact.ready`. Progress reflects only actual stages and known elapsed time, without fabricating completion percentages. Receiving HTTP 200 means only that the stream has been established, not that the table of contents or body succeeded.

Ordinary chat and intent classification display only the thinking animation, without a step panel or placeholder text such as “The current step is shown below.” After non-whitespace body text arrives, the animation is hidden and the answer is streamed. Only table-of-contents research, style analysis, and body generation display a step panel, positioned above the response body so that the growing answer does not push it downward. Progress records in ordinary chat history remain in the backend and are not displayed as tasks after refresh. Once style analysis is complete, preparing an explanation and streaming the response do not reopen the completed analysis steps or continue showing old steps as running.

For table-of-contents research, `directory.update` carries a stable `activity.id`, an action description in the interface language, the current status, total elapsed time, and elapsed time for the current step. Action descriptions use actual filenames, sections / Sheets / pages, and actual counts of returned structures and source-text characters, rather than tool names such as `fs.inspect` as progress. Each new action adds a record; heartbeats and model-response phases for the same action update only the existing row. Model transport provides four status categories—waiting, connecting, analyzing, and receiving results—through task-isolated activity subscriptions. It transmits neither raw reasoning nor structured JSON and adds no model calls. Steps collapse on successful generation and remain expanded on failure. Processing records are saved in `activities` on the session's assistant message and remain viewable after refresh, but do not enter the model context for the next chat or intent classification.

Interface requests use `Accept-Language`. The backend applies the bilingual catalog in `locales/*.json` to JSON and SSE display fields through `api/localization.py`, without rewriting saved tasks, source materials, or downloaded files. Complete SSE events are forwarded immediately rather than waiting for task completion. Responses carry `_translations`; the frontend resolves text at render time so received progress, diagnostics, and errors can switch languages too. User messages, filenames, section titles, quotations, model prose, and streaming replies retain their original content; new model replies carry `content_origin=model`. Unknown text stays visible rather than being hidden behind a generic status.

Document output and interface languages are stored separately in `JobInput.language` and `JobInput.ui_language`. Body text, default placeholders, reference labels, and document download suffixes follow writing requirements, with explicit language requests taking precedence. Interface preferences control the workbench and process descriptions only. Register both translations for new fixed messages; write code comments, tool descriptions, and model prompts in English. Preserve Chinese input-recognition rules, actual font names, protocol identifiers, and historical evidence text so translation does not break saved task identity or content validation.

Style analysis uses `style.update` to reuse the same progress structure, labeled “Style analysis process” in the interface. `style.completed` provides the status, filename, cache-hit status, and style-notes URL, and ordinary `message.delta/completed` responses may still follow. The session saves `style_analyses` records, and assistant messages save the `style_analysis` result and `activity_label`. Result cards can be restored after refresh, and generated notes remain viewable even if the subsequent explanation fails. This event does not change the table-of-contents preview, its confirmation state, or the body-generation stage.

Ordinary chat responses that use style summaries also save `style_context_versions`, binding the answer to the attachment IDs and content hashes actually supplied. Before the next intent classification or answer, the program checks current roles, versions, and the scope selected for that request. Invalidated old style responses are replaced with expiration notices in model history, while the original conversation records remain available for users to view. Result cards, progress, and version metadata are not resent to the model.

## Persistence and Task Control

Messages, original requirements and versions, material references, table-of-contents state, job associations, and input drafts are saved in the server-side workspace. The browser saves the current session entry point, unsynchronized text drafts, and interface preferences such as panel dimensions. Creating a new session does not delete old data. Service restarts should continue using the same data directory.

Historical sessions are displayed with single-line titles. On desktop, an ellipsis menu and pin button appear on hover or keyboard focus; touchscreens retain directly accessible controls. The menu has only four options: rename, pin / unpin, delete conversation only, and delete conversation and files. The latter cleans up exclusively owned uploads, all table-of-contents / style working directories, and document tasks according to resource ownership. Files referenced by other sessions or tasks, globally shared previews, and material-processing caches are retained. This is not a full workspace wipe. Paths and running states are checked before cleanup, and ordinary file-operation failures restore the original files and session records.

The frontend isolates asynchronous responses by session ID and view version. Switching sessions can detach the current SSE observer while already-created document tasks continue running. Reopening a session restores server-side state and progress. Disconnections do not cause backend failures or pauses to be mistaken for success.

The body-generation stream sends `job.snapshot` first, including the current state and available delivery information. The frontend requests `replay_history=false`: terminal and paused jobs restore from the snapshot without waiting for historical logs to replay. Active jobs still receive progress events. Completed progress cannot overwrite the final state or restart the animation after `artifact.ready`.

The send and table-of-contents confirmation buttons are disabled while uploads are unfinished, failed files exist, materials are being removed, or roles are being saved, preventing tasks from starting with incomplete inputs. Pausing keeps the session locked, and explicit resumption continues the same job. The failure view retains the reason, stage, related sections, saved progress, and necessary safe diagnostics. Raw requests, keys, and internal service errors are not rendered directly on the page.

## Follow-up Answers and Rechecking for Pending Confirmation

After a delivery requiring confirmation, `ConfirmationPanel` displays the actual questions, related sections, calls used, and answer fields. Users can answer some questions or leave answers blank to retry unfinished checks directly. The current run's call allowance defaults to 200 and allows 1–10000; the cumulative count is not reset and is capped at 100000. Source comments also have a “This answer resolves this source comment” checkbox. A comment is closed only after the user explicitly checks it and the revision is successfully committed. Answers such as “Uncertain” do not close it automatically.

Unanswered business questions remain pending confirmation and cannot disappear merely because the model does not report them again during rechecking. When the same answer applies to multiple related questions, users can enter the same answer separately for each. Technical and layout issues are rebuilt through their corresponding checks; retrying with blank answers does not constitute approval of business conclusions.

Submissions include `revision` and a stable `request_id`. Version conflicts retain the input and require a refresh, and retrying the same request does not add the allowance again. Answer drafts, allowances, and request IDs are saved separately by session/job, preventing old asynchronous responses from writing to a new session after navigation. On success, the frontend resubscribes to the original job's events. The table of contents remains unchanged; only the sections corresponding to the issues are directly revised before review and delivery run again.

Downloads of the old Word file point to the archive path for the current round. The question view, session restoration, and delivery events all provide a historical draft list, so earlier versions remain accessible after refresh. New files being generated are not presented as old drafts. For business evidence scope, technical retries without answers, and transaction boundaries, see [Pending Confirmation Answers and Continuation Design](confirmation-and-resume.md).

## Model Settings and Validation

Model settings support OpenAI-compatible generation and optional decision models, each with a Base URL, API Key, and Model. Decision models may also use native Jev: supply the complete `/v1/systemone` endpoint and a provider model ID such as `jev-latest`. Search supports Tavily or DeepSeek Search. Optional services require a successful test of the current settings and explicit enablement. Keys are not returned to the frontend or stored in the browser; closing the dialog clears key inputs.

Advanced parameters retain the “Current generation model supports image input” option (`supports_image_input`), disabled by default, for actual image input in material research, style analysis, and similar operations. It is a capability declaration; an ordinary text connection test cannot prove that the model can recognize images.

The “Have Jev score each page and optimize layout after generating Word” switch has been removed. New generation tasks no longer invoke Jev page scoring, image self-checks, or automatic layout changes after low scores. Normal font, font-size, heading, table, source-marker, template-protection, and pagination processes continue. Content-review and template-check failures are still handled under the original rules. Folio does not claim that these checks constitute visual page-design acceptance, nor does it automatically invoke the independent DocPolish project.

Browser regression testing uses actual Vue build artifacts and controlled API / SSE responses, covering multiple-material uploads, role saving and restoration, second-template rejection and failure rollback, queue and session isolation, table-of-contents confirmation and revision, pause and resume, and actual DOCX downloads. Mock API tests do not constitute acceptance of the model's business-output quality; file research and generation quality are validated separately.

Page scores, issues, and preview records in historical tasks continue to be displayed in their original states and are not rewritten as passed. Retaining read access to historical artifacts does not mean the current generation workflow still performs page scoring.

## Duration and Token Accounting

Delivery duration is wall-clock time from job creation to its last terminal update (`updated_at - created_at`), including waiting, pauses, and interruptions. Parallel task durations are not added; outline planning before job creation is excluded. Legacy records without this duration fall back to the interval between the earliest task start and latest task finish. The displayed Token total sums the available business-task usage records; it is not a complete provider invoice and may omit calls outside those task records. Use provider events and outline/session logs for a complete call audit.
