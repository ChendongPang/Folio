# Source Research and Word Layout Design

> 中文版: [中文版](source-materials-and-layout.zh-CN.md)

The workbench takes writing requirements and source materials as input and supports an optional DOCX template; it does not restore the legacy mandatory-template or pseudo-outline workflows.

## Source Inputs and Fact Boundaries

The GUI distinguishes ordinary source materials (`source`), document templates (`template`), and style references (`style_reference`). Ordinary source materials and style references support DOCX, Markdown, TXT, XLSX, PDF, PPTX, and images; each session supports at most one DOCX template, explicitly designated by the user in the source library. A filename containing “template” or “sample” does not automatically change its role. The CLI uses `--request`／`--request-file`, a local source directory, or explicit knowledge base configuration; `--sample` feeds into the same style analysis workflow. Style references first undergo format measurement, followed by batch reading of all extractable text according to actual request capacity. Page-image analysis separately records the scope actually viewed; finishing the text does not justify claiming that all images have been viewed. Portions left incomplete due to budget, parsing, or model errors remain recorded as gaps. The analysis generates `style.md` and a frozen style profile for reuse in the table of contents, body text, Word layout, and final checks. Sample source text enters only the separate style analysis, not business facts or evidence. Explicit user requirements and templates take precedence over samples; styles that cannot be reliably measured or confirmed remain unknown.

Source materials are first frozen as snapshots, and a shared Manifest and internal structure index are created. The Manifest records file identity, type, size, hash, and preprocessing status; the structure index preserves headings, sheets／column headers／cells, actual PDF bookmarks or page numbers, and warnings about OCR, formula caches, and unread ranges. Source locations and final document section identities are maintained separately.

The original template is frozen separately as `template.docx`, extraction results are written to `template-contract.json`, and the roles of all uploaded files are stored in the directory metadata field `source_roles`. Fixed template sections, completion instructions, and table headers serve as output constraints; sample body text and data rows in the template do not enter the ordinary source catalog, retrieval evidence, or global facts. If a template with identical content is also marked as ordinary source material, removal of the duplicate attachment is explicitly required before planning, and chat does not read its sample body text either. Replacing a template does not automatically turn the old template into a basis for business content.

Before generating the table of contents, the main LLM first browses the Manifest, then independently selects files, inspects internal structures as needed, locates and reads relevant source text, and continues paging through it to produce table-of-contents requirements and unresolved questions backed by source evidence. When explicit page numbers or node locations are already available, direct reading is allowed; skipping structural browsing alone does not block completion of the research. Notes and table-of-contents conclusions cite evidence IDs. The program associates batches and selected ranges based on actual delivery records; the model is not required to maintain internal request or range IDs. Delivered page segments may serve as evidence without requiring the entire query range containing them to be read; unread status remains accurate, and partial citations must not be presented as full-text coverage. A small number of files or completed preprocessing does not mean the model has read them; fixed excerpts from the beginning of each source no longer substitute for this step. Research calls, tools, and time are all bounded. If key evidence affecting the table of contents is insufficient, the budget is exhausted without a valid conclusion being submitted, or the package／business scope remains unclear, the draft remains `partial` and cannot be directly confirmed for body drafting.

For body research, the recommended evidence-gathering sequence is file list → internal structure → retrieved excerpts → corresponding complete ranges, while direct reading from known locations is allowed. Each round permits a limited number of tool actions, with at most three local rounds and at most two web-search rounds. If project evidence is still lacking, model suggestions may be added, but guesses must not be written into verified shared facts. Reading records from before table-of-contents generation and source evidence from the same version may serve as starting points for subsequent tasks; “having read a location” must not be treated as verification of the entire source or complete body text. Unverified OCR, unapproved parameters, and unvalidated calculations retain their respective statuses.

`reader.py` continues to read DOCX headings, paragraphs, tables, revisions, and comments. The revision view is selected explicitly; search hits do not automatically prove complete coverage. Comments and source content do not automatically become user requirements merely because they appear in a sample.

## Table of Contents and Body

Without a template, the table of contents is planned jointly from the writing requirements and actual source research findings. With a template, writing is organized while preserving its fixed structure and explicit extension boundaries. Neither workflow creates a pseudo-outline or requires the model to output legacy source-mapping rationales. The program validates the structure of the table of contents itself; when a template is selected, it also validates fixed headings, levels, parent-child relationships, ordering, and the sections to which required tables belong.

After the structure passes validation, the main model checks each research requirement against the source text to ensure that it has an explicit destination in a table-of-contents heading or writing instructions. One requirement may be handled by multiple nodes, and multiple requirements may share one node. Inapplicable items require an explicit scope-based justification, and the program rejects nonexistent requirement, evidence, or node IDs. Omissions trigger bounded repair. A table of contents with unresolved issues, incomplete research, or an undetermined scope remains a draft and cannot be confirmed. See [LLM Table of Contents Planning Design](outline-planning.md). Actual business citations remain stored in Evidence, location information, and trace; the body does not display internal `ev_`, `sfref`, or runner fields.

The program binds template constraints to the confirmed plan: `template_section_id` links to template sections, `required_tables` defines required tables, and `allow_subheadings` limits additional headings in the body. The model cannot delete these fields on its own. During body drafting, deterministic checks enforce requirements such as table headers, table counts, data rows, and prohibitions on adding headings, using the existing repair and pending-confirmation delivery mechanisms. Fields lacking source data must be explicitly marked as pending confirmation, rather than filled with template sample values as facts.

The confirmed table of contents enters the business-task DAG. `Store.create(..., directory_research=...)` freezes the table-of-contents research and requirement-allocation review results into the job’s `inputs/directory-research/`. Body tasks inherit only source evidence from the same version and requirements for the corresponding nodes, and continue reading as needed for business questions. The Business Agent researches source materials, consults global facts, and generates body text and required illustrations; the reviewer checks facts, completeness, and consistency; the coordinator controls budgets, dependencies, submission, and recovery. Table-of-contents summaries do not enter global facts directly, and template samples always remain isolated from business evidence. Removing legacy mapping fields from the table of contents does not change these collaboration boundaries.

## Word Layout and Template Formatting

The sole body export entry point is `render(target, plan, states, ...)`. Without a template, the program creates a document and installs built-in Chinese／Western fonts and heading, body, table, and table-of-contents styles. With a template, it fills the body using the frozen original DOCX as the base, preserving template-defined styles, page and section settings, fixed headings, headers and footers, and required table layouts. Body content follows the formatting of its corresponding section; unspecified new content uses default rules. Neither mode restores the legacy `{{folio.content}}` whole-block insertion protocol.

Completion prompts, sample body text, and sample data rows within template sections are replaced with the current content. Fixed cover content and graphics before the first section are preserved, and explicit document-title placeholders are supported; the system does not guess replacements for every old project value on the cover. Structures that cannot yet be safely populated, such as body images, content controls, and unprocessed revisions, cause errors. For the full supported scope, see [User Template Design](templates.md).

Common rules include heading levels and numbering, stable bookmarks, a clickable table of contents, page-number fields, body-list indentation, repeated table headers, preventing table rows from splitting across pages, image width and height limits, figure captions, and continuous figure numbering. When applying these rules, formatting explicitly defined by the template takes precedence. Local body headings are formatted at levels relative to their containing sections, must not compete with the confirmed table of contents for numbering, and must comply with template extension permissions. Business tables with explicitly specified column names are validated for table shape. Ordinary generated tables disable inherited cell numbering; required template tables retain their original layouts and header formatting.

Model suggestions continue to be marked in red; formatting does not confer factual status on source content. The document title comes from user requirements, and table-of-contents previews, drafts, and demo artifacts are clearly labeled. Font rules do not prove that the corresponding fonts are installed in the actual environment; rendering-substitution checks must be interpreted according to the capabilities actually reported.

## Pagination and Formatting Checks

LibreOffice/UNO calculates bookmark page numbers and a PDF on a copy, and the program writes the page-number field caches back into the DOCX without replacing the complete original document. The caches and final PDF are saved after pagination converges. If the components are not installed, the result is marked `requires_office`; Word/WPS can update fields, but actual pagination is not claimed to be complete. Page images are generated by `pdftoppm`.

Final Jev page scoring and automatic optimization after low scores have been removed. The current workflow retains constrained formatting optimization of paragraph, table, and similar properties, content protection, and actual pagination. Formatting adjustments do not modify body text, sources, heading identities, or the red color of model suggestions, and cannot override formatting specified by the user template. These checks do not constitute visual or aesthetic acceptance. Source research and style analysis may still use image inputs; the standalone DocPolish has not yet been integrated into the generation pipeline.

Template tasks validate the frozen original’s hash and template formatting during rendering, checks after formatting changes, and final publication. Checks cover fixed sections, style definitions, page and section settings, headers and footers, and required tables and their header layouts. Results that violate template constraints cannot be published directly as final artifacts.

`reformat` uses the saved body text and document plan, applying the built-in layout when no template is present and reusing the frozen template when one is present, without calling the model. Saved valid formatting patches are replayed only when they match the current document signature; on failure, a safe version is retained. Replay does not constitute a new visual check.

## Compatibility and Validation

Legacy jobs and historical tables of contents preserve body text, evidence, and stable section identities through explicit migration on read; new public requests still reject legacy mandatory-template／outline fields. Historical plans without templates follow the original path; new plans with templates save complete constraints and a separate snapshot of the original. Old previews can be opened read-only, and the preview resource API does not handle template selection. Only a DOCX uploaded by the user and explicitly assigned a role enters the new template branch.

Regression coverage includes table-of-contents structure and local corrections, source parsing, shared facts, business tasks, citation provenance, body and table completeness, illustrations, pagination, source colors, page patches, and recovery. The template branch additionally validates role freezing, sample isolation, fixed structure, required tables, and final formatting protection. Mock-model tests validate contracts and boundaries; they do not replace real business-quality acceptance.
