# 业务任务执行设计

> English version: [English version](task-execution.md)

本文件描述当前实现，会议纪要更新不在范围内。

## 文档结构和执行计划

DocPlan 保存稳定的文档节点、顺序、标题级别、写作约束和节点用途。WorkPlan 保存业务执行单元，两者不使用同一粒度。LLM 根据完整内容节点索引、用户要求及材料索引提出分组，不按一级、三级或叶子标题固定分组。

每个 WorkTask 包含 `task_id`、`title`、`objective`、`section_ids`、`questions`、`depends_on`、`completion_criteria`、`rationale`。程序校验：任务 ID 唯一；内容节点覆盖完整且恰好一个写入负责人；容器不可分配写作；依赖必须存在且无环；单任务节点数符合配置。格式和约束错误返回模型修正，遵守原有重试及总调用预算。

初步规划读取本地事实材料的标题与字符量、本地知识文件索引或远端 dataset ID。成品示例不进入事实索引。索引有界，节点写作指令最多展示 600 字并标记是否截断；执行阶段读取完整指令。远端材料尚未检索时明确标记数量未知，不伪造对知识库的完整理解。

任务不少于 4 个、最长依赖路径不少于 3 层且允许并行时，执行前或恢复时可进行一次 `audit_work_dependencies`：模型只对候选边返回保留、移除或不确定及简短原因，不重写任务。最多检查 16 条边，调用限时 20 秒且不重试；上下文过大、调用不可用或结果不完整时沿用原图，继续生成。只允许移除尚无 WorkState、尚无正文节点的任务入边，已开始任务的研究版本与进度保留。调用计入逻辑次数预算并归档；该直接 Runtime 路径不进入 HTTP 额度作用域和主服务总并发闸门；Store 在同一事务中保存有效计划及审计缓存，恢复不重复调用。业务流程先后或共享资料不等于生成任务必须依次完成；不确定的真实产物依赖仍保留。

## Agent 角色与交接契约

业务执行实现位于 [agents.py](../src/folio/orchestration/agents.py)。`BusinessWorkflow` 保留 Engine 已有调用入口并提供共享服务；`BusinessAgent` 接管自主文件研究、缺口补写和任务执行，`ReviewAgent` 接管任务审阅，`BusinessCoordinator` 接管 DAG 调度。所有模型调用仍经过原有运行时、请求覆盖契约和调用预算。角色交接不增加固定请求；V2 每次研究工具决策及派生结果核验会产生受预算控制的实际模型请求。

| 契约 | 内容与检查 |
| --- | --- |
| `BusinessAssignment` | WorkTask、确认目录与输入哈希、已有节点版本、依赖结果、剩余检索预算；接手前验证仍匹配当前计划及来源 |
| `BusinessResult` | task_id、完整节点版本、review_key、当前有效问题；节点齐全且审阅版本一致才允许释放后继任务 |
| `RepairAssignment` | 业务负责人、预期节点版本、原问题及修复要求；禁止跨负责人直接修改或使用过期修复单 |

任务包、交付回执、修复单分别写入 `contexts/agent_assignments`、`agent_results`、`agent_repairs`。这些是可审计的输入输出，不是模型内部思考过程。正文、研究、问题与预算仍由同一 Store 管理；暂停恢复不依赖 Agent 内存会话。

## 执行与模型交互

```text
写作要求、资料清单与结构摘录 → DocPlan
    ↓ work_plan（LLM）
WorkPlan → 程序校验覆盖、唯一负责人、依赖和预算
    ↓ 异步就绪队列（检查全部任务，默认最多 16 个同时执行）
V2 任务研究：research_step → 文件读取 / 搜索 / 隔离 Python / 产物核验 → 再决策
    ↓ finish：保留已取得证据与未解问题 → understand_work
可按需使用既有知识库和已启用的搜索服务，沿用对应来源与额度边界
    ↓ 研究完成后仍有缺口 → complete_gaps（LLM）生成红字建议
按内容节点 generate → extract → validate（共享业务记录，按动作读取原文）
    ↓ review_work
任务整体检查 → 全文 review → drill_down → 有限 repair → 重新检查
    ↓
内置版式 Word → 按业务分组、最多4路属性排版优化 → 最终分页
    ↓
模板与格式保护检查 → 交付与执行报告
```

新 GUI 和 LLM CLI 作业使用 `research/workflow.py` 的自主研究循环。原件经共享 `SourceIndex` 预处理为文件清单、独立结构索引和正文缓存，Workspace 在此基础上提供 Word、Excel、PDF、PPTX、文本与图片的渐进读取；业务任务先看清单和结构，再按片段或 `node_id` 读取整章及子章节。各任务共用原始解析，OCR、笔记和计算产物仍归各任务所有；Sandbox 按需分配容器；ArtifactManager 区分执行完成、产物登记与证据核验。V2 本地研究最多三轮，每轮默认12个工具步骤，三轮仍不足后由协调器安排最多两轮联网补查；普通返工不重置轮次。原图查看、独立视觉释义核验、历史结果／证据分页、范围覆盖与 OCR 接续均复用当前任务及固定事实快照。V2 工具步骤、解析缓存、派生证据、完整覆盖清单与恢复详见[文件研究与执行设计](agent-research.zh-CN.md)。旧作业未配置 `research` 时保留 `next_action/search/write/pending` 路径，但动作选择和查询请求同样使用原生 tool_calls，不解析文本动作 JSON。下文三轮内部检索描述适用于旧路径及 V2 显式调用既有知识库的额度，不限制 V2 原文件分页读取只能三次。

`BusinessRecord` 保存 summary、带 evidence_ids 的 facts、terminology、conflicts、open_questions。事实引用必须存在；语义支持由独立审阅检查。记录中的事实不是业务审批结果，也不能替代原始 Evidence。补查后模型读取当前证据，必要时分批理解并汇集全部事实，原始证据不被摘要替代。

一个任务可以多次调用写作模型。每次只写入一个明确的文档节点，同时接收任务目标、问题、完成条件、必要节点索引、共享记录及为当前节点选择的完整证据；不附带同任务其他节点整份正文。生成与修复无论整包材料是否能放入上下文，都先按当前节点的对象、路径和写作要求选材，避免把同任务另一栏目的材料直接当成本节依据；必须覆盖的项目来源和所选事实的原文仍强制保留。这样保留按节点修复和恢复的能力，也让各栏目共享业务理解。

依赖就绪表示上游正文和任务审阅均已完成，并不等于需求已获确认。上游任务审阅完成后，下游按需选择带来源的已支持陈述和建议；完整原始审阅问题留在后台，交接采用当前有效问题。只传递选中的相关风险及其来源；同页选中多个任务时，按所属任务恢复各自原始风险，禁止给每个任务复制一份混合摘要。有当前有效问题或任务审阅版本已过期的节点不输出已支持事实给下游。下游不能把待确认项提升为业务结论。

## 并行状态与缺口补全

调度器维护 pending/running/completed，使用 `asyncio.wait(FIRST_COMPLETED)` 释放容量和依赖。就绪任务无需 LLM 逐个挑选，默认最多16个业务任务同时执行；真实依赖继续等待上游正文和任务审阅完成。任务先研究，随后全部待写节点直接进入最多八路编写，最后汇集任务审阅；补写记录在任务锁内合并。业务任务执行期间主模型最多32路，后续审阅等阶段16路，跨阶段合计受主服务32路总上限保护；已验证并启用的判断服务统一使用独立16个并发名额，主模型与判断服务合计上限48路。没有判断模型时筛选也计入主模型名额。意图可能回退主模型，仍走主模型队列；下一步动作固定使用主 LLM 原生工具调用。可恢复的模型失败停止派发新任务，并等待已启动任务保存结果；不可隔离的异常或取消会 cancel 并 gather 所有工作协程，避免释放作业锁后残留写入。恢复时跳过已提交节点，并补齐尚未完成的任务审阅。

每个任务在新研究版本开始时固定 `global_facts`，只读取已完成对应版本任务审阅且无当前有效阻断问题的节点；快照对应的原始证据一并纳入任务资料，即使该事实提供方不属于显式依赖。运行中的请求不会自动注入其他任务的新事实。任务/节点以各自 ID 在 SQLite 事务内 upsert，完整作业有文件锁。全局事实是所有当前节点记录的派生视图，不维护多个协程读改写的共享 JSON；相同业务键冲突保留各来源与节点版本，最终统一检查。

共享事实与依赖交接使用同一 `IssueLedger` 和派生状态入口。`adjudications.json` 的误报处置按正文与任务审阅版本过滤当前问题，原始检查记录保留。`SectionState.claim_verdicts/validation_completed` 保存逐事实支持结论；只有已有正向判定或兼容的旧 supported 状态、且引用有效的事实才可进入共享视图。负向或未完成判定、模型建议、缺失来源不会因问题被排除而晋升。`WorkState.review_revisions` 防止旧任务审阅为新正文背书。

兼容研究路径仍有缺口时先使用内部检索预算，默认每个任务最多三轮。内部预算用尽后，若搜索服务已测试成功并启用，再执行最多两次联网补证（Tavily 使用 `advanced`，DeepSeek 使用其搜索协议）；每次由 `web_query` 围绕缺口生成公开知识查询，取得资料后重新整理记录并判断，充分即可停止。搜索服务未启用时直接沿用内部检索后补写的路径。内部 `searches` 与联网 `web_searches` 按任务持久化，重启、修复指令、依赖或研究版本变化都不重置。

[联网流程](../src/folio/orchestration/web_research.py)在请求前保存尝试记录；失败、中断或重复查询跳过仍占用一次额度，恢复时不自动重发。联网失败不阻塞交付。来源由[搜索适配器](../src/folio/knowledge/search.py)及其共用的 [Tavily 实现](../src/folio/knowledge/tavily.py)保存 URL、标题、摘录、检索时间和 `public_web` 角色，不可作为项目内部阈值、人员或审批决定的证据；将公开惯例应用于本项目仍属模型建议。

可用预算均用尽后，`complete_gaps` 分批接收当前缺口、必要证据、相关依赖建议及目标节点，输出具体建议与 `section_ids`。程序验证缺口 ID 覆盖恰好一次、节点有效，持久化 `proposals`，交给写作模型按本节范围整合，不再由程序整段追加。编写人、日期、版本等不能推测的元数据，以及收集信息、检索和文档编写指南，标记 `disposition=record_only`，仅保留后台。

写作返回空正文且没有提出缺口时，立即按该节已确认要求进入同一套有上限的补查与补写流程，不等跨章检查后才发现。检索额度用尽后，若写作重复提出同一个缺口，而对应补写方案已逐字完整出现在本节红字段落中，则记录命中关系并跳过重复整合；不做同义推断，不移除工作记录里的原缺口，仍独立核验正文。逐项整合保护其他方案的已知完整段落及前项刚写入的块，后项不能删除或改写；无效修改保留原文并留下待确认记录。

补写选材最多提前准备三项，跳过只保留后台的记录。预取只返回选中的资料，不预先生成正文补丁；轮到每项时仍以最新正文、保护块和已有引用重新构造请求、测量容量并串行整合。单项选材失败按原顺序留下待确认，全局调用额度耗尽继续向外报告；退出时等待全部预取完成取消清理。

写作产生的新缺口和提前返回的 `model_proposal` 都由[引擎](../src/folio/orchestration/engine.py)检查剩余额度：即使三轮内部检索已结束，只要还有一次联网额度，也须先补查，再决定是否补写。`model_completion_allowed` 对兼容路径使用原检索计数，对 V2 使用协调器完成本地／联网阶段后保存的 `fallback_ready`。任务补查互斥且保存独立状态，避免并发修复覆盖计数；重新研究后，每节只补全本次 `requested_gaps` 与仍未解决的 `work.missing` 的交集，不能因旁节补查而把整项任务的剩余缺口交给当前节点；已经解决的缺口不再生成建议，历史依据与建议继续保留审计。

补写业务内容以 `origin=model_proposal` 留存在后台，Word 仅使用红字区分，不附加“【模型建议】”标签或方案说明。正文初始排版继承已指定表头、字体与字号，最终排版只允许受限格式调整且保留红色；不提供伪造 evidence 引用，不进入 supported 事实。下游单独接收前置任务建议；全文审阅在相邻窗口、具体事实、共同主题及依赖形成的节点组中检查建议；不会仅因双方都含模型建议就建立配对。含建议的文档输出为完整草稿，不自动发布为已确认事实。接口、模型调用、格式或一致性检查失败仍明确报告。

## 审阅、修复和一致性

事实整理、写作、事实抽取和下一步决策的证据引用，均在每次调用时按实际 `evidence` 构建输出枚举；依赖事实、章节或其他批次的编号不属于当前可引用集合。传输层将枚举与材料编号一起转换为短引用并还原，容量测量也使用相同约束。引用错误仍会拒绝，不静默删除事实或猜测替换编号；纠错反馈给出具体事实位置、无效编号和合法范围。失败的完整 JSON 输出保存在作业 `contexts/rejected/` 中，便于核对模型实际返回。编号合法只代表来源引用存在，内容是否受证据支持仍须后续抽取与校验。

持久化的 `Finding.description`、`key` 上限分别为 3,500、300 字符；模型生成 `Review` / `LocalReview` 时，单次请求仍将 description、key 收紧为 240、120 字符，逐条判定 reason 上限为 1,000 字符，要求简述差异，不复制源材料。较大的存储上限也用于程序生成的问题说明，不代表所有审阅请求都允许输出同样长度。事实抽取 `Extraction` 的摘要与事实陈述上限为 3,500 字符；业务理解 `BusinessRecord` 的单次请求摘要仍限 800 字符。正文审阅因容量或输出截断需要继续拆分时，单个表格可按完整行递归拆分；每个子请求保留对应证据与原表行号范围，全部行均检查后合并问题，不把缺少其他行误报为遗漏。输入可容纳但已无法拆分的小审阅单元，若输出仍截断，允许一次带 compact_review_retry 的简洁重试；再次失败明确报错，不接受半份 JSON 或当作审阅通过。

输出 Schema 已确定为空的数组（maxItems=0）不交给模型填写：传输层移除字段，由后台恢复顶层常量，嵌套字段沿用模型定义的空数组默认值。例如正文审阅没有逐事实判定时只要求返回 findings，verdicts=[] 由程序补回。这样避免当前模型在必为空的 verdicts 数组内持续输出空白。不会覆盖模型实际返回的非法非空值，正常校验继续执行；失败日志记录尾部空白字符数，以区分空白循环与实际内容超长。

同样，没有 kind=risk 的材料索引页不要求模型填写风险引用和摘要，risk_refs=[]、risk_summary="" 由程序恢复。选择器只负责选取当前页面可用的资料；已有风险材料时仍须提供合法风险引用与对应摘要，不能凭空生成风险结论。

节点校验继续负责内容格式、表头、引用、事实抽取和局部语义。项目来源必须覆盖的范围按节点匹配，不能要求每个小节重复覆盖整个任务的全部材料。业务主表与额外表的数据行、来源类型和引用完全相同，且表题相同或仅一方有表题时，合并重复表并保留非空表题及配图引用；不同数据、来源或两个不同表题不合并。

明确正向写作指令中的流程图、界面图要求，由本地规则加输出约束和漏图检查；不根据标题或普通“流程/界面”描述新增配图，否定、条件、举例及“二选一”不升级为两项强制要求。实际子图可满足父节要求；无正文写作责任的容器若尚无子节承担，记录待确认，不反复修订空容器。完整正文与来源校验仍保留，详见[文档配图工具](illustrations.zh-CN.md)。

任务整体审阅检查跨小节分工、流程衔接和同一适用范围的规则，逐条证据支持由节点校验负责。单次放不下时，先根据任务问题、完成条件和目录确定最多8项实际相关的跨节点检查，再按问题选择资料、分批阅读；不枚举全部节点对。当前正文、必要来源与来源类型仍受覆盖校验保护，不能声称已审核未提供的原文。

全文审阅保留相邻重叠窗口，优先按相同 `scope / subject / predicate` 组织具体事实，再按共同主题与显式业务依赖补组。每组不超过 `review_batch_size`（默认6节）；广泛主体出现于多节时分为相互衔接的小组，不建立所有节点对。已有窗口或主题组覆盖的关系只补充分组原因，可在容量内合并相交主题组。同一事实键在宽度内汇集不同原样取值的代表；超过宽度时形成一个包含全组记录的精查候选，不展开所有不等值对，包括未获支持或未声明单值的候选断言。首个代表同属一个任务时寻找其他任务的代表；已由宽事实组覆盖的键不再另外生成规则候选。整组不能完整核对时明确保留待确认。取值文字不同只生成审阅候选，不直接判定矛盾。确定性事实冲突索引继续保留；主题相同、同义表达、不同业务条件或另一章未重复说明，都不能单独证明冲突。

跨章请求携带事实锚定的完整正文块及模型方案；每项候选必须以真实 `block_refs` 定位至少两个不同章节，给出 `comparison_scope`（共同适用对象、阶段、条件）和 `incompatibility`（不能同时成立或无法衔接之处）。单节来源和遗漏检查仍在节点与任务审阅中执行。完整原文块超容量时可明确标记延后至精查，事实、方案索引和后台原文不删除，不能据索引差异直接授权修复。

审阅组由有界工作队列并发执行，`max_parallel_reviews` 默认16（可设1～16），共享单作业模型调用总名额。同一任务内部内容已由任务整体审阅处理，不再仅为同任务形成全文模型组；有待确认项仍执行其余预算内检查。缺少抽取主题且不在相邻窗口或依赖范围内的隐含关联仍可能漏检，不承诺所有潜在关系均已枚举。

疑点只有类型、位置、引用集合及规范化描述完全相同才合并，原记录留在 `contexts/review_deduplication/`；同一短问题键但描述不同的疑点仍分别保留。局部及任务审阅的“缺引用”规则须定位本次提供的事实块，输出协议与程序校验不接受仅针对红字补写的缺引用指控；实际事实冲突、伪造和遗漏仍可报告。去重后的有效疑点统一进入独立精查，对照原文核定误报；不能借红字豁免结构及来源硬校验，或把设计提升为已确认事实。

问题从产生起采用 v2 内容身份，去重、有效问题视图与版本化豁免使用同一指纹，不再因同时出现在某个列表里才临时修改 key。身份包含描述、规则、依据类别、定位及比较范围，无定位时保留原问题键。不同问题在分批、重排或重启后仍分离；旧豁免身份不含完整描述，保留审计但须重新精查，不自动迁移。

精查同时确认多项问题时，程序按业务任务归属与依赖的读写范围选择互不影响的一批，基于同一份已保存正文并行修订。相同任务、引用了另一待修任务或存在传递依赖的修订留到下一轮，避免使用过期判断。全部工作协程结束后，Store 在一个 SQLite 事务中比对预期读版本、提交整批节点并使相关审阅失效，随后复查；候选阶段或事务失败均不保存部分正文，取消会收回在途协程。修复单归属校验按原业务负责人进行，预算按实际修改节点计算。结构修复仍未满足明确验收条件时，本批保留原正文并记录待确认。任务审阅也按依赖波次并行，真实前置任务未审完时不启动后继审阅。

修订阶段与首次写作共同校验来源：全为无依据方案的章节不能在修订时变成无引用事实，旧有效引用不能被清空；不会通过自动染红既有错误事实绕过核验。图标题区域若重复抄写至少两段相同出处的完整源段，返回重复块定位并在已有重试次数内纠正；不同业务标题下的同文、不同出处以及表格与列表不作自动合并。

精查需要用户决定、无法裁决或经过有限重试仍未给出可执行修复决策时，保留问题并交付待确认草稿。用户可通过当前问题版本提交答复和本轮调用额度，归档旧交付后继续；业务答复成为限定章节的项目依据，由原负责人直接修订涉及章节，随后重新审阅与导出。目录保持不变，未答复问题不自动消除。本轮修复额度以提交时的章节版本为基线，检索次数和累计模型调用不清零；技术重试允许不填答复。接口、幂等及额度边界见[待确认补答与续跑设计](confirmation-and-resume.zh-CN.md)。

局部修复接收同一任务的业务记录、相关依赖和当前节点必要原文；写回受影响节点后重新检查整个任务。正文写入会清除该任务及依赖它的任务的审阅有效标记。依赖事实变化后，下游任务审阅读取新依赖并重新核对已有正文；只有后续明确修复或新的研究版本才刷新研究记录，不重置检索额度，也不自动把旧正文当作已适配。全局审阅快照与当前节点、业务记录必须一致才可发布。

## 持久化与可观察性

- SQLite `work_plans`：每个作业的固定执行计划。
- SQLite `work_states`：研究上下文哈希、业务记录、证据、内部查询历史、联网尝试及状态、缺口、研究状态、review_key 及对应 review_revisions。
- 模型调用与检索继续使用原有缓存。同请求成功缓存先校验复用，未命中才访问容量服务；缓存失效或进程在远端响应落库前退出仍可能重新请求，不承诺外部恰好一次。
- `GET /jobs/{id}` 包含 work_plan；`GET /jobs/{id}/work` 返回计划和任务状态。
- GUI SSE 展示实际分组、检索、记录整理和整体检查，不展示内部思考链。
- 完成时在作业目录导出 `work-plan.json`、`work-records.json`、`formatting.json`，原有 trace 和 Word 保留。

用户暂停通过持久化 `pausing` 状态通知当前执行者；Web 与独立 Worker 均监测该状态。执行者取消并等待全部并发请求、配图工作及本地文件写入退出，关闭模型客户端后确认 `paused`，期间保留作业锁。启动前再次原子核对状态，防止排队任务在暂停后被误启动。继续将同一作业重新入队并保留原执行阶段；正文完整且已进入审阅或导出时，不重启业务研究。成功调用与已保存章节继续复用，中断调用只能重新请求；真实调用计数、原有失败重试记录及检索轮数不重置。未完成调用的中断不占失败重试名额，但已经计入的总调用额度不退回。`run_timeout_seconds` 仍限制每次执行窗口，继续任务会开始新的窗口。

升级不会自动改动已结束的旧文档；符合检查点契约的待确认作业仍可经用户显式补答或重试开启新轮，先归档原交付。旧自研引擎的未完成作业恢复时，如果没有 WorkPlan，会补建执行计划，复用已有节点和证据，并执行新的任务整体审阅；不会沿用旧的最终审阅结论。已退役框架作业沿用原迁移规则。

## 第一版边界

WorkPlan 的任务分工在执行前确定；依赖审查只修改尚未开始任务的阻塞边，不进行运行中动态拆分、合并或任务重规划。单节点多个研究子任务的协作也未实现。Word 目录结构已改为 LLM 根据写作要求和资料一次规划，程序校验目录结构、可选模板约束，并由模型审查来源要求在目录中的去向；详见 [LLM目录规划设计](outline-planning.zh-CN.md)。

默认单任务最多8个内容节点（`max_work_sections`），业务并行上限默认16个任务（`max_parallel_tasks`），没有就绪候选截断窗口；每个任务累计最多3轮内部检索，启用搜索服务时额外最多2次联网补证，单次资料读取/检索字符预算默认600,000，多轮结果累计保存。所有 LLM 请求默认输入600,000 Token、输出128,000 Token，服务不能计数时使用明确标记的本地 Token 估算；已知服务窗口更小时仍须符合实际容量。仅缺少 Token 计量能力的兼容 Runtime 和独立判断服务使用600,000字符回退。主 LLM 选材不再受32,000字符和24项候选限制；所有独立判断模型统一每页最多24项判断，超长项无损拆分。这些是资源预算，不是标题级别或业务类型规则。

模型调用次数预算耗尽或受支持的服务/超时中断时，只有全部目录节点的正文及容器状态均已保存，才停止新模型调用并导出 `needs_confirmation` 草稿；明确记录检查未完成，保留原疑点、有效配图和待补图位置，`review_passed=false`。正文未齐全则仍失败并保留检查点。技术中断草稿不算完整生成验收通过；暂停/取消、存储错误、程序错误和导出失败不被该路径掩盖。待确认不会自动续跑，只有用户明确提交补答或重试及新轮额度后才重新排队。

任务计划和记录目前通过 API 及文件查看，GUI 沿用简洁的对话与过程展示，没有引入任务看板或编辑页面。字体、表格和目录统一由内置版式渲染。

## 完整的节点任务分配

工作计划的内部模型仍是 WorkPlan / WorkTask。真实 LLM 传输由每个任务返回 `node_refs`，使用 n1、n2 等可逆短引用。JSON Schema 直接限制每组节点数量并限定合法编号；程序检查节点唯一归属、完整覆盖及无环依赖。模型漏掉节点时，保留已生成分组，只将剩余节点交给下一次调用；新任务不能重用已有任务编号，可以声明对已有任务的依赖。最终完整计划通过校验后才开始生成。此修复仍受三次规划调用上限约束，不按固定目录层级或节点顺序替模型分组。即使有子节点，凡列入内容节点清单的节点也必须分配；只有明确标记 container 的节点不进入清单。

runtime/work_plan_transport.py 只按模型选定的归属恢复内部 section_ids，不自行分组、补任务或选择负责人。任务 ID 重复、归属缺项、归属不存在的任务仍会报错；内部继续校验唯一写入负责人、依赖无环、每任务节点数上限。失败反馈携带已返回的无效计划供修正。工作计划未完成时界面明确标识该阶段，不再笼统提示检查知识库。

工作计划使用独立的 `work_plan_attempts`（默认最多 3 次模型调用），其他常规调用仍遵守 `call_attempts`；内部检索和可选联网补证分别遵守上述任务预算。超限反馈包括具体任务、节点数量及全部节点引用；修正时传入上一次候选计划。输入同时提供总节点数及最低任务数，要求模型保留有效分组并拆分超限业务子问题。达到预算后明确失败，不无限重试或自行补造任务。

## 正文校验的上下文范围与模型容量

`extract` 只接收当前节点、完整正文、原始证据和本次反馈，不再携带整组任务节点及其他章节正文。`validate` 保留当前正文、证据、共享业务记录、建议方案和依赖结论；跨章节原文一致性由 `review_work` 及全局审阅负责。这样避免在逐节点事实抽取中反复传入整组正文，也避免把其他章节的事实误抽取为本节结论。

`runtime/extraction_transport.py` 将抽取响应字段转换为短名称，收到后还原原业务结构，并统一设为 `candidate`。事实文本、限定条件、实体和引用保持不变，`supported` 仍由独立核验决定。数据库及历史缓存继续使用完整字段名；这是传输压缩，不是减少抽取或合并校验步骤。

正文已经完整返回后，若 `extract` 或 `validate` 在原有尝试额度内仍因连续空白、输出截断、协议错误、重复输出或超时而未完成，保留正文并继续其他章节，同时记录“事实抽取/正文核验未完成”的待确认项。抽取失败不采纳半份 JSON，核验未完成的事实保持 `candidate`，确定性检查仍执行，不能标成通过。配置、认证、额度、容量及程序错误不使用这一处理方式。界面明确显示具体章节、失败原因和处理结果，不以增加重试次数掩盖失败。

运行时遇到服务端明确返回上下文容量错误时，读取响应中的数值诊断，在输入和 Schema 不变的前提下调低输出预留（每次最多保留原预留的 75%，并留出窗口余量），容量调整最多 3 轮（原生工具兼容重试另计 HTTP 次数）。只对尚未输出正文的容量拒绝执行调整；输入本身过大、数值诊断不足、普通 400、认证失败均不套用此策略。返回截断仍视为失败，不能接受半份 JSON。成功调用的 usage 记录 `context_rejections` 和 `effective_max_tokens`。传输层调整仍失败时，引擎不再添加格式反馈原样重试。发送前优先使用服务端 tokenizer 测量实际输入并预留配置的输出额度；服务不支持计数时采用标注的本地 Token 估算。可分批动作收到容量/输出截断后调整请求边界，成功子请求独立复用。

共享正文中的自动建议与 `model_proposals` 完全相同时，用 `proposal_ref` 指向相同 `gap_id` 的完整内容，避免同一大段建议在多个已写章节中重复传输。只有正文文本（含建议标签）完全一致才替换；人工修改或模型改写的段落保留原文，事实段落及引用不变。正文模型中未写出的默认字段由提示词明确解释。此紧凑格式用于任务整体审阅；持久化正文、最终 Word 不变。

## 动作选择与检索上限

每次 `next_action` 只提供当前允许的原生函数（`search`、`write`、`pending`），由主 LLM 通过 `tool_calls` 选择，程序校验调用与剩余额度。内部检索用尽后移除 `search`；协调器负责剩余联网补证及缺口补全。无效调用在原预算内反馈，不静默改为写作。

可选判断服务只负责意图和资料相关性，不负责 `next_action`、工具参数或研究额度。详见[LLM 交互流程](model-interactions.zh-CN.md)。

## 最终排版与交付

正文审阅完成后先生成内置版式 DOCX，再按现有 WorkPlan 业务组调用 `format_document`，不重新规划或改写正文。[排版流程](../src/folio/orchestration/formatting.py)每组最多3次调用、25秒，全阶段最多120秒，每次调用只尝试一次。模型只提交格式白名单补丁，字号相对原初始版式基线最多调整1磅，文本、顺序、封面、标题、字体和建议红色受程序保护。失败或超时不阻塞交付；通过保护检查的调整才进入最终分页，调整导致分页失败则恢复内置版式。该阶段读取段落、表格等格式属性，不代表检查了实际页面的美观程度。

业务 Agent 通过正文中的 `VisualRequest` 确定原型图或流程图的含义、来源块和插入位置，共享 `VisualAgent` 复用既有生成/渲染/校验流程。来源无实质问题的图可在局部核验后后台制作，与其余写作并行；最终导出按当前正文身份合并有效结果。

最终 Jev 逐页评分、低分自动修正与重新评分流程已取消，正常生成不再以页面评分作为交付条件。图片输入能力保留给研究和风格分析。历史评分报告及可验证补丁仍可读取，不将历史未完成审校改写为通过。独立项目 DocPolish 尚未接入 Folio，不会在交付时自动运行。

`formatting.json` 保存基线、补丁和未完成范围，`layout.json` 保存结果摘要。`reformat` 可重放匹配的安全补丁，不重新调用模型；详细边界见[材料与 Word 排版设计](source-materials-and-layout.zh-CN.md)。

## 正文任务的无损传输格式

`runtime/business_transport.py` 统一处理写作、抽取、校验、检索决策和审阅请求，不改变数据库中的业务结构或 Word 内容：

- 长的节点、证据、事实及正文块引用，转换为本次调用有效的 `sfrefN` 短编号；仅转换明确的引用字段，普通原文和表格单元格不替换。模型响应中的引用恢复为原编号后再验证。
- 多行且字段相同的对象数组，采用 `$columns` 声明字段名一次、`$rows` 按原顺序保留全部值。不同字段的对象不合并；空值、换行、表格结构和原文全部保留。这只是传输编码，不是材料摘要或任务拆分。
- 模型可读消息携带紧凑完整传输 Schema；结构化输出模式同时使用 `response_format` 约束，普通提示词模式依靠消息中的同一契约。
- `LLMRuntime.request_parts()` 同时供发送请求和 `prompt_chars()` 使用。局部调用预算、业务任务审阅拆批及全局审阅拆批均依据实际传输消息计算，避免先按原始冗长 JSON 拦截一个本来可以发送的紧凑请求。

当前由按动作选择资料、紧凑传输、服务端 Token 计数或明确标注的本地估算，以及请求分批共同管理容量，默认输入600,000 Token、输出128,000 Token；兼容 Runtime 的600,000字符回退值不与实际 Token 预算取交集。压缩效果取决于输入结构，不能把某次真实请求的压缩比例当作固定保证。紧凑表示不能消除模型容量的物理上限；仍超限时不会截断原文或接收不完整模型结果。

## 写作输出重复与截断

`generate/repair` 的流式响应通过 `RepeatedParagraphGuard` 逐个读取完整正文块。忽略 `block_id` 后其余字段完全相同的长段落连续出现3次，或最短周期为2–8个段落的一组正文连续循环3轮，均中止流并关闭连接；后一种要求单周期非空白文字至少60字符，单个长段落阈值为80。来源、引用、正文及范围差异保留，标题、表格和显式范围变化会重置序列；短标签不会通过重复计数凑阈值。完整响应及缓存也执行检查。检测只拒绝异常输出并沿用原重试额度，不删除正文或拼接部分JSON冒充完整结果。

重复和输出截断分别给模型提供明确的重试反馈，要求不重复规则、不重写其他节点或已有模型建议，并在当前节点完成后结束 JSON。仍遵守 `call_attempts`，不提高输出额度、不无限续写。达到重试上限则保留已有检查点并准确提示失败类型。重复输出与正常长正文需要区分，诊断记录应保留错误类型，不能一律解释为输入材料过大。

## 请求工作集与业务任务解耦

完整实现、动作输入契约、分批覆盖、恢复和审计路径见 [请求上下文与容量设计](context-and-capacity.zh-CN.md)。上游完整审阅报告不再直接透传到下游普通请求，业务任务边界不再承担请求容量保护的职责。

## 并发审阅与组进度

跨任务审阅先固定本轮节点版本及分组，再由最多 `max_parallel_reviews` 个协程领取组；完成后继续领取下一组。结果按原分组顺序汇集、按类型、位置、引用及规范化描述去重；同短键不同问题保留独立身份，并保留事实键冲突的确定性检查。与业务写作并行度 `max_parallel_tasks` 分开配置。

某组失败或外部取消时，取消并等待其余审阅协程退出后才释放作业锁；已成功的请求仍可从持久化缓存恢复。同一引擎中完全相同的请求使用锁串行进入缓存/调用过程，避免多个父组拆出相同子请求时重复调用、竞争重试次数或覆盖结果。

界面显示“共 N 组，最多 K 组同时处理”和“已完成 X/N 组”。这里的组数是本轮顶层审阅分组；组内部因容量不足再拆小不会改变该总数，所有子请求完成才计该组完成。审阅计划和逐组结果分别保存在 `contexts/review_plans`、`contexts/review_results`，成功子请求继续使用 SQLite `tasks` 缓存。

### 客观待填项与业务补查

正文可用 `record_only_pending` 标记现有表格空白单元里的姓名、联系方式、文档日期、版本或编号。每项绑定真实表格块、最终表格行列及逐字列名；表头行号为0，首个数据行为1。同一空格可以分别缺姓名和联系方式，按位置及 `kind` 判断重复，保留各项说明。它只生成后台待填写项，不进入业务补查，也不编造值；正文校验和任务审阅仍检查是否误把业务规则归类为元数据。分页保留原行号与表头，业务主表恢复同步引用。旧 `pending_items` 不按关键词重新分类，业务信息缺口仍走原流程。待填项不会被当作审阅通过。

精查 `confirmed` 的含义是“候选问题成立”，并非“正文正确”。理由为“无矛盾、无需修改”时应返回 false；确认有错误且无需用户决定时，必须同时给出有效目标节点与具体修复指令。字段互相矛盾的响应会重试或保留未完成结论，不自动猜测并改写裁决。
