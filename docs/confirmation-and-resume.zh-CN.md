# 待确认补答与续跑设计

> English version: [English version](confirmation-and-resume.md)

待确认补答的实现入口为 [confirmations.py](../src/folio/confirmations.py)、[会话接口](../src/folio/api/confirmations.py)、[Engine](../src/folio/orchestration/engine.py) 和 [ConfirmationPanel.vue](../frontend/src/components/ConfirmationPanel.vue)。失败或暂停任务另由作业控制接口恢复。两种机制都复用已确认目录、业务任务归属和现有检查点，不重新生成整本正文。

## 失败或暂停后的继续生成

正文任务因模型接口等执行错误进入 `failed` 时，页面在失败诊断下提供“重试并继续”。刷新或重新打开会话后仍可操作；恢复接口失败会保留诊断和恢复入口。暂停任务继续使用输入框旁的继续按钮。

用户也可以直接说“接着上次的任务继续”。意图识别通过 `resume_generation` 进入续跑分支，先查当前会话绑定的正文任务，再调用 `POST /jobs/{job_id}/resume`。恢复沿用原任务 ID、已确认目录、已保存正文、研究检查点和成功请求缓存；失败或取消的未完成步骤重新执行，不经过目录规划。没有可续跑的正文任务时明确提示，不能自行重新生成目录。

失败恢复不会清零累计模型调用次数，也不默默增加调用上限。已经输出的 `needs_confirmation` 草稿仍走下文的补答入口，已发布文档和普通草稿不作为失败任务恢复。运行中的同一任务只重新订阅进度，不重复创建后台执行。

前端恢复成功后订阅同一任务事件，并显示“从保存的进度继续生成正文”。事件重播从最近的续跑边界开始，历史失败或暂停事件不会覆盖当前运行状态；完整历史继续保留在后台审计中。

## 用户操作与状态

完整正文交付为 `needs_confirmation` 后，页面列出当前问题及涉及章节。用户可以只回答其中一部分，也可以因模型服务恢复而不填答案、仅重新执行未完成检查；两种操作都必须显式提交本轮调用额度。空答案不会被解释为对业务规则的批准。未回答的业务问题保持待确认，即使模型本轮没有再次报告；同一答复能解决多个关联问题时，可在各问题框中分别填写。技术、版式及有明确检查器的封面、来源批注问题通过对应检查重建，不能因历史问题保留而永久冻结。

补充确认是可选操作，已有文档可直接下载。标题栏可以展开或收起；点击“跳过本次补充”后仅保留一行提示和“重新补充”入口，已填答复继续保留。跳过不提交答案、不启动重新检查、不增加模型额度，也不清除文档中的待确认标记。折叠与跳过选择按会话、作业和确认 `revision` 保存在当前浏览器，刷新或切换会话后保持；新一轮确认自动展开。

```text
needs_confirmation
  → 用户提交当前问题版本、可选答复和本轮额度
  → 归档旧交付，原子保存续跑记录，queued / review
  → 读取已有正文，落实本轮答复
  → 任务与全文审阅、必要修复、配图核对、Word 交付
  → published / draft / needs_confirmation，或明确失败
```

普通执行入口不会自行重启待确认作业。已发布文档及普通草稿也不会通过此接口直接修改。只有完整目录节点的正文检查点齐全，才能从待确认状态接续；原有暂停/继续另有独立控制接口。

## 接口与并发保护

| 接口 | 契约 |
| --- | --- |
| `GET /jobs/{job_id}/confirmation?conversation_id=...` | 校验会话归属，返回问题列表、`revision`、累计调用次数及默认本轮额度 |
| `POST /jobs/{job_id}/confirmation` | 接收 `conversation_id`、`request_id`、`revision`、`answers` 和 `additional_calls` |
| `GET /jobs/{job_id}/confirmations/{request_id}/artifact` | 下载对应续跑轮次之前归档的 Word |

`answers` 为 `{issue_id, answer, close_comment?}` 列表，`close_comment` 默认 `false`；一次最多40条，每条答复最多600,000字符，同一问题不能重复或提交空白答复。问题 ID 使用 `Finding` 的 v2 身份。`revision` 由当前问题快照、作业输入、各章节版本及上一续跑轮次共同计算，旧页面不能覆盖新问题。

提交时先取得会话锁和作业锁，再以 SQLite 事务检查状态、保存轮次并将作业排队。客户端为一次提交保留稳定的 `request_id`，网络重试须携带同一 ID 和完全相同的内容；相同请求只生效一次，不重复增加额度或写入答复。复用同一 ID 却改变内容、作业不属于当前会话、状态或问题版本已变化，均返回冲突。

前端按会话和作业保存尚未提交的答复及请求 ID，切换会话时隔离异步返回。提交成功后重新订阅作业事件，旧下载消息指向归档 Word，新的交付对应当前运行结果。问题视图、会话恢复及交付事件提供历史草稿列表，刷新页面后仍可下载先前版本。

## 调用额度与恢复

本轮额度 `additional_calls` 默认200，允许1～10000。新的作业调用上限为 `已消耗 calls + additional_calls`，而非在旧上限上无条件叠加；累计计数始终保留，总上限100000。剩余旧额度不额外叠加，接口重试不重复授权。成功请求缓存继续复用，失败或未完成请求的尝试检查点在新轮清理，旧失败详情和计数保存在事件及续跑审计中。

本轮修复额度从提交时各章节的实际 `revision` 起算，已有修复次数不会让新答复立即失去修订机会；本轮仍受原 `max_repairs` 限制。知识库和联网检索次数仍按业务任务累计，不因补答而清零。配图预生成的软额度使用当前总上限命名的独立预算桶，但整体调用次数仍覆盖此前全部尝试。

V2 文件研究为显式续跑建立新的研究额度归属，身份包含本轮 `request_id`；普通暂停、恢复和自动修复不重置额度。即使只增加调用额度而没有新增业务答复，也能重新进入此前未完成的研究，而不会复用已耗尽的研究会话。原始工具记录和旧额度保留，新的研究模型调用仍计入整篇总账，并为后续正文与审阅保留额度。

## 答复如何进入正文

每条答复连同原问题、来源 ID 和限定章节加入不可变需求修订记录，更新 `JobInput.requirements` 与完整要求文本。`ConfirmedReferences` 将业务答复提供为 `human_confirmation=true` 的项目依据，保留来源和版本，不改上传原件，也不把用户答复伪装成外部法规或知识库证据。

明确的业务、封面和版式补答同时作为修订记录保存在当前会话，后续重新规划目录仍能使用；只重试服务的操作不产生新写作要求。相同问题的新答复替代旧答复成为必需项目依据，原始答复继续留在轮次审计中。

处理本轮答复时，只重新理解涉及的业务任务，只直接修订问题列出的内容章节；章节仍由原业务负责人写入。修订结果必须对应分配章节且版本递增一次，所有正文修改与本轮完成标记在同一批事务中提交。失败不能留下“只改了一半却已应用”的轮次。其余正文、目录、来源和既有检索额度保持原契约，后续完整审阅仍可以发现并按原规则修复其他真实问题。

封面答复写入指定封面字段。来源批注答复保留与原批注的对应关系，默认不关闭批注；只有用户明确勾选“此答复已解决这条来源批注”，且本轮正文与 `applied` 状态原子提交成功，才设置 `resolved`。仅填写“不确定”或提交一个非空答案不会自动关闭批注。

页面版式与技术中断问题不作为新增业务事实，不因“确认了”就跳过实际页面检查或原来未完成的审阅。空答复技术重试也会重新执行此前 `local-check-incomplete` 的事实抽取和正文核验，保留已有正文，不以沿用未完成的局部检查结束续跑。答复不是直接删除问题的指令：修订后仍须完成适用的结构、来源和语义校验。

研究额度不足、覆盖范围未核定和计算核验未完成均有专门的待确认项。重新检查会复核当前覆盖清单和派生问题；研究模型返回空缺口列表、普通审阅认定可通过，都不能直接关闭这些问题。未核实计算只有在同一产物通过核验，或独立审阅确认正文未使用该主张且实际任务要求已有原始依据时才能解除；正文和来源版本变化后再次检查。

新审阅合并最近一轮原问题快照中尚未被明确答复的业务待确认项，已成功应用的历轮答复按准确问题身份匹配，不按主题或章节相同推定已解决。精查中断、修复额度耗尽等包装问题若能对应到同一快照中的原始候选，交回原精查和修复链处理；没有可核对原问题时保守保持待确认。新的完整审阅完成前再次中断会恢复上一轮的问题清单，完整新结论已保存后则不重新引入旧疑点。

本轮保留全局事实的研究快照策略，不新增事实订阅、自动广播或跨任务实时同步。显式依赖及最终全局审阅继续承担一致性检查。

## 归档与验证边界

`confirmation_rounds` 保存请求、原问题、答复、提交时章节版本、旧输入/快照和累计调用数；`jobs/{job_id}/confirmations/{request_id}/draft.docx` 保存前一交付。同目录另存本轮 `input.json` 和 `requirements.json`，初始 `inputs/` 快照保持原样，避免把新要求冒充初始输入。旧失败调用另存事件审计，原始问题和误报台账不抹除。

专项回归覆盖旧版本拒绝、请求幂等、额度边界、空答复技术重试、业务答复证据范围、按章节修订、整批提交、旧草稿归档及前端恢复。自动测试不代表真实模型一定能正确理解每条用户答复，续跑后的待确认状态和审阅结果必须如实呈现。
